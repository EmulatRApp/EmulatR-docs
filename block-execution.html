Block Execution

Block execution is EmulatR's normal execution model. Once a run of straight-line code has executed, EmulatR lays its already-decoded instructions end to end as a block. The next time execution reaches that code, the whole block runs without going back through fetch, decode and the run loop's checks between every instruction.

Nothing is translated or recompiled. Each instruction in a block runs through the same execution code as the main pipeline, so registers, memory and processor state are exactly what instruction-by-instruction execution would produce. What a block saves is the approach work around each instruction, not the instruction itself.

What ends a block

A block is built only from code that has already run, and it stops at whichever comes first:

•an 8 KB page edge -- a block never spans two pages;

•code that has not been decoded yet;

•a CALL_PAL or other privileged (hardware-format) instruction;

•an unconditional transfer, which is kept as the block's last instruction;

•the EMULATR_BLOCK_MAX limit.

A conditional branch that is taken leaves the block early. The smallest block is two instructions. Code that does not form a block simply runs on the main pipeline -- the difference is speed, never results.

Interrupts and time

Interrupts are checked at block boundaries and at the configured sweep interval rather than after every instruction, so delivery can lag by a few guest cycles. Asynchronous system traps (ASTs) are never deferred, and the interval timer is edge-exact at any block depth: a timer boundary inside a block cannot be stepped over.

Settings

All three are read once, at start-up; changing them mid-run has no effect.
