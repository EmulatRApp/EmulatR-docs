1. One sentence

EMULATR_BLOCK_MAX is the maximum number of instruction descriptors the block executor will place in a single block -- i.e. the longest run of straight-line guest instructions EmulatR will execute before returning to the run loop to service time and interrupts.

 

It is a performance dial, not a correctness switch. That sentence is only true as of the F-1 fix; section 7 explains why it was not true before, and why that history matters when reading older measurements.

 

2. Where it lives

EMULATR_BLOCK_MAX descriptor cap per blockdefault 32, clamped 2 .. kMaxCap (256)pipelineLib/BlockCache.h blockMax()

 

Companion geometry dial, frequently confused with it:

EMULATR_BLOCKCACHE_BLOCKS number of block FRAMES in the cachedefault 8192, floor 256, rounded DOWN to apower of two (the slot index is a mask)

 

BLOCK_MAX is the depth of one block. BLOCKCACHE_BLOCKS is how many blocks are retained. They are independent, and confusing them produces nonsense conclusions about memory.

 

Both are read exactly once, in a function-local static initializer. Changing the variable mid-run has no effect, and the value is fixed for the life of the process. Per the SPEC-BATCH-001 Sec 7.2 ruling, every measurement pins them explicitly and a release ships one frozen default.

 

3. What a block is

A block is a bounded straight-line descriptor run: what the DecodedICache already memoized per instruction, laid head-to-tail from a head PC.

 

struct Desc { 

// 16 bytescoreLib::GrainEntry const* ge; 

// semantics + exec functionuint32_t encoded; 

// the instruction worduint8_t primaryOp;

};

 

struct Block { 

// 56 B header + 16 B * kMaxCapuint64_t head; 

// full pc incl. the PALmode bituint64_t linkFall, linkTaken; 

// D-1 slots: filled, NEVER followeduint64_t vaPage;uint32_t pageGen, mapEpoch, contentEpoch, fetchGen;uint16_t count, flags;uint8_t asn, mode;Desc desc[kMaxCap];

};

 

Blocks are held direct-mapped by head PC -- (pc >> 2) & (frames - 1). A conflict is simply a miss, and a miss refills through the fully faithful path. There is no associativity and no eviction policy to reason about.

 

3.1 A block is not a translation

Nothing is compiled, and no semantics are rewritten. Execution replays the faithful back-end verbatim, per instruction:

PipelineDriver::buildCtx

•(GR)grain execFn

•(EX)MemDrainer::drain

•(MEM)PipelineDriver::retire

•(WB)plus the same per-retire bookkeeping the faithful path performs -- cycle tick, RetireProfiler, profile counters, the BYTECHECK seam, the trace hook. A traced block run therefore feeds the same retire stream the reference path produces, which is what makes the Gate 2 retire-diff meaningful.

 

What the block eliminates is not the work of executing an instruction. It is the per-instruction approach work: the fetch/decode probe, and the run loop's boundary predicates.

 

4. What bounds a block -- the cap is only one of six

Fill is a forward walk over already-decoded instructions. The DecodedICache is the side-effect-free decode oracle, so fill probes it per PC and stops on the first cold slot. Blocks therefore form only over code that has already executed -- the reuse principle enforced by construction, with no speculative translation and no architectural side effects during fill.

 

Fill stops at whichever comes first:

Conditional branches do not stop fill: a taken conditional is an early exit at execute time, detected by the divergence check.

A fill producing fewer than 2 descriptors is discarded (count = 0, "not worth a frame"), so the smallest real block is 2 instructions -- which is why the clamp floor is 2 and not 1.

The practical consequence: raising the cap only helps where conditions 1-5 do not already bind. On real Alpha code, basic blocks between unconditional transfers and page edges are short. This is the whole reason the dial saturates (section 6.2).

 

4.1 What terminates a running block

Execution exits early -- before count -- on any of:

•cpu.halted

•Divergence: cpu.pc != slot.grain.pc + 4 (a taken branch, a divert, or a fault delivery)

•F-2 interrupt break-out (section 5.2)

 

5. How it moves run time

5.1 The mechanism: amortizing the boundary, not the instruction

On the reference path the run loop runs its boundary work once per retired instruction. With blocks, that same boundary work runs once per block exit. The instruction work itself is unchanged.

Boundary work per exit includes evalDeviceIrqs() (the UART -> 8259 -> DRIR level mirror), the interval-timer edge test, the acceptance predicates (pendingIrq0/1/2/3 + canAcceptInterrupt), the stop-sentinel poll on its coarse cadence, the RSCC warp trigger, and the auto-snapshot check.

 

So the first-order model is:

time ~= N * (instruction cost) + (N / L) * (boundary cost)

where L is the achieved mean block length -- not BLOCK_MAX. The dial raises the ceiling on L; conditions 1-5 decide the actual value. This distinction is the single most common source of wrong expectations about this knob.

 

5.2 Why depth does not cost interrupt latency (F-2)

Naively, a block of depth N delays interrupt detection by up to N instructions. That was true, and it is why the cap could not simply be raised.

F-2 (JRN-V2-SINGLEPIPE-001) puts the Cchip's own pending computation inline in the execute loop:

 

if (i != 0 && (drir & dim & kIrqBreakMask) != 0) return;

 

systemLib::Machine pushes the Cchip's DRIR/DIM words and the mask into pipelineLib at construction (a one-way push, so pipelineLib gains no chipset dependency). The pointers default to a shared zero word rather than nullptr, so the hot loop needs no null check -- unpushed, the test folds to false. Cost: two relaxed loads, two ANDs, one predicted-not-taken branch.

 

Three properties make this sound:

•Breaking out early is always safe. The loop returns; the caller's systemTick runs exactly as at any block exit and decides delivery (IPL, DIM, PAL state). This relocates detection, never delivery.

•Forward progress is guaranteed by i != 0: every entry retires at least one instruction. Without that guard, an interrupt the CPU cannot yet accept (IPL masked) would break at i = 0 forever -- zero retires, livelock. With it, the degenerate case is one retire per tryRun: exactly the reference path's granularity and cost, never worse.

•No PC bookkeeping is needed: the divergence check guarantees pc == head + 4*i at the top of iteration i.

 

Net: device-interrupt latency is one instruction at any depth.

Do not raise kMaxCap on a tree without F-2. There, depth N really does mean N-instruction device latency.

 

5.3 Why depth does not lose timer ticks (F-1)

The interval timer is tested on a crossed-edge predicate:

 

timerFires = (now != 0) && ((now >> bit) != (last >> bit));

not on exact equality ((now & mask) == 0).

 

A block advances the clock by up to BLOCK_MAX between checks, so an exact-landing test would step over an edge that falls inside a block and lose the tick. The crossed-edge form cannot.

This is a strict generalization: when the clock advances by 1 per check the two predicates are byte-identical, so the reference path is unchanged. A block is at most 256 cycles against a 2^19-cycle period, so at most one edge can fall inside a block and a single fire per check is sufficient.

 

5.4 The boundary check is unconditional, by ruling

The block executor's boundary check is unconditional and periodic (epoch/budget), never a conditional event gate -- SPEC-TC-001 Sec 11.6.

 

This is a settled design ruling with an expensive provenance. The S-3b experiment (2026-08-22, built and removed the same day) tried to skip the IRQ/timer section on retires where "nothing can need service". The gate was self-referential: it tested pendingIrq1, which reads drir & dim, but for every ISA-class device that DRIR bit is set by mirrorIsaIrqs(), which lives inside evalDeviceIrqs() -- inside the section being skipped. UART/FDC/8042 interrupts were invisible until a backstop fired. Measured cost: post-banner gap to %STDRV went 174 s ungated to 502 s gated.

 

Method note worth carrying: the full test suite passed 637/637 on every defective build. Only a boot-to-Username twin detects this class of defect.

6.2 Why 256 and not more

kMaxCap was raised 64 to 256 on 2026-08-26 after weighing 1024 and rejecting it. The reason is block population, not storage: blocks terminate at page edges, unconditional transfers, and PAL/HW-format instructions regardless of the cap, so above ~256 there is storage with no population to fill it. Revisit only with JRN-V2-BLOCKPHASE-001 data in hand.

 

6.3 Memory -- the trap

Block = 56 B header + 16 B * kMaxCapCache = Block * frameCountAt kMaxCap 256 and 8192 frames: ~34 MB (was ~8 MB at kMaxCap 64)

desc[kMaxCap] is sized at compile time.

 

Therefore:

Setting EMULATR_BLOCK_MAX=4 does not reduce memory. It still allocates 256 descriptor slots per frame and simply refuses to fill past 4. Only changing kMaxCap (a rebuild) changes the footprint; only EMULATR_BLOCKCACHE_BLOCKS changes it at run time.

 

count is uint16_t, so the structural ceiling is 65535 -- do not exceed it without widening the field.

 

7. History that changes how you read old data

Before F-1, depth 32 stalled at TDF (a TIME operation) / DECdtm, while depth 4 and blocks-off both booted. The dial was then a correctness hazard masquerading as a tuning knob: the exact-equality timer test lost ticks that a deep block stepped over.

 

After F-1 (crossed-edge) and F-2 (in-loop break), depths 64 and 256 both boot with margin, and the dial became a pure performance dial.

Consequence for anyone reading pre-2026-08-26 measurements: a stall or anomaly attributed to block depth in that era is very likely the timer defect, not a property of depth. Do not carry those conclusions forward.

 

8. Interactions and caveats

•Overshoot. With blocks on, --max-cycles overshoot is bounded by BLOCK_MAX - 1. A run will not stop exactly on the requested cycle.

•Retire shift. Interrupt delivery may legitimately shift by up to BLOCK_MAX cycles between runs; tools/cmp_retire_shift.py takes this as a tolerance parameter. Its default still says 64 -- pass the depth you actually ran.

•PAL mode never enters a block ((cpu.pc & 1) != 0 returns false), so depth has no effect inside PALcode.

•Flagged pages run on the reference path. Today that set is exactly the UDELAYWARP anchor page: a block containing the anchor would hide the warp trigger. Other armed instruments (PC/value gates, DIAG PC windows) force the executor off globally -- the S-3b lesson, that a census which can be incomplete must fail safe rather than silent.

•Snapshots start cold. The cache is transient host state and is never serialised, so the first post-resume execution re-fills. Depth does not survive a resume; a resumed run's early throughput is not comparable to a warm one's.

•The spin census depends on blocks being on. BlockExecutor::noteSpin feeds traceLib::WarpProfile and is the only detector that can see delay loops the 0xB740 RSCC anchor is blind to (the anchor page is deliberately kept off the block path, making the two complementary). With EMULATR_BLOCKEXEC=0 that census is silent.

•Not a fidelity lever. Depth changes when boundary work happens, never what an instruction does. If a guest-visible behaviour changes with depth, that is a defect in the boundary machinery -- as F-1 was -- and must be chased as one, not tuned around.
