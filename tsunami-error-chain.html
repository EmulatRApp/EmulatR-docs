Tsunami Error Chain (PERROR / No Devsel)

EmulatR models the 21272 Pchip PCI error-reporting chain end to end (21272 HRM Ch 8.8 and 10.2.5.6-10.2.5.8). When a PCI transaction fails in a way the Pchip latches on real silicon, the emulated Pchip latches it the same way, raises the same error interrupt, and the guest firmware or operating system reads the same registers a real DS20 would present. If the SRM console prints:

 

Error detected by Pchip 0

    PERROR = 0070010011480100

        No Devsel

 

that is the SRM's own IRQ0 error handler decoding EmulatR's PERROR register. This topic explains the chain, how to decode the value, and what a report means for troubleshooting.

 

The chain, end to end

1. A CPU access reaches the Pchip's PCI dense-memory window and NO device claims the address (on real PCI: no DEVSEL, a master abort). The read returns all-ones; a write is discarded.

2. If the corresponding PERRMASK bit is set, the Pchip latches the error bit in PERROR together with the failing PCI address and command. The FIRST latched error freezes the register; later errors can only set LOST.

3. The Pchip asserts b_error to the Cchip, which raises DRIR bit 62 (the Pchip0 error interrupt, HRM Table 6-9). That is an IRQ0-class interrupt.

4. The guest's error handler reads PERROR, reports it, and writes 1s to clear (W1C). When all error bits clear, the register unfreezes and b_error deasserts.

What EmulatR latches today

Source

When it latches

NDS (No Devsel)

Unclaimed dense PCI-memory read or write (master abort), and master-aborted CONFIG WRITES. Exempt by the HRM itself: config READS and special cycles (HRM 8.8.2.1), and sub-64K legacy I/O ports (the south bridge claims ISA ranges subtractively).

SGE (scatter-gather error)

A DMA scatter-gather walk fetched an invalid page-table entry (V bit clear) inside an SG-enabled window (HRM 8.8.2.5).

All other sources

TA, RDPE, PERR, APE, SERR, DCRTO are not yet wired (they require PCI master/target timing models). Documented in the source TODO table.

 

PERRMASK gating

Out of reset, PERRMASK = 0: NOTHING latches (HRM 10.2.5.7 -- the default is all errors disabled). Firmware enables reporting by setting mask bits; the DS20 SRM does this during console init, which is why boot-time BAR sizing probes never storm the handler but a post-init unclaimed access reports immediately. LOST is gated by mask bit 0 like every other bit. PERRSET (W1S) honors the same mask and the same freeze semantics.

 

When you see No Devsel: it is a real finding

As of 2026-08-02, every device EmulatR presents in PCI config space also DECODES the memory/IO windows its BARs claim -- behavioral models answer with real behavior, and config-only stub devices answer with an inert claimed window (reads float all-ones, writes absorbed, logged as STUB-BAR rows on stderr). A No Devsel report therefore names a GENUINELY unclaimed address: decode the ADDR field and ask what assigned that address and to whom.

 

Case study (the report shown at the top of this topic): the DS20's DE500 tulip was declared as a config-only stub, so the SRM assigned its memory BAR but nothing claimed the window. The ew driver's SROM/microwire polling at PCI 0x0100_1148 then master-aborted on every access -- a write/write/read rhythm of No Devsel reports. The correction was to bind the behavioral 21143 model (which claims its BARs) and to make stub devices claim their windows in general. The error chain was working exactly as documented; it made a real modeling gap audible.
