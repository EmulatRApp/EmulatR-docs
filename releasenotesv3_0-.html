3.0 (Experimental)

The full User and Developer Reference is published online at https://EMulatRapp.github.io/EMulatR-docs/. It is the same guide the kit installs as documentation/EMulatRGuide.pdf, and it is updated with each release.

 

EMulatR 3.0 is an experimental release. This page records what has changed since 2.1 was frozen on 30 September 2026 (tag v2.1-freeze), and is the release notes for the 3.0 kit. Entries are added as the changes land, so the page describes the current build, whose badge is X3.0-2 (X marks an experimental build; the release stage is Experimental). The 2.1-1 beta kit was built before the freeze, so some changes listed on the 2.1 page are not in that kit.

 

Status, 30 September 2026

•Baseline: 3.0 opened from the frozen 2.1 build. No 3.0 change so far adds or removes a supported system or device, so each system runs what it ran at the 2.1 freeze.

•Guest behavior: with [System] cpuFrequencyHz unset, the certified DS20 boot retires exactly the same number of instructions, in the same number of cycles, on 3.0 as on the frozen 2.1 build. DS20 boots now log one new warning, and the DS10 is expected to as well; see Known limitations.

 

The status above is dated. Where the entries below differ from it, the entries below are current: the default CPU speed is now 50 MHz, and the DS10 and DS20 now tell the guest the configured speed.

 

Added

•CPU speed setting. A new ini key, [System] cpuFrequencyHz, sets the processor's clock speed as a whole number of hertz, for example cpuFrequencyHz = 500000000. It fixes how many processor cycles fall between interval-timer ticks (the speed divided by 1024); the interval timer itself stays at 1024 Hz at any speed. When the key is unset or 0, EMulatR uses the platform manifest's cpu_speed_hz default, and when the manifest has none, the legacy 536,870,912 Hz (2^29), the speed 2.1 ran at. The DS10, DS20 and ES40 manifests set a default of 50 MHz (see Changed), so with the key unset the system runs at 50 MHz; leave it unset for normal use. A value below 1024 Hz is refused with a warning and the legacy speed is used; a value that is not a whole number is reported as an ini warning and ignored. If a manifest lists the supported speeds of its model (cpu_speed_hz shipped), an ini value outside that list still runs, and the run log warns that guest timing at that speed is untested; the DS10, DS20 and ES40 manifests list 50, 60, 75, 85 and 100 MHz, so a value that is not one of those five runs with that warning. The key is a number, so it does not take a ${NAME} environment reference, and there is no command-line option or environment variable for it. The config/Emulatr.ini staged with a 3.0 build (the copy a 3.0 kit ships) lists it under [System], commented out; the 2.1-1 kit's copy does not, and neither does the Emulatr.ini the launcher writes for a new system, so add the line yourself.

•CPU clock in the run log. Every run logs the speed in use and where it came from, for example CPU clock: 50000000 Hz (platform manifest default); interval timer 1024 Hz, 48828 cycles per tick + 128/1024. The source in parentheses is ini [System] cpuFrequencyHz, platform manifest default, legacy 2^29 default, or legacy 2^29 default (requested value refused). Once per run, when the console has built its HWRPB (the table it hands to the operating system), EMulatR compares the interval clock and cycle-counter frequency the console published there with the values the configured speed implies, and logs a CPU clock agreement: line ending AGREE when they match, or a warning ending MISMATCH when they do not. The DS10, DS20 and ES40 run the console in silicon mode, in which it measures the processor, so the line ends AGREE at each supported speed.

•Console status key. Press Ctrl/ (or Ctrl/_) in the console to print an EMulatR host status line -- UTC time, host elapsed time, the exact guest cycle count, guest time and time dilation, with the change since the previous press -- and send Ctrl/T to the guest at the same moment. The ret field counts every retired instruction, including those run in JIT-compiled code, and uses the same count as the MILESTONE and PROFILE lines of the run log. The setting EMulatR_CONSOLE_STATUS_KEY changes the key byte (default 0x1F, Ctrl/ or Ctrl/_); 0 turns the key off and passes the byte to the guest. See Console Control Keys.

•Late console clients. A console client that connects after EMulatR has started now receives the console output that was queued before it connected and all output after. Previously a client that attached after any output had been produced with no client connected received nothing for the life of the connection.

•IdleScan and the idle pacing barrier. On a platform whose SRM firmware reports more than one CPU slot (the DS20 and ES40), the OpenVMS idle routine spends most of its instructions on a loop that finds the highest set bit of the CPU mask. EMulatR now executes that loop in closed form. Every instruction is still charged and credited and every register is left as the loop would leave it, so retire counts, cycle counts and the full-boot hash are unchanged; only host work is removed. IdleScan is on by default, and EMulatR_IDLESCAN=0 turns it off. Because the collapse costs the host almost nothing, an idle guest ran ahead of wall time, so an idle pacing barrier now sleeps the host when idle guest time is 2 ms or more ahead of wall time; at 50 MHz the DS20 idle dilation moved from 0.35 to 1.01. At exit the run log prints an IDLESCAN: line with the counts. The DS10 has one CPU slot, has no such loop and is not paced; its idle still runs ahead of wall time. See 6.14 IdleScan.

•Launcher: system ini file. The System group of the launcher now shows an Emulatr.ini: row with the path to the selected system's ini file, as text you can select, and an Open button that opens that file in your default editor, so you can find, edit and save a system's configuration from the launcher. The button is disabled when the system has no Emulatr.ini.

 

Changed

•The default CPU speed is 50 MHz. The DS10, DS20 and ES40 now run at 50 MHz when cpuFrequencyHz is not set, instead of 536,870,912 Hz. The supported speeds are 50, 60, 75, 85 and 100 MHz, the speeds EMulatR has been tested at. Any other value runs, and the run log warns that guest timing at that speed is untested. The default comes from the platform manifest, so existing Emulatr.ini files need no change, and [System] cpuFrequencyHz still overrides it. Boot time does not depend on the speed, and at 50 MHz the guest's clock stays closest to the wall clock while the system is idle. See Tuning EMulatR.

•The interval timer is exact at any CPU speed. The interval timer used to fire each time the cycle counter crossed a power-of-two boundary, so it ran at exactly 1024 Hz only when the processor speed was 1024 times a power of two (536,870,912 Hz, the speed 2.1 ran at, is one). Tick n now falls at cycle floor(n * speed / 1024), computed in whole numbers, so any 1024 consecutive ticks span exactly the configured number of cycles and the timer stays at 1024 Hz at any speed. Wherever EMulatR jumps the clock ahead to the next tick (for example, past busy-wait loops that poll the cycle counter), it uses the same clock. At 536,870,912 Hz, the speed 2.1 ran at, every tick falls on the same cycle as before.

•Build constant no longer sets the timer. For builds from source: the compile-time constant EMulatR_PROFILE_ALPHA_CLOCK_HZ (chipsetLib/Tsunami21272_CsrSpec.h) no longer sets the interval timer's period. The period now comes only from the CPU speed (see CPU speed setting).

•The untested-speed warning says so. When the CPU speed is not one of the platform's tested speeds, the warning now says that the speed is untested and that the system runs anyway. It no longer claims that the speed is not one a real machine shipped at.

•DS20 cold boots skip the firmware's reset-settling delays. While it resets the PCI bridges, the DS20 V7.3 PALcode waits out three fixed countdown loops. EMulatR does not need that settling time, so these three loops are now skipped by default. Each skip charges exactly the instructions and cycles the loop would have taken, so everything the guest observes, including its clocks, is unchanged, and the boot reaches OpenVMS sooner. The setting EMulatR_SPINSKIP controls it: unset skips only those three DS20 loops (matched by address and by their instruction bytes, so other firmware is never affected); 1 skips every countdown loop SpinSkip can prove safe; 0 turns skipping off. Each run's log states the mode in use (SpinSkip: ...).

•The guest is told the configured CPU speed. The DS10 and DS20 now run the console in silicon mode, as the ES40 already did. The console measures the processor and publishes the configured speed as the cycle-counter frequency in the HWRPB, so OpenVMS timed waits and timeouts are no longer stretched or shortened at a speed other than 100 MHz. The run log's CPU clock agreement: line reports AGREE; every DS10, DS20 and ES40 boot in the 50 to 100 MHz speed tests did. See Tuning EMulatR.

 

Fixed

•Instruction-fetch faults are reported as the architecture specifies. An access violation or a non-canonical address on an instruction fetch is now delivered to the console PALcode's instruction-access-violation entry (IACV, offset 0x480) instead of the data-stream fault entry (DFAULT, offset 0x380), as the 21264 hardware reference manual specifies. A fault on an instruction fetch also no longer writes the data-stream VA and MM_STAT registers; the faulting address of an instruction fetch is reported in EXC_ADDR. The check that decides whether an instruction address is canonical now follows the I_CTL VA_48 bit, as the manual specifies, instead of the VA_CTL bit used for data accesses. The console sets both bits to the same value, so a normal boot is unaffected.

•Machine reset. A machine reset now clears the decoded-instruction cache and the block cache, so no entry from before the reset can be used again afterwards, and it keeps the processor's assigned SMP slot instead of resetting it to 0. The normal start-up path resets before any instruction has run, so a boot behaves as before.

•A non-existent-memory error raises its interrupt at once. When an access to non-existent memory latches the Cchip NXM error (DRIR bit 63), the interrupt is now raised when the error is latched. Previously a deliverable NXM interrupt could wait until some unrelated event next raised an interrupt.

•JIT break-out boundary. When a device interrupt became pending during a JIT-compiled block, the block could retire one instruction more than the interpreter would have before stopping, so the interrupt boundary fell one instruction later with the JIT on than with it off. Both now stop at the same instruction.

•Console typing is no longer doubled (EMulatR PuTTY session). EMulatR opens the console in PuTTY as a raw connection. With PuTTY's default setting, Auto, a raw connection echoes what you type locally and holds each line until Return, so every character typed at the console appears twice (for example, system shown twice at Username:) and input reaches the guest only on Return. The kit installs a settings file, EMulatR.reg, in the installation folder (by default C:\Program Files\ASA-EmulatR) that creates a named PuTTY session called EMulatR (registry key HKEY_CURRENT_USER\Software\SimonTatham\PuTTY\Sessions\EMulatR). It no longer touches PuTTY's Default Settings. The session sets Local echo = Force off, Local line editing = Force off, Keyboard function keys = VT100+, a scrollback of 20000 lines, a width of 132 columns, and session logging of all session output to a file named putty_console_p10023_&Y&M&D&T.log (PuTTY replaces &Y&M&D&T with the date and time). EMulatR starts its console with putty.exe -load EMulatR -raw -P <port> localhost, so the look and the logging come from the EMulatR session and only the per-system port is on the command line. The launcher's Open Console uses the same session (putty.exe -load EMulatR -telnet <host> <port>). Setup imports EMulatR.reg automatically at the end of the installation, so the session exists for the Windows user who ran setup and that user needs to do nothing. Uninstalling removes the EMulatR session and also removes the two values (Local echo and Local line editing) that the 3.0-1 kit wrote into PuTTY's Default Settings. If the EMulatR session is missing, EMulatR starts PuTTY without it and writes the log itself, as putty_console_p<port>_<date-time>.log; the console then shows each typed character twice, because of PuTTY's built-in Auto echo, so import the file as described below.

•A new system gets a memory size its platform supports. A system created in the launcher now gets the platform's board maximum, capped at 4 GiB: 2 GiB for a DS10, 4 GiB for a DS20 and an ES40. Before, every new system asked for 4 GiB, and a DS10 logged memory: GEOMETRY CLAMP ... memory RESET to the supported maximum on every start. Existing systems keep their setting. To silence that line on a DS10 system created earlier, edit its Emulatr.ini to read memorySize = 2147483648.

 

To import EMulatR.reg by hand. This is needed only for other Windows users of the same PC, or if setup was approved (UAC) with a different administrator account, in which case the session was created in that account's registry. Double-click EMulatR.reg in the installation folder and accept the Registry Editor prompt, or run this from a command prompt:

 

reg import "C:\Program Files\ASA-EmulatR\EMulatR.reg"

 

PuTTY reads a session only when it starts, so close any open EMulatR console window after importing. Because the file creates a named session and leaves Default Settings alone, it does not affect your other PuTTY sessions.

 

Log file names. The log file name contains p10023 for every system, because the session cannot know each system's port. The date and time keep the files apart, and each file is written in that system's profile folder.

 

If you imported the 3.0-1 file. The EMulatR.reg shipped in 3.0-1 wrote Auto (2) instead of Force off (1) into PuTTY's Default Settings, so it did not help. If you imported it, you may reset Local echo and Local line editing in Default Settings to Auto, which is PuTTY's default, or leave them as they are.

 

Upgrading from an earlier release

EMulatR no longer loads or saves snapshots. Every start is a cold boot. There is no automatic resume, no periodic save, no save on halt and no on-demand capture. The run log states this on every start: snapshots: disabled -- cold boot; no snapshot is loaded or saved.

 

Resuming a saved snapshot restored memory only. The guest's disks had moved on since the snapshot was taken, and on a DS10 the system disk came back offline (mount verification), so the login hung after the Username: prompt. Snapshot support was already deprecated.

 

The launcher's environment panel no longer lists the snapshot variables (EMULATR_AUTOSNAP, EMULATR_AUTOSNAP_KEEP, EMULATR_AUTOSNAP_PERIOD, EMULATR_NO_AUTOLOAD and EMULATR_SNAPSHOT_FILE). The command-line options --no-autoload and --autosnapshot are still accepted so that existing scripts keep working, but they no longer do anything. The option --snapshot-on-pc is ignored, and EMulatR prints a message saying so.

 

What to do:

 

•Profiles created under an earlier release can be used as they are; they cold-boot.

•The snapshots folder of such a profile is no longer used. You can delete it to reclaim disk space: each file is 2 GiB on a DS10, and a profile can hold tens of GB. The profile's disks folder is not affected, so your disk images stay as they are.

•If the previous session was not shut down from OpenVMS, check the system disk after the first boot (ANALYZE/DISK_STRUCTURE), as after any unclean stop.

 

Known limitations

•Open item, DS10 idle timing: IdleScan does not take effect on the DS10, because no matching idle site is recognized there, so the idle pacing barrier does not apply either. At idle the DS10 runs fast: guest time is not held to wall time (about 1.5 times ahead, a dilation of 0.67, at 50 MHz). The DS20 and ES40 measure 1.00. A general barrier for the DS10 is under review and is not part of this release.

•The supported speeds, 50, 60, 75, 85 and 100 MHz, are the speeds the CPU-speed tests covered; they are not claimed to be the speeds of the original machines.

•The CPU speed sets only the interval timer and the speed-ups that skip ahead to its ticks. Whatever the setting, the time-of-year clock still converts cycles to seconds at 1,000,000,000 cycles per second; and on the ES40, the processor speed EMulatR stores in the dual-port RAM still reads 500 MHz.

•A speed other than 50, 60, 75, 85 or 100 MHz has not been tested; Tuning EMulatR gives measured figures for those five.

•The Platform Editor keeps a manifest's cpu_speed_hz entry unchanged. It has no dedicated control: the default appears as a generic text field, and the shipped list cannot be edited.
