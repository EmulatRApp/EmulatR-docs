Storage Paths and the Block-Media Seam

Every guest disk and CD in EMulatR is reached through one narrow interface, the block-media seam. Replacing what sits behind that seam changes how storage behaves on the host without touching the emulated controllers or anything the guest can observe.

 

The seam

The interface is scsi::IBlockMedia (deviceLib/scsi/IBlockMedia.h). It exposes a medium as a block device: open and close, whether media is present, whether it is read-only, the block size (512 bytes for disks, 2048 for CDs), the block count, and read / write of a run of blocks. Every call returns a status; there are no exceptions.

 

Three device models consume it and nothing else:

•VirtualDiskDevice -- the SCSI disk behind the NCR 53C810 (dka).

•VirtualIsoDevice -- the CD-ROM, on SCSI or on the ATAPI channel.

•The ATA taskfile engine -- the IDE fixed disk and ATAPI device on the Cypress or ALi south bridge.

If the pool refuses a disk -- an image whose size is not a whole number of 4 KB pages, a volume whose sector size does not divide 4 KB, the dump file on the same volume, the pool failing to allocate -- the run log records an ERROR naming the disk and the reason, and that disk falls back to the direct engine. A comparison run is therefore never mislabelled: the log states which engine served every disk.

 

The direct engine: FileBlockMedia

FileBlockMedia (deviceLib/scsi/FileBlockMedia.h) opens the image as an ordinary buffered file stream and seeks, reads and writes in place on the thread that issued the request. Reads and writes pass through the Windows file cache, so recently used images are served from host memory. After each write the stream is flushed -- to the Windows cache, not to the device. A write the guest sees as complete can therefore be lost if the host itself loses power before Windows writes it back.

 

The pool engine: PooledBlockMedia and the backing store

PooledBlockMedia (deviceLib/scsi/PooledBlockMedia.h) is a thin adapter: each block request becomes a byte-range request on one pool disk, and pool status codes map to block-media status codes. The pool itself is described in The Buffer Pool.

 

Beneath the pool is a second seam, storage::IBackingStore (storageLib/BackingStore.h): the host side of one medium -- its size, its volume's sector sizes, its identity (volume serial number, file ID, size and last-write time), and whole-page reads and writes. The product implementation is Win32FileStore:

•Two handles per image. The write handle is opened first, with host buffering disabled and write-through on, sharing only read access -- so from the moment the pool attaches, no other process can open the image for writing. The read handle, also unbuffered, is opened second.

•Reads and writes are whole 4 KB pages from 4 KB-aligned buffers, and a run of contiguous pages is written as one host write.

•Neither handle uses the Windows cache, so the two can never disagree about the file's contents.

 

Tests use an in-memory backing store instead, which can fail, delay or hang any chosen host call on demand (see Storage Verification).

 

What the guest sees

Nothing different. Both engines finish a request before the instruction that issued it completes, so guest time does not advance while a request is in progress and the guest never observes one outstanding. The SCSI disk model currently reports its write cache as disabled on both engines.
