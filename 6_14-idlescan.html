6.14 IdleScan

The OpenVMS idle routine, on a multiprocessor platform, spends most of its instructions on a loop that finds the highest set bit of a CPU mask. IdleScan is the EMulatR feature that executes that loop in one step instead of one pass at a time. It saves host work, not guest time: the guest sees exactly what it would see if the loop had run literally. This page describes the loop, how IdleScan recognizes and collapses it, what it does and does not change, and the pacing barrier that keeps an idle guest from running ahead of the wall clock. For how guest time is kept, see 6.12 Guest Time. For how cycles are charged to instructions, see 6.11 Cycle Harness.

 

The loop

When no process is runnable, OpenVMS enters its idle routine, SCH$IDLE. On a platform whose SRM firmware reports more than one CPU slot, the routine finds the highest set bit of a 64-bit CPU mask with a loop that shifts the mask one place on every pass. The DS20 reports two CPU slots and the ES40 reports four. The number comes from the SRM firmware and is the same whatever number of CPUs is installed. The loop is:

 

body:

ADDQ Rx,Rx,Rx ;  Rx <<= 1

LDA Ry,1(Ry) ; Ry += 1 BR test

test:

BGE Rx, body ; top bit still clear -> again

 

With only CPU 0 present, the mask has a single low bit set, so the loop takes 63 passes. That is about 252 instructions and about 126 block boundaries of pure register work in every idle pass. Real hardware runs the same loop. The DS10 reports one CPU slot, so its firmware branches around the loop and IdleScan never applies to it.

 

How IdleScan collapses it

IdleScan computes the result of the loop directly. Entering the loop body with the mask in Rx equal to x0, it forms y, which is x0 shifted left by one place.

•If y is zero, the loop would never end, because zero stays zero. IdleScan refuses and the loop runs literally.

•Otherwise n is 1 if the top bit of y is set, and 1 plus the number of leading zero bits of y if it is not.

•The result is Rx equal to x0 shifted left by n places, Ry increased by n, and the program counter at the instruction after the BGE. The collapse retires 4n instructions: the BGE is taken n-1 times and not taken once.

 

IdleScan finds the loop by its shape, not by its address. It looks for a block of exactly those three instructions whose BR target holds a BGE on the same register, back to the head of the block, where Rx and Ry are different registers and neither is R31. The site is recorded when the block executor fills the block. Before every collapse the four instruction words are checked again against the decoded instruction cache, and the processor mode must match.

 

IdleScan refuses, and the loop runs literally, when the span of the collapse would cross the next interval-timer edge, the interrupt-sweep cadence, the interrupt injector or an autosave, or when the interrupt break word is set.

 

What it changes and what it does not

IdleScan is not a warp. It skips no guest time. Every instruction is charged and credited, and every register is left exactly as the loop would leave it. Retire counts, cycle counts, the V-1 figure and the full-boot hash are therefore unchanged. A DS20 boot to the milestone reached 4,566,980,744 retires and 21,883,889,462 cycles both with and without IdleScan. What IdleScan removes is host work: the host no longer executes about 250 instructions for each idle pass.

The pacing barrier

Because a collapse costs the host almost nothing, an idle guest with IdleScan ran ahead of real time. At 50 MHz on the DS20, the idle dilation (wall time divided by guest time) was 2.23 without IdleScan and 0.35 with IdleScan alone, which means the guest ran about 2.9 times ahead of the wall clock. The pacing barrier stops that. It paces idle guest time to wall time. It is a barrier, not a change to the model: no guest-visible quantity moves.

 

A stretch begins at the first collapse after more than 20 ms without one. It is anchored at the wall time and the cycle count of that collapse. At every collapse, EMulatR compares the guest time since the anchor (cycles divided by the CPU frequency) with the wall time since the anchor.

 

•If the guest is ahead by 2 ms or more, the host sleeps for the difference. On Windows the sleep uses a high-resolution waitable timer, so it is not rounded up to the 15.6 ms system tick.

•If the guest is behind, nothing happens. Busy work and boot are already behind wall time and are not touched. No sleep occurs during a boot.

 

A sleep changes no cycle and no retired instruction. Only the wall time between guest events moves, and the host stops using a core to spin in idle. With the barrier, the DS20 idle dilation at 50 MHz measured 1.01.

 

Control and accounting

IdleScan is on by default. Setting EMulatR_IDLESCAN=0 turns it off. The setting is the bisection switch and has no other purpose: use it to check whether a difference in behavior comes from IdleScan.

 

The pacing barrier runs only immediately after a successful collapse. With EMulatR_IDLESCAN=0 there are no collapses, so the barrier is off as well. A collapse that IdleScan refuses never paces either.

 

At exit EMulatR prints one line:

 

IDLESCAN: sites=<n> collapses=<n> credited=<retires> refused=<n> paced_sleeps=<n> paced_ms=<ms>

 

The fields are the number of recorded sites, the number of collapses, the retired instructions credited by them, the number of refusals, the number of pacing sleeps and the total time slept in milliseconds.

 

Status and open items

IdleScan and the pacing barrier ship in the 3.0 Experimental release (X3.0-2) and are on by default. EMulatR_IDLESCAN=0 turns them off.

 

The barrier lives at the IdleScan collapse, so a platform without the scan is not paced. The DS10 is the case: its idle measured about 1.5 times ahead of wall time, a dilation of 0.67, at 50 MHz. That comes purely from executed work: about 39.5 million instructions per second at 1.88 cycles each is 74.4 million cycles per second, against a CPU speed of 50 million. A general barrier, and an analysis of the uniprocessor and multiprocessor execution paths, are under review. Neither is settled. This is a known open item in 3.0-1 Beta: on the DS10, IdleScan does not take effect because no matching idle site is recognized, the pacing barrier does not apply, and the DS10 runs fast at idle, with guest time not held to wall time.
