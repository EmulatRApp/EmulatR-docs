Windows Registry Settings

Every key EmulatR persists is listed here. You should not normally need this topic -- every value below has a control in the launcher UI -- but it is the reference for auditing a machine, scripting a deployment, or recovering from a damaged configuration.

 

The product hive

All persistent launcher state lives in ONE per-user hive:

 

HKEY_CURRENT_USER\Software\eNVy Systems\EmulatR

 

Four design rules explain its shape:

 

•The product is EmulatR; the launcher and Platform Editor are SUBSYSTEMS of it. Each namespaces its keys with a prefix -- launch_ today, with platedit_ reserved. One regedit path shows the whole product, and subsystems can never collide.

•HKCU scope, never HKLM. No administrator rights are needed, and a kit install or uninstall -- which touches Program Files and the HKLM uninstall entries -- never removes it. Named systems survive every upgrade.

•Not keyed by version. Deliberate: an upgrade must never orphan the system catalog.

•The registry is the CATALOG, not the substance. It stores names, pointers and small per-system knobs. The substance of a system -- Emulatr.ini, the platform manifest copy, disks, firmware, logs -- lives in that system's profile directory on disk. If the hive is ever lost, Add Existing... re-registers any profile directory. Nothing load-bearing exists only in the registry.

 

Values are written through Qt QSettings in native format: strings land as REG_SZ, integers as REG_DWORD, booleans as REG_SZ holding "true" or "false", and list values as REG_MULTI_SZ. The only binary blob is the saved window geometry.

 

launch_systems -- one subkey per named system

Each system is a subkey launch_systems\<guid>\. The GUID is assigned at creation and is immutable: renames and run-directory moves never change it, so per-system settings can never be orphaned. Deleting a system in the launcher removes the entire subtree in one operation, because all per-system state keys off that GUID by design.

launch_paths -- operator override paths

All three are optional. When one is absent, discovery runs instead, in this order: explicit override, then the installed location C:\Program Files\eNVy Systems, Inc\ASA-EmulatR, then the newest development-tree build.

launch_run -- run behavior

shutdownTimeoutMs (REG_DWORD) sets how long Stop waits, after writing the EMULATR_STOP sentinel, before OFFERING escalation. The default is 10000 and the floor is 1000. The launcher never force-kills on its own.

 

Legacy hive migration

Launcher builds before 2026-08-14 used a private hive at HKEY_CURRENT_USER\Software\eNVy Systems\EmulatrLaunch. On startup the current launcher performs a ONE-TIME, READ-ONLY migration: if the product hive has no launch_systems group and the legacy hive has keys, every legacy key is copied into the product hive with the launch_ prefix -- systems\... becomes launch_systems\..., ui\... becomes launch_ui\..., and so on.

 

The legacy hive is left untouched and can be deleted by hand once you have confirmed the migration. The gate -- that the product hive must not already have launch_systems -- guarantees the migration can never overwrite real state.

Editing by hand

Prefer the launcher UI -- every key above has a control. Hand-editing the hive is safe while the launcher is NOT running; it reads the hive at startup and on selection changes, and concurrent instances are last-writer-wins. Two rules if you do edit by hand:

 

1.runDir must remain an absolute path to a directory holding an Emulatr.ini. Otherwise preflight flags the system Broken -- it is never silently dropped.

2.Do not invent keys outside your subsystem's prefix. Unknown keys are ignored today, but the prefix IS the collision contract between subsystems.
