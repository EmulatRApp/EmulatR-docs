Durability, Faults and Recovery

This topic describes what EMulatR promises about guest data on each engine, and what the pool does when the host's storage fails, hangs, or loses power.

Bounded waits

Every host call the pool makes has a time limit, hostCallTimeoutMs (15 seconds):

•A fill runs on the disk's read worker; the vCPU bounds its own wait for it.

•An MPW write runs on the writer thread; the watchdog thread times it.

A call that outlives the limit is abandoned, never cancelled. EMulatR does not resume the affected disk while an abandoned call is still pending (rule R-1), because the late call could land its data after newer writes. To make a late write harmless, the writer sends each write from its own staging copy, never from pool memory, and a fill's buffer stays with its frame until the fill returns.

 

Retry, then pause

A failed host write is retried with exponential backoff -- from 10 ms, doubling to at most 2 s -- for a total of 30 seconds (retryWindowMs), and every retry is logged. A hung call is not retried; it pauses at once. When retrying is exhausted, the pool pauses:

•the queue is kept in memory, in order;

•the machine is told through the pause callback before the writer is marked Paused;

•later writes and flushes wait; the guest sees no error.

The writer states are Running, Retrying, Paused and Aborted.

 

Why pause rather than fail the request: a device error returned to OpenVMS starts mount verification, and if that times out the device cannot be recovered short of a reboot. The mount-verification timer runs on guest time. Because no guest I/O is ever outstanding while the guest's CPUs run -- the vCPU waits inside the instruction, with guest time frozen -- a host stall of any wall-clock length never advances that timer. The time limits exist so the fault is detected and reported, not to protect the guest.

Abort (orderly)

Paused, and a dump file is configured

Writes the dump first -- refused if it cannot -- then discards the queue. Later writes fail.

Discard

Paused (last resort)

Logs the lost write range per disk, leaves a DISCARD marker in the dump file when it can, discards the queue.

 

If the pool closes while paused, it dumps the queue (event Stop) when a dump file is configured. Otherwise it logs that the queued writes are LOST.

 

The pool dump

The dump (storageLib/PoolDump.h) is the recovery record for a data-pool failure. It holds every modified page the host did not accept, so an acknowledged write is never silently lost.

•Location: pool_dump_path. The file is preallocated at start, so a full disk cannot prevent a dump. It must be on a volume that holds none of the writable images -- the failing volume cannot be trusted to receive its own recovery data -- and attach refuses otherwise.

•Layout: a header (magic EMRPDUMP, version, dump id, and the identity of each disk), then one entry per queued write in sequence order (a 64-byte record with disk, dump id, sequence number, page and checksum, followed by the 4 KB page), then a terminator.

•Terminator: written last, after the entries are flushed. It carries a SEALED marker, the event (writer fault, abort, stop, operator dump or discard), the failing disk, page, operation, cause and host error, the retry count and duration, the first, last and durable sequence numbers, the sequence numbers of calls still abandoned, and a checksum of the whole file. A dump without a valid terminator is torn and must not be trusted.

•Protection: every entry carries the dump id, so stale bytes from an earlier dump are never mistaken for part of this one. A pool whose dump file holds a pending dump refuses to start, so a recovery record is never overwritten.

 

Status in this release

•Implemented and tested in storageLib: bounded waits, retry, pause, resume, dump, orderly abort and discard, including the sealed dump and the refusal to start over a pending dump.

•Not yet wired in the emulator: the machine-wide pause and the operator commands for resume, abort and discard. Today a pause writes an ERROR to the run log. A disk with write_cache off then holds the vCPU (guest time frozen) until the writer recovers; an ordered disk keeps running until its queue fills.

•Planned: replaying a sealed dump into the images at the next start; a separate system-disk pool that reports a failure to the guest as a device error rather than pausing.
