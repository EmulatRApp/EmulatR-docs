Time-of-Year Clock (TOY)

The Time-of-Year clock is the machine's battery-backed real-time clock: an MC146818-compatible part in the Cypress CY82C693 southbridge, reached through I/O ports 0x70 (index) and 0x71 (data). It holds the date and time the console and the operating system read, plus 256 bytes of CMOS scratch the SRM uses for its own settings.

 

On real hardware this clock runs from a battery, so it keeps time while the machine is powered off. EmulatR has no battery, so where the time comes from is a choice - and that choice trades everyday usability against exact reproducibility. EMULATR_TOY_MODE makes it.

 

Time-source modes

Mode

Where the time comes from

Use it when

host

(default)

Seeded from the host wall clock when the machine starts, then advanced by the emulated cycle counter. The clock always reports itself valid.

Normal interactive use. A fresh installation boots with a correct clock and the guest does not ask you for the date.

fixed

A pure function of emulated cycles: epoch 2026-01-01 00:00:00 plus elapsed emulated seconds. The host clock is never read.

Any run whose output is compared byte-for-byte with another run - do-no-harm, differential and certification passes. Set it explicitly; never rely on a default for this.

unset

Dead battery. Register D reports VRT = 0, the clock fields read invalid and do not advance, until the guest writes the time through the MC146818 SET protocol. Answering the OpenVMS boot-time date prompt does NOT do that - see the note below.

Reproducing a machine whose battery has never been charged - the faithful lifecycle. Expect the guest to ask for the date on EVERY boot, not just the first.

 

EMULATR_TOY_MODE=fixed # deterministic clock, for a comparison run

EMULATR_TOY_MODE=unset # dead-battery lifecycle

 

In unset mode the date prompt does not go away. Answering it sets the time inside OpenVMS for that session, but nothing is written back to the emulated clock chip: the stored origin stays at the factory epoch and the validity bit stays clear, so the next boot honestly reports a dead battery and asks again. This has been confirmed across a clean shutdown - it is not a persistence failure, the store saves and reloads correctly. What is missing is the write itself. Whether OpenVMS is expected to write the chip from that prompt on real hardware is still being established; until it is, use host mode (the default) if you want the prompt to stop.

 

An unrecognised value is not fatal - the emulator says so and falls back to host:

ToyRtc: unknown EMULATR_TOY_MODE 'wallclock' -- using host

 

The default was unset in earlier builds and is host from 19 August 2026. Under the old default every fresh installation booted with an invalid clock, and because OpenVMS will not write a clock it does not trust, the boot-time date prompt returned on every cold boot. Host mode removes that. The reproducibility rule is unchanged: a run that must reproduce has to pin fixed itself rather than inherit whatever the default happens to be.

 

Why reproducibility cares

In unset and fixed modes the clock is never read from the host. Time advances as

elapsed_seconds = (cycles - origin_cycles) / cycles_per_second

from a deterministic origin, so two identical boots read byte-identical clock registers. host mode breaks that by construction - guest-visible time stops being a function of guest state - which is exactly why it is not valid for a run whose whole purpose is to reproduce.

 

Persistence

The 256-byte CMOS array and the time origin persist to nvram/<stem>_toy.bin, relative to the run directory, where <stem> is the base name of the firmware image - the same stem the log artifacts use, overridable with EMULATR_LOG_STEM. EMULATR_TOY_NVRAM overrides the whole path. The file is written on every CMOS store rather than at exit, so an abrupt kill loses nothing. It is read back at startup, and a store that is absent, short, corrupt, or written under a different mode is refused with one loud line, leaving the clock unset.

 

This is a different store from the SRM environment-variable flash image - see Firmware Images: .exe and .rom. The store is keyed by that same firmware stem, so every platform in a run directory keeps its own clock and CMOS: a DS20 run uses nvram/ds20_v7_3_toy.bin and a DS10 run its own file. Before 19 August 2026 the two shared one store, and a DS10 boot could consume the clock a DS20 boot had written.

 

A store left over from that shared scheme is ignored rather than migrated - there is no silent conversion - and the emulator says so once at startup:

 

Machine: legacy nvram/toy_cmos.bin present but IGNORED -- the TOY store is stem-keyed now (nvram/ds20_v7_3_toy.bin)

 

Initializing a clock that has never been set

This applies only to unset mode. It is the behaviour of real hardware after a battery replacement, not a defect.

 

OpenVMS gates its clock writes on the validity bit. While the hardware clock reports VRT = 0, answering the date prompt at boot sets the system time only - nothing reaches the chip, so the next boot asks again. Once the clock reports valid, VMS both reads it and maintains it; the first write after validity was observed setting the full date and time through the standard SET protocol.

 

The designed heal on real hardware is the console DATE command, which writes the clock with that same protocol. The v7.3 console images shipped for these platforms do not carry it, so in practice a dead store is initialized either by running once in host or fixed mode - the clock then reports valid and the guest writes it - or by initializing the store file directly. Either way it is a one-time step; afterwards the clock persists and the prompt does not come back.

If the date prompt PERSISTS across boots even in host mode - a store carried across mixed mode histories can hold a wedged validity latch - reset it: shut the guest down cleanly, delete the run directory's nvram/<stem>_toy.bin (for example nvram/ds20_v7_3_toy.bin), and boot twice. The first boot asks for the date once; answering it latches validity into the freshly created store. Shut down cleanly again, and the second and every later boot comes up with the correct time, unprompted. The clean shutdowns matter - they are what persist the store.
