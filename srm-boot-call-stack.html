SRM Boot Call-Stack

This appendix names the ordered path from power-up to the >>> prompt, and where each stage lives. Its practical use is localization: when a boot goes quiet, the last line the console printed identifies the stage it died in, and the stage identifies the file to open.

 

Where the console sources actually are

One scope correction saves most of the hunting. apisrm/ref is the platform and chip reference LEAF -- device drivers (dq_driver.c), PAL macros (ev6_huf_decom.m64), the definition files (ev6_defs.mar, osfalpha_defs.mar) and the IPR examine / deposit driver (ev6_ipr_driver.c). The boot-to-prompt SPINE -- the kernel executive, the secondary-start logic, and the shell that actually prints >>> -- lives in the shared apisrm source directories, not under ref/. A call stack confined to ref/ is therefore incomplete by construction. Source Cross Reference covers the tree layout.

 

The ordered path

The first three stages run before the console has a working output path, so they are invisible unless a trace is armed. Everything from the banner down is observable on the console.

The CSERVE seam

CSERVE is the call gate between the console and PALcode, and it is where most boot-path work actually lands. The console loads a function code into R16 and traps; EmulatR dispatches it in palBoxLib/grains/PalEntries.cpp. The architecture is run-the-guest-PAL: wherever possible a CSERVE call is routed into the guest's own handler rather than replicated in C++.

The START path is worth understanding before touching it. On a uniprocessor model there are no secondaries to start, which once made a no-op look harmless -- but the primary OS boot transfer runs through the same entry. It reaches sys__exit_console, which restores the boot context from the per-CPU HWRPB slot, flushes the ITB and DTB, and restarts fetch at the slot's halt PC. Stubbing it stranded the whole hand-off. The current default routes faithfully into the guest PAL; EMULATR_CSERVE_START_MODE selects guest (the default), cpp (a C++ replica, for testing) or off. Reset into Secondary Boot covers that hand-off in full.

 

Unimplemented CSERVE codes are a known divergence

A function code with no case falls to the dispatch default, which returns with R0 untouched. That is a DIVERGENCE from real execution, not a tolerated no-op: the guest sys__cserve would dispatch the same code to a handler with real side-effects.

 

The distinction was settled empirically. 0x65 MP_WORK_REQUEST disproved the earlier assumption that these were silicon-tolerated -- the console loops on it and re-initializes, because the guest handler never saves R18 into CNS__WORK_REQUEST. Codes still landing in the default arm include 0x0A, 0x0B-0x0D, 0x32-0x37, 0x45 JUMP_TO_ARC and 0x65 MP_WORK_REQUEST.

 

Set EMULATR_CSERVE_AUDIT=1 to capture the missing contract for each: the function code and its inputs, the caller PC, and whether the call is one-shot or a polling loop. That capture is what lets a code be closed against the corresponding guest handler in the apisrm source.

 

Localizing a stall

Read the last console line and map it to the table above. A boot that stops after a device-probe line and before any prompt is in enumeration; one that stops at UPD> is waiting in LFU, not hung. A boot that produces no output at all never reached the banner, which puts it in one of the three pre-console stages -- and there the only instrument is a trace, because the console cannot yet report on itself.

 

Two failure shapes look like hangs but are not. A long pause during self-decompression is the guest doing several million cycles of real work. And a memory geometry the machine cannot support does not fail -- it churns its memory configuration indefinitely, alive but never converging; see Platform Identity & Memory Geometry.
