Pre-decompressing the Firmware

An SRM firmware file such as es40_cl67srm.exe is compressed. Every cold boot, EMulatR loads it and the firmware's own start-up code decompresses the console on the emulated processor before anything else runs. That step is mandatory for a .exe: the console does not exist in memory until it has been unpacked.

The decompression can instead be done once, ahead of time, on the host. The result is a .rom that EMulatR boots with no decompression stage.

 

Why do it

•The console is proven before it runs. The tool is DEC's own decompression algorithm built as a native program; the image it writes does not depend on the emulated processor at all. From HP's cl67srmrom.exe it reproduces, byte for byte, the reference image EMulatR's loader was validated with.

•It takes the decompression out of the boot. With a .rom, the first instruction EMulatR executes is the console's own. If a .rom boots and the .exe does not, the fault is in the decompression path; if both fail the same way, it is not.

•It gives you the console to study. The .rom (or the raw image without --rom) is the console exactly as it sits in memory, ready for a disassembler.

 

What it does not gain today

Measured on 29 September 2026 (ES40, Release build, 4 GB, same settings): the .exe reached P00>>> in 695 seconds; the .rom, with the platform's badge profile copied beside it, in 684 -- the same, within run-to-run variation. Without any profiles beside it, the .rom took 920 seconds. The reasons it is not faster:

•The speed-up profile does not carry over. EMulatR keeps a speed-up profile beside each firmware file (es40_v7_3_warp.json) and checks it against that file. A .rom is a different file, so the .exe's profile is set aside as stale (WarpProfile: *** STALE ***) and the .rom starts without one. It builds its own over later runs.

•The decompression itself is short. It is a small part of the boot; most of the time to the prompt is the console's own initialization and memory test, which both files run.

•On the ES40 the .exe does not enter the console update (LFU) on a cold boot, so there is nothing to skip there either.

Until the profile is keyed to the console rather than the file, use the .rom for verification and diagnosis, and the .exe for everyday running.

 

Making the .rom

Use the tool in the tools folder of the installation: tools\host_firmware_decompressor.exe cl67srmrom.exe --rom firmware\es40_cl67srm.rom

It accepts HP's file as downloaded or the prepared es40_cl67srm.exe; both give the same result. See Firmware Images: .exe and .rom for the format.

 

Booting it

Name the image for what it is, for example es40_cl67srm.rom, and put it in the system's firmware folder beside the .exe. The system's identity comes from systemStem in its Emulatr.ini (the launcher sets it, systemStem = es40_v7_3 on an ES40), not from the file name, so:

•The system stem selects the platform: the ES40 manifest, es40_v7_3_platform.json, is used whether the .exe or the .rom is chosen.

•The flash (console settings) is still firmware/es40_v7_3.rom beside it, bound exactly as for the .exe. The image and the flash have different names, so they no longer collide, and no EMulatR_FLASH_ROM setting is needed.

 

In the launcher, select the .rom in the Firmware control. For a direct run:

EMulatR.exe --firmware firmware/es40_cl67srm.rom --system-stem es40_v7_3 --mem 4294967296

 

The badge profile (es40_v7_3_badge.json) is named for the system too, so the one already in the firmware folder applies. EMulatR refuses to use a console .rom as its own flash; if it would, it prints FlashRom: REFUSED. Never overwrite firmware/es40_v7_3.rom: it holds the console settings.
