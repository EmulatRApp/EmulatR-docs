6.11 Cycle Harness

EMulatR measures guest time in processor cycles. The cycle harness decides how many cycles each retired instruction adds to the cycle counter, and through it to the guest's clocks: the cycle counter the guest reads, the interval timer and the time-of-year clock.

 

Every retired instruction is charged the weight of its class. A block of instructions is charged the sum of what its instructions actually did; it has no separate cost. Every execution path (single step, interpreted block and the JIT) charges the same number of cycles for the same instructions, so the guest's clock does not depend on which path ran the code.

 

For each instruction, the cost is its class weight (never less than 1 cycle), plus 1 if it is a conditional branch that was taken, plus any event weight.

Outside the per-instruction charge

Some mechanisms advance the clock in one step instead of instruction by instruction. SpinSkip, which skips firmware countdown loops, charges the skipped passes times the loop's weight as a single amount. The warps that skip timed waits advance the clock to the next event. No cycle is charged twice.

The guest's CC_CTL register controls only the cycle counter the guest reads. Guest time itself always advances.

The cycle charge model

 

Under the cost model that has been ruled for the calibrated mode (Mode C2), every executed instruction is charged the processor cycles the 21264 hardware spends on it. The cycles charged for a stretch of execution are:

 

C = s * ( SUM_k w_k * n_k + T + M + SUM_m P_m * E_m )

 

The terms are:

 

•k is an instruction class from the cost table above and n_k is the number of class-k instructions executed.

•w_k is the class weight: the latency of the class in Table 2-4 of the 21264 Hardware Reference Manual, never less than 1 cycle. The weights are fixed. They are never tuned or fitted to run data.

•T is the taken-branch adder: 1 cycle for every conditional branch that was taken.

•M is the expected branch-mispredict cost, described under Branch prediction below.

•P_m and E_m are the penalty in cycles and the number of occurrences of each modelled pipeline event (see Event penalties below).

•s is the scale factor. It is a property of the compiled instruction grain: it is built in with the weights and there is no setting to change it at run time.

There is no tuning lever and no cost file. The charge is a property of the compiled image of EMulatR, so two runs of the same build always charge the same cycles for the same instructions. The configured CPU speed F is the only speed control. The default is 50 MHz and the supported speeds are 50, 60, 75, 85 and 100 MHz. Guest time is the cycles charged divided by the CPU speed:

 

guest time (seconds) = C / F

 

For example, 5,999,609,411 cycles at 50 MHz is 120.0 seconds of guest time.

 

Exact arithmetic. Weights are held as fixed-point numbers in units of 1/256 cycle (Q8), so a weight of 1.5 cycles is stored as 384. The product of the scale and a weight is an exact integer, and a sub-cycle accumulator carries the fractional remainder from one instruction to the next. Two instructions of weight 1.5, for example, charge 1 cycle and then 2 cycles, with the remainder of 0.5 carried between them, so the cycle count is always an exact, deterministic integer.

 

Collapsed loops. Loops that EMulatR skips in closed form (SpinSkip and the IdleScan collapse) are charged exactly what the literal loop would have been charged, through the same weights, including the expected mispredict term. Collapsed and literal execution therefore give identical cycle counts.

 

Why the cost shape is fixed

 

The weights are not learned from measurements of EMulatR running a guest, for two reasons.

 

Too many unknowns. Suppose the cost of each class were fitted from the wall time of runs. Each run gives one equation, where h_k is the host seconds per class-k instruction and other_r is the time that no instruction accounts for:

 

W_r ~= SUM_k ( h_k * n_kr ) + other_r

 

There are roughly 15 to 20 classes, so at least that many runs are needed, and they must have genuinely different instruction mixes. Stacking the runs as the rows of a matrix N (runs by classes), the per-class costs can be recovered only if N has full column rank, and recovered reliably only if it is well conditioned. The runs EMulatR has do not supply that:

 

•A boot from the SRM console to the OpenVMS Username prompt executes the same code every time, so its mix is nearly identical from run to run. Fifty boots are one equation repeated fifty times. The rank of N is therefore expected to be close to 1. (This is an expectation; the mix matrix has not been measured.)

•Classes move together. Loads, address arithmetic and conditional branches rise and fall as a block in almost any code. With strongly correlated columns the fit can trade cost between classes freely, for example loads at 4 cycles with ALU at 1, or loads at 3 with ALU at 1.4, and explain the totals equally well. The condition number of N is expected to be very high.

•Rare classes (FP divide, FP square root, MB, HW_MTPR) are a tiny fraction of the count. Noise in the large classes swamps them, and a fit can put almost any value on them.

 

A least-squares fit always returns numbers. They look plausible but are not stable: with one more boot or a different workload the per-class values change while the predicted total barely moves.

 

The wrong quantity. Even with perfect data, a fit to host wall time measures h_k, how long this host takes to emulate a class, and not what the Alpha spends on it:

If guest time followed the host costs, a guest that timed itself with RPCC would see the host's ratios: FP-heavy code would look fast and memory-heavy code slow, the reverse of real silicon in places. The guest's sense of its own performance would also change whenever EMulatR itself got faster. Keeping the Alpha's relative costs and applying one built-in scale preserves the silicon shape: the ratio of any charge to any other is always the HRM ratio.

Branch prediction

 

The EMulatR pipeline fetches no speculative path: every branch is effectively mispredicted as far as fetch is concerned, and nothing speculative is ever squashed. The 21264 does predict, and a mispredicted conditional branch costs 7 cycles, so EMulatR needs an estimate of how often the real processor would mispredict.

 

Observe mode. A two-bit predictor carried forward from earlier versions (cBoxLib/BranchPredictor.h: 512 sets of 2 ways, two-bit saturating counters, and a backward-taken guess for branches it has not seen) runs in passive observe mode, and only in the attribution (profiling) build. At each executed conditional branch it predicts, compares its prediction with the real outcome, counts the hit or miss and updates itself. It never changes fetch, the PC, the cycles or the retire count, so it cannot alter any guest result. Unconditional BR and BSR are always predicted correctly and are not observed. Branches skipped by a collapsed loop never execute and are not observed. The predictor is an approximation: the real 21264 uses a tournament predictor (local, global and choice predictors, HRM Figures 2-3 to 2-5), and a two-bit table usually mispredicts more, so the counts lean high.

 

Measured mispredict rates. On a DS20 boot to the end of OpenVMS startup the observer saw 388,185,559 conditional branches, of which 30,282,070 were mispredicted: 7.80%. At 7 cycles each that is 211,974,490 penalty cycles, about 1.0% of the cycles of the boot. The rate differs by opcode:

Expected-cost charging. The mispredict penalty is not charged by running a predictor. Each conditional-branch opcode carries an expected penalty equal to its observed mispredict rate times 7 cycles, folded into the weight that is compiled into its grain, and charged whenever that branch executes. For example a BEQ carries 0.0781 x 7 = 0.547 cycles. Nothing on the execution path predicts: the predictor stays in the attribution build, where it only refreshes the per-opcode rates.

 

M = SUM over conditional-branch opcodes b of ( n_b * rate_b * 7 )

 

Serial and out-of-order charging

 

The 21264 fetches in program order, issues up to four instructions per cycle and executes them out of order. The ruled table charges every instruction its full latency, as if each depended on the one before it. This serial model is conservative: it over-charges code made of independent instructions.

 

A more faithful model would split the charge into an issue cost (functional-unit throughput) and a dependency stall. A stall exists only where an instruction j reads a register that an earlier instruction i writes and issues within the latency of i:

 

stall = SUM over dependent pairs (i -> j) of max(0, latency(i) - distance(i, j))

 

The latency comes from Table 2-4 and the distance is the issue distance between the two instructions. Both are static for a block of instructions. This model is reserved for a future dedicated timing mode. It is not added on top of the serial table, because that would count latency twice.
