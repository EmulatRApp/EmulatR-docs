OpenVMS Crash or Hang: Capturing Diagnostics

When OpenVMS stops with a bugcheck, or hangs, the fastest route to a cause combines two views: the guest's own crash dump, analysed with SDA, and EMulatR's diagnostic settings, which show what the emulated hardware did. This page gives the sequence and the commands for both.

1. Keep the evidence from the start

•Keep the console output. PuTTY writes a session log in the run directory (putty_console_p<port>_<date>.log), and the run log in logs/ mirrors every console line.

•Note the build (the Alpha Emulator Console line in the banner), the platform, the firmware, the memory size and every EMulatR_* setting you launched with.

2. Arrange a crash dump before the problem happens

Boot conversationally and choose the dump style (the device is your system disk):

P00>>> b dka200 -flags 0,1

SYSBOOT> SET DUMPSTYLE 9

SYSBOOT> CONTINUE

DUMPSTYLE 9 writes a compressed selective dump (system space and key processes); 8 writes a compressed full dump. The dump file SYS$SYSTEM:SYSDUMP.DMP must be large enough for the style you choose.

3a. On a bugcheck

Copy the bugcheck block from the console: the bugcheck code and name, crash CPU, current process and image name. Wait for the dump to finish before stopping EMulatR. The console reports when the dump is complete.

3b. On a hang

1.Press Ctrl/P in the console to halt the CPU. The console prompt P00>>> appears.

2.Optional, but recommended: take an EMulatR snapshot first. It saves every register and all of memory without disturbing the run, so the state can be examined later. It needs EMulatR_CONSOLE_SNAPSHOT=1 at launch; at the halted prompt type set oem_string snapshot.

3.Type crash to force OpenVMS to write the dump. (If the hang is very early in boot, before OpenVMS has its exception handlers loaded, crash cannot work; use the EMulatR diagnostics in section 6 instead.)

4. Analyse on a copy, never on the live disk

Stop the emulator cleanly, then copy the whole storage folder, so the file names the platform manifest expects stay the same. Boot a second EMulatR instance from the copy, on its own environment and console port. Two emulators must never use the same disk files at once.

cp -rp "/d/EMulatR/vStorage/<set>/Alpha" "/d/EMulatR/vStorage/<set>-dump/Alpha"

Point the second instance at the copy with EMulatR_DISK_DIR and boot the copied system disk. A different platform model can be used for the analysis; a DS20 boots an ES40 system disk.

5. SDA commands

$ ANALYZE/CRASH SYS$SYSTEM:SYSDUMP.DMP

SDA> SHOW CRASH

SDA> SHOW STACK

SDA> EXAMINE/INSTRUCTION @PC-20;40

SDA> SHOW EXEC

SDA> SHOW PROCESS/REGISTERS

SDA> CLUE CRASH

Command

What it answers

SHOW CRASH

The exception type, the faulting PC and PS, and the signal array. This is the first thing to read.

EXAMINE/INSTRUCTION around the PC

The instruction that faulted. An unusual instruction class or an internal-register access points at the emulator.

SHOW EXEC

Maps the PC to the loaded executive image and offset.

SHOW STACK, SHOW PROCESS/REGISTERS

The call path and register state at the crash.

CLUE CRASH

A one-page summary suitable for a report.

6. EMulatR-side diagnostics

These settings need the RelWithDebInfo build (they are compiled out of Release). Set them in the environment before launch. Several of them keep the JIT off and slow the run, so compare them only with runs made the same way.

Setting

What it shows

EMulatR_HALT_DIAG=1

Every CPU halt, with its PC and halt code.

EMulatR_CSERVE_AUDIT=1

Each console-callback (CSERVE) function the guest calls that EMulatR does not implement yet.

EMulatR_DIAG_PAL=1

PAL-level events, including how the console hands control to the OpenVMS bootstrap.

EMulatR_PCTRACE=1, EMulatR_PCTRACE_N=<n>

A forward trace of up to n instructions from the console-to-bootstrap handoff.

EMulatR_UART_TRACE_MARKER=<text> with EMulatR_PC_GATE=<pc> and EMulatR_LOOKBACK=<n>

Arms when the console prints the text, then dumps the last n instructions once execution reaches the given PC. Useful for "what ran just before this?".

7. Work one change at a time

•Reproduce once with nothing changed. That is the baseline.

•Keep every condition the same between runs (build, memory size, disks, settings), and change one thing per run.

•Restore the disks from a saved copy before each run, so every run starts from the same state.

•Record each run: what changed, what the console printed, and where it stopped.

8. What to include in a report

•The console capture from the boot command to the stop, including the whole bugcheck block.

•The run log from logs/, and the build and settings noted in step 1.

•The SDA output from step 5, at least SHOW CRASH and CLUE CRASH.

•For a hang: where it stopped, how long you waited, and the snapshot file name if you took one.
