Source Cross Reference

Every claim EmulatR makes about the machine is meant to be traceable to something that is not EmulatR. This appendix says where those authorities live, and how the topics point at them.

 

The convention

Most engineering topics end in a Source References block naming the exact files behind the behavior they describe -- 47 topics carry one as of August 2026. To recount: grep -rlE '<para styleclass="Heading[23]">Source References' Topics/ | wc -l. That block is not decoration. When a topic, a test, and the code disagree, it is where the argument gets settled, because it names the thing that is allowed to decide.

The ordering matters most when a test fails. A test encodes an expectation, and an expectation can be wrong; a tier-1 source cannot be argued with. The rule is to let the source say which of the code and the test is mistaken, rather than adjusting whichever is easier to change.

 

Where the sources live

The reference library is Processor Support/. It is large, and scanning it is the wrong move: start at Processor Support/REFERENCE_INDEX.md, which lists every document with a one-line description and ends in a "what should I read for X?" lookup, then open only what that points at.

 

The SRM console sources sit at Processor Support/PalcodeBitsavers/apisrm/apisrm/. One scope correction saves a great deal of hunting: ref/ is the platform and chip reference LEAF, not the console's spine. It holds the device drivers (dq_driver.c, n810_driver.c), the PAL macros (ev6_huf_decom.m64), the definition files (ev6_defs.mar, osfalpha_defs.mar) and the IPR examine / deposit driver (ev6_ipr_driver.c). The boot-to-prompt spine -- the kernel executive and the secondary-start logic -- is elsewhere in the tree; Hierarchy.txt maps it.
