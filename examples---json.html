<firmware>_warp.json -- Calibrated-Delay Census

<firmware>_warp.json is the calibrated-delay census: a run product, stem-keyed beside the firmware image it was measured against. It records every delay loop the RSCC anchor collapses, plus the spin candidates the block executor finds, and it accumulates: each boot of the same image loads it, adds what that run observed, and rewrites it at clean exit. Since 2026-09-19 the file is also read back. A caller the RSCC anchor has already recorded confirms its warp after 8 tight re-reads instead of the full spin depth, so most of the discovery tax is paid once. A block loop that a human has audited (audited) is warped at a work-paced rate: at most one timer tick per 12000 executed instructions, which keeps an idle guest near real time and every run reproducible. No block loop has been audited yet, so no tick-step warp is armed by default. The census is always on and has no configuration knob (architect ruling D-2). One bisection switch exists so the warp can be A/B tested in two runs rather than two builds: EMULATR_UDELAYWARP=0 turns the warp off, while the census is still loaded and saved. The platform manifest key warp_spin_depth sets how many consecutive tight RSCC re-reads confirm a spin. See JRN-V2-WARPPROF-001 and the run-products discussion in Block-MAX-Internals.

The file is content-bound to the exact firmware image: firmware_bytes and firmware_fnv64 together are the binding key. A consumer that computes a different FNV-1a hash for the firmware it is about to run must treat the file as stale -- refuse it loudly and regenerate at clean exit, never consume it silently. The stale file is not overwritten: it is renamed to <firmware>_warp.stale-<fnv64>.json, keeping any hand-set flags. A read-only file is used but never rewritten, which is how to run timing twins from the same census.

 

Like the flash NVRAM, this file never ships and is never copied between machines. A fresh install generates its own on first boot.

 

Top-level fields

Field

Type

Meaning

version

integer

File format version. Current value 2 (since 2026-09-19). Version 1 files still load, with every site enabled and none audited.

comment

string

Human-readable description embedded in the file itself: what the census is, what src bits 0 and 1 mean, and the staleness rule. Authoritative -- read it before this table if the two disagree.

firmware_bytes

integer

Size in bytes of the firmware image this census is bound to. Half of the content-binding key.

firmware_fnv64

string

FNV-1a 64-bit hash of the firmware image, as a lowercase hex string with no 0x prefix. The other half of the content-binding key.

collisions

integer

Hash-slot conflicts in the census table that caused data to be dropped. The census stores sites in a direct-mapped table — slot = (pc >> 2) & (kSlots-1), kSlots = 32768 (raised from 512 to 2048 on 2026-08-26 and to 32768 on 2026-08-27) — and by explicit architect ruling (D-3), a lookup is never a search: one shift, one mask, one compare. So when two different caller PCs hash to the same slot, the second site is not recorded anywhere — the slot keeps its first occupant, and collisions increments instead. It increments on every dropped EVENT (each encounter of a PC whose slot another PC owns), not once per lost site, so the value says that sites were lost but not how many. It describes the most recent run's table only: it is not restored from the file on load.

 

collisions = 0 — the most recent run lost nothing: every distinct delay site it encountered is in the file.

nonzero — the census silently lost at least one site, and the correct response is enlarging kSlots (a rebuild), never adding probing — the counter exists precisely so an undersized table announces itself rather than degrading into a scan.

sites

array of objects

One entry per PC identified as a delay loop or spin candidate during discovery. See Site record fields below.

total_warps

integer

Count of delay-loop warps performed, accumulated across every clean run of this image. It is counted BEFORE the slot lookup, so it includes warps at sites lost to a collision: when collisions is nonzero it exceeds the sum of hits across the is_warpable sites.

total_skipped

integer (64-bit)

Emulated cycles collapsed by the anchor warp, accumulated across every clean run of this image. Like total_warps it includes collided events, so it can exceed the sum of cycles_skipped across the sites. Exceeds 32 bits on any real firmware.

 

Site record fields

Each entry in sites describes one program-counter address the census discovered:

 

Field

Type

Meaning

pc

string

Address that names the site, as a lowercase hex string with no 0x prefix (e.g. 6ab34). For an RSCC-anchor site (src bit0) it is R26 at the warp -- the delay routine's return address into its caller, which names the delay site -- not an address inside the loop or inside PALcode. For a block-level candidate (src bit1) it is the head PC of the repeating block.

src

integer (bitmask)

How this site was found. See The src field below.

is_warpable

boolean

RSCC-anchor evidence: the anchor's spin test confirmed a pure busy-wait for this caller. It licenses the anchor warp for that caller and nothing else. In particular it never arms a block site; only audited does. (An earlier tick-step experiment could leave it set on a block site, so it must not be read as an audit.)

audited

boolean

A human audit of a block site's loop: loads, compares and branches only, waiting on time rather than on a device. It is the only thing that arms a tick-step warp. The emulator never sets it, and saving preserves it. Absent (version 1 files) means false.

enabled

boolean

Architect policy. false keeps recording the site but never warps it. The emulator never changes it: loading restores it, saving writes it back, and a new site gets true. A disabled anchor caller is still counted in hits.

pal_mode

boolean

True when the site was caught by the RSCC anchor, which fires at the PAL-mode CALL_PAL RSCC entry; false for block-level candidates, which the block executor only ever sees outside PAL mode. It does NOT say that pc lies in PALcode: most anchor sites are ordinary console or OS return addresses (a DS20 OpenVMS census holds many like ffffffff801e010c), and only a few have PC bit 0 set. Because both fields are set by the same detector, it tracks is_warpable exactly.

hits

integer

Number of times this site was encountered, accumulated across every clean run of this image.

max_consec

integer

Longest run of consecutive iterations observed in one spin episode at this site: consecutive re-entries of the same block head, recorded once a run reaches kSpinThreshold (64). A loop whose body spans more than one block resets the count at every block change, so the detector sees it weakly or not at all. Always 0 for RSCC-anchor (warped) sites; meaningful only for block-level spin candidates, where it is the spin detector's diagnostic signal (BlockExecutor::noteSpin / traceLib::WarpProfile -- see Block-MAX-Internals).

end_pc

string

Block sites: the loop's back-edge, the branch that closes each pass, so the loop spans pc to end_pc. Lowercase hex, no 0x. 0 means not measured (anchor sites, version 1 records, or a loop with no PC-relative back-edge).

period

integer

Block sites: block entries per pass. 1 is a loop inside one block; 2 to 7 is a loop spanning several blocks, keyed on the block its back-edge returns to, never on a shared routine it calls. 0 means not measured.

cycles_skipped

integer (64-bit)

Emulated cycles this site's warp collapsed. Zero for a block site unless it is audited, enabled and armed.

first_cycle

integer (64-bit)

Emulated cycle count at the first encounter, as recorded by the run that first saw the site.

last_cycle

integer (64-bit)

Emulated cycle count at the most recent encounter, in the most recent run that saw the site. The two values can come from different runs, whose cycle counters each start at zero, so last_cycle can be smaller than first_cycle.

 

The src field

Per the file's own comment field, src is a bitmask:

 

Bit

Meaning

Observed src value

bit0 (0x1)

Seen by the RSCC anchor and warped.

src = 1

bit1 (0x2)

Block-level spin site: recorded with its extent, warped only after a human audit (audited).

src = 2

Every sample entry shows src as exactly 1 or 2, never both bits set. The comment describes the two as independent bits, so a future entry with src = 3 (a site found by both detectors) cannot be ruled out by this schema alone.

 

Worked example

The highest-impact site in a typical census is an RSCC-anchor site -- a calibrated delay routine whose RSCC re-reads the anchor collapses -- for example:

 

{

 "pc": "6ab34",

 "src": 1,

 "is_warpable": true,

 "pal_mode": true,

 "hits": 99458,

 "cycles_skipped": 51522740539,

 "max_consec": 0,        

 "first_cycle": 1573916471,

 "last_cycle": 57220797888

}

 

Read as: a delay routine returning to 6ab34 in the SRM console was warped 99,458 times, and the RSCC anchor collapsed roughly 51.5 billion emulated cycles it would otherwise have spent spinning through that loop. The counts are cumulative over every clean run of this image, and the two cycle values need not come from the same run.

 

By contrast, a block-level spin candidate is discovery-only and contributes nothing to total_skipped:

 

{

 "pc": "1b7924",

 "src": 2,"is_warpable": false,

 "pal_mode": false,"hits": 458,

 "cycles_skipped": 0,

 "max_consec": 432795,

 "first_cycle": 1240000912,

 "last_cycle": 52674310402

}

 

Read as: guest code at PC 1b7924 was flagged as a spin candidate -- one episode ran 432,795 consecutive iterations -- but a block site is warped only after a human audit sets audited, so no cycles were skipped there.
