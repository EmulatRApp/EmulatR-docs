V1.6 (Beta)

EmulatR brings the real DEC/Compaq/HP Alpha SRM console firmware to life on emulated Tsunami/Typhoon-class hardware. Each release records what landed, what was fixed, and the current known limitations. Entries are newest first.

 

How EmulatR is delivered today: as a single Windows installer, EmulatR_V<version>-setup.exe, which lays down a complete ready-to-run installation - see Installing with the Windows Installer. Firmware is never included: SRM images are licensed, so you supply your own. Older entries below describe the packaging of THEIR release (v1.4.4 and earlier shipped as build-variant zips) and are kept as the record of what was delivered then, not as current instructions - the same applies to their known-limitation lists. In particular, entries up to v1.6 say OpenVMS stops short of a login prompt; that is no longer the case - the DS20 now boots OpenVMS Alpha V8.3 through to the DCL login prompt.

 

X1.6-15 (Beta) — 2026-08-19

The headline is that a cold boot now reaches the OpenVMS Username: prompt without a human at the console: the firmware-update prompts answer themselves, the clock is valid on a fresh install, and the multi-minute post-banner stall is gone. The version minor is now derived from the source tree (v6 gives 1.6), so the kit names the hive it came from.

 

Added

•LFU auto-response. The console matches the update image's two prompts on its own output and answers them as an operator would (<CR>, then exit), printing one LFU-AUTORESPOND: line per injection so the log always says why the machine appeared to type. Capped at six injections, after which the console is handed back. EMULATR_LFU_INTERACTIVE=1 opts out entirely.

•Console input pacing. Input is delivered at a serial-plausible rate (EMULATR_CONSOLE_PACE_CPS, default 9600; 0 = legacy unpaced). Multi-line pastes into TPU or EVE no longer truncate with Data Overrun. Paced by guest cycles, so determinism is unaffected.

•BYTECHECK certification facility. A standing shadow checker that validates every bitwise and byte-operate retire against a reference, with fault-injection self-test and a one-shot listing window on first divergence. Diagnostic builds only.

•USER0 volume on the shipped DS20 manifest.

 

Changed

•EMULATR_TOY_MODE now defaults to host (was unset). The dead-battery default meant every fresh install booted with a clock VMS refuses to write, so the boot date prompt returned on every cold boot. Gate, differential and certification runs MUST still pin fixed explicitly rather than inherit a default; the faithful lifecycle remains one variable away (unset).

•Shipped platform manifests are tailored at ship time. Every storage row's media field is emptied except dka0.vdisk. The rows stay as documentation of the available slots; an empty-media row does not enumerate, so a fresh install boots dka0 only and no shipped manifest points at a path that existed only on the build machine.

•SCSI fault reports carry identity - id, LUN and CDB are included, so a fault names the device and command instead of only the condition.

 

Fixed

•READ LONG / WRITE LONG and ILI sense. The roughly six-minute post-banner stall on every boot is gone; startup no longer appears to hang for minutes after the banner.

•Installer staging is hive-aware. The launcher payload is resolved from its real location, so staging no longer fails its own precondition on a release build.

 

Known limitations (what to expect in this beta)

•>>> init reset-boot is unverified. Do not rely on it; see gap G-31.

•Guest SHUTDOWN ... POWER_OFF does not stop the emulator. Shut the guest down, then use the stop sentinel; see gap G-32.

•Tru64 is untried. The OpenVMS path is the one exercised.

 

v1.6 (Beta) — 2026-08-01

Two firsts this cycle: EmulatR produces a guest crash dump on disk, and the reason OpenVMS stops short of the login prompt is now identified rather than merely observed. The operator crash path, which previously stopped after the register dump, now runs to completion and writes a dump that the OpenVMS System Dump Analyzer reads. That dump is what located the remaining boot blocker.

 

Highlights this cycle

•Crash dumps reach the disk. The sequence now runs from Ctrl/P through the bugcheck banner, the register dump and the loaded-image table to a written dump — Memory dump complete, 28809 blocks used of 167418 blocks in dump file. The dump loads cleanly in SDA, which makes guest-side post-mortem analysis a working tool rather than a goal.

•Execution accelerations removed for fidelity. The delay-loop and idle-spin "warp" levers are gone from the execution path. They advanced the guest clock, and one of them wrote a guest register directly to force a countdown loop to exit. Runs are now cycle-honest end to end: the cycle accounting reports warp_cyc=0 with MHz_real == MHz_eff, meaning every cycle was executed and none fabricated. Boot is slower as a result. That is the intended trade.

•An undocumented processor register no longer faults. The SRM writes an EV6 internal register absent from the published 21264 register table. EmulatR raised an illegal-instruction fault on it, which aborted part of firmware reset initialization and sent secondary boot back into console startup. Accepting the write is required to boot a guest operating system — see Conditions.

 

Conditions — what this result requires

The crash-dump result was produced under the configuration below; departing from it will not reproduce the result. One row has since been overtaken by a change - see EMULATR_2D_NOOP below.

Setting

Value and why

Platform

DS20, firmware ds20_v7_3.exe, guest media dka0, OpenVMS Alpha V8.3.

Launcher

tools/run_ds20_bplus.sh — it carries the secondary-boot stack. The plain console launcher tools/run_ds20_putty.sh does not, and falls back into console initialization instead of entering the bootstrap.

EMULATR_2D_NOOP

No longer needed, and no longer read. This result was recorded on 1 August 2026; the gate was removed the following day and the faithful behaviour is now unconditional, so a leftover export of the variable has no effect. run_ds20_bplus.sh still sets it harmlessly. Nothing needs to be done to reproduce this row.

SRM STARTUP_P1

Left blank, i.e. a full startup. A minimum startup may not bring up enough of the system to reach SYS$SYSTEM:SYSDUMP.DMP, and a dump can then fail quietly.

SRM DUMPSTYLE

11 (selective + full console output + compressed). Selective preserves system space and the current process; the console-output bit puts the crash-time registers and stacks in the console log where they are readable without opening the dump.

Console

PuTTY over the TCP console port. Use a port no other instance holds — a bind collision suppresses the PuTTY auto-launch silently.

 

Boot command variants

All three forms are accepted. The console echoes the normalized form it will act on.

Command

Effect

b dka0

Normal boot. Runs into the operating system without stopping.

b -fl 0,1 dka0

Conversational boot. Stops at SYSBOOT> so system parameters can be set before the OS starts. This is the form used to set DUMPSTYLE above.

b dka0 -flags 0,1

Equivalent long form. The console echoes (boot dka0.0.0.8.0 -flags 0,1) for either spelling.

 

The crash sequence, end to end

This uses the firmware's own controlp machinery. There are no emulator hooks in the path.

1.At SYSBOOT>, set dumpstyle 11, then c to continue.

2.With OpenVMS running, press Ctrl/P. The console reports halted CPU 0, halt code = 1, operator initiated halt.

3.At P00>>>, type crash. The console reports CPU 0 restarting.

4.OpenVMS prints the BUGCHECK banner with code 0000064C: OPERCRASH, the register dump, the stack and the loaded-image table.

5.The dump is written to the system disk, then analysed with ANALYZE/CRASH_DUMP SYS$SYSTEM:SYSDUMP.DMP.

 

Restored: the dump now reaches the disk

Everything from Accessing system disk onward is new in this release. The previous cycle stopped after the register dump with no banner and no dump file.

Storage: why OpenVMS stops short of the login prompt

This limitation is unchanged in effect but is no longer unexplained. The crash dump identified it precisely, and the finding is recorded here because it is the single blocker between the current release and an interactive guest.

OpenVMS boots into the executive and prints its banner. The swapper then waits for the system disk to be marked valid, and that never happens. The chain, measured rather than inferred:

1.The SCSI driver issues an INQUIRY asking for up to 255 bytes. The disk answers with the standard 36.

2.On real hardware the target then changes bus phase, the adapter detects the mismatch, records the unsent byte count and raises an interrupt. EmulatR instead padded the transfer with zeroes and reported it complete, so no interrupt was ever raised.

3.The port driver waits on that interrupt to finish initialization, so the SCSI port never comes online and reports zero completed operations.

4.The disk behind it therefore never leaves initialization and never reports a device type, so it is never marked valid.

5.The swapper's wait for that valid flag never ends. Because no timeout routine is registered on either device, nothing recovers it.

The phase-mismatch behaviour has been implemented against DEC's own NCR 810 register definitions and the SRM's own driver for the same chip. Verification is in progress and this release does not yet claim the guest reaches a login prompt. Note that the adapter identity itself is correct: OpenVMS classifies the emulated controller exactly as it classifies the real part.

 

Known limitations (what to expect in this beta)

•OpenVMS does not yet reach the login prompt. Cause identified — see Storage above.

•The cause of the restored dump path is not yet isolated. Three things changed together this cycle: the accelerations were removed, DUMPSTYLE moved, and the startup went from minimum to full. Any of the three could carry the result. Recorded as an observed result, not an explained one.

•Boot is slower than the previous release. Deliberate. Firmware settling delays and idle spins now run at their real cost. Cold boot to P00>>> runs at roughly 3.7 to 4.1 million emulated cycles per second on the reference host, and a full crash dump takes several minutes to write.

•Guest clock date. The guest boot time and dump timestamps do not track the host clock. The TOY/RTC date path is a known open item, and because driver timeouts are driven from that clock it may also be why a stalled device is never recovered.

•Single-CPU only. Unchanged from the previous release.

 

v1.5 (Beta) — 2026-07-29

Breakthrough: OpenVMS makes it off the firmware and into the operating system. OpenVMS Alpha V8.3 now boots from dka0 past SYSBOOT into the executive — banner, exec init, and a running scheduler — on DS20. Two CPU-faithfulness defects that each ended the boot in an INVEXCEPTN bugcheck were root-caused with the full oracle loop (EmulatR crash dump, SDA analysis, Alpha Architecture Manual confirmation, fix, in-boot verification) and eliminated. The previous release reached the SRM >>> prompt only; this cycle the guest OS runs.

 

Highlights this cycle

•OpenVMS boots into the executive. The boot now runs an order of magnitude past both former crash sites with a live scheduler, currently progressing through early system initialization.

•The crash-dump workflow is a proven tool. Operator halt (Ctrl/P) from a running OS to >>>, conversational boot (b -flags 0,1 to SYSBOOT>), and the halt / crash / dump / SDA loop all work against EmulatR guests — the firmware's own controlp machinery, no emulator hooks needed.

•The TOY clock behaves like real hardware. Dead-battery lifecycle, guest SET TIME honored, and the CMOS persists across runs (see Added below).

 

Fixed

•Stale firmware bytes in the instruction stream. The SRM loader's instruction-fetch override served frozen firmware-image bytes for any fetch in the firmware load range for the life of the run; once OpenVMS loaded executive code into that physical range, the CPU executed stale firmware content while data reads saw real memory (INVEXCEPTN, garbage instruction stream). The override now retires at the decompressor hand-off — the only era it legitimately models — verified at the bus level.

•Loads to R31/F31 could fault. Per the Alpha architecture, a load whose destination is R31/F31 is a prefetch and never signals an exception (LDQ_U R31 is the canonical UNOP). EmulatR executed them as real accesses, and SWAPPER's scheduler epilogue padding — LDQ_U R31,(SP) at a stack boundary — took an architecturally impossible ACCVIO. Such loads now perform no memory access and raise no fault.

 

Added

•TOY/RTC time-source modes via EMULATR_TOY_MODE: unset (default) is the faithful dead-battery lifecycle — the clock reads invalid until the guest sets the time, then stays set; fixed is a pure function of guest cycles (required for differential/oracle gate runs); host seeds from the host wall clock (best usability, breaks bit-reproducibility).

•Guest SET TIME honored and persisted. The MC146818 SET-protocol write is decoded and latched as the new time origin (previously it was silently discarded), and the full CMOS — clock plus the NVRAM bytes the console really uses — persists to nvram/toy_cmos.bin in the run directory (EMULATR_TOY_NVRAM overrides). Corrupt or mode-mismatched stores are refused loudly.

•21 new unit tests covering the instruction-stream regressions and the full TOY lifecycle (write protocol, persistence round-trip, corrupt store, gate rule).

 

Known limitations (what to expect in this beta)

•OpenVMS does not yet reach the login prompt. After the banner the guest idles between bootstrap-driver disk reads; whether this is emulation pacing or a wait condition is the active investigation. The boot-time clock also logs 17-NOV-1858 (VMS time-zero), implicating the OS-side RTC access path — both are next-cycle leads.

•Single-CPU only. The HWRPB correctly advertises the second DS20 CPU slot as empty (verified live); SMP execution remains future work.

 

Operator note — the LFU prompts during init

•LFU>> update srm. The running console is V7.3-2 (Feb 27 2007) — the same ds20_v7_3.exe image EmulatR loads  fresh on every launch. There's nothing newer to update to, and the loaded firmware always comes from that file, not from what an update would write. For now: LFU>exit

oThe LFU write path is untested territory in EmulatR. An update attempt exercises the firmware-update utility's flash-programming sequence against the emulated TIG flash, whose backing file (ds20_v7_3.rom beside the firmware) is where SRM environment variables live —

oauto_action, boot_osflags, controlp, the wwid entries, everything you saw in show *. A partial or misbehaving update could corrupt that store, and then every subsequent boot inherits scrambled env state.

o The LFU prompts you see during init are noise, not a request. This firmware auto-enters the LFU during startup (sometimes twice, per the run-emulatr gotchas — "Option firmware files were not found on CD or floppy..."). The correct response is to  exit/decline back to P00>>> — the scripted console driver does exactly that. It's asking whether you want to load option firmware, not telling you an update is needed. If the prompt in front of you is the LFU asking for a device, just get back to P00>>> and proceed with the boot.

 

 

v1.4.4 (Beta) — 2026-07-23

This beta reaches the SRM >>> prompt on DS10, DS20, and ES40. Guest-operating-system boot is not yet available (see Known limitations below).

 

Highlights this cycle

•A second classic Alpha comes to life. The DS20 now cold-boots to the SRM >>> prompt and badges correctly as AlphaServer DS20 — joining DS10, with ES40 (Clipper) bring-up also reaching the console.

•Platform manifest system. Each model's device tree is described by a runtime-loaded <firmware>_platform.json, editable through the Platform Editor desktop application (editors/platedit_qt) with live validation and format-preserving save.

•Deterministic execution substrate + fast resume. A multi-agent scheduler (agent + dispatcher, Sequential==Threaded verified) and Level-1 snapshots (auto-save / autoload-newest, plus an entry snapshot that skips the firmware decompressor).

•New device models. Floppy FDC, keyboard + VGA console, and IDE/ATAPI storage (Cypress func1 on DS10/DS20; ALi M5229 on ES40) over a common block-media seam.

•Cross-platform. macOS/Linux build hardening alongside the Windows build.

•Packaging & docs. Versioned redistributable packaging, the full user guide shipped inside the package, and this release-notes track.

 

Fixed

•DS20 model badging — root-caused to an IIC completion-interrupt gap and fixed; the console now reports the correct system identity.

•ES40 memtest ACV — resolved (an AAR ASIZ decode-width mismatch); a spurious CSERVE 0x66 get_time behavior was identified as a regression and removed (the 0x66 no-op is the faithful behavior).

•ES40 console — SCB base-mismatch halt fixed and the COM2 console backend landed.

•MMU / TLB — the DTB/ITB are now modeled as truly 128-entry fully-associative, fixing a conflict-eviction thrash.

•Memory — a page-crossing store overrun in the sparse pager was fixed.

•Build portability — added the explicit <new> / <cstdlib> includes that the Release configuration and the clang (macOS) build require.

 

Known limitations (what to expect in this beta)

•No guest OS boot yet. The SRM-to-OS hand-off at VA 0x20000000 is the active frontier: the VMB loads and builds the HWRPB/page tables but the transfer to the OS entry does not yet fire.

•OpenVMS/Tru64 install is gated on floating point. The FP unit is an IEEE-T proof-of-concept; VAX G/F float (which VMS relies on) is not yet implemented.

•PCI enumeration. The on-board devices are now walked and enumerated - that is how the 53C810 SCSI adapter is found and bound, and it is what carries the boot as far as the OpenVMS startup banner. That path now carries OpenVMS through a full startup to the login prompt.

•No Ethernet yet. The on-board DE500 / 21143 ("Tulip") NIC is designed but not implemented.

•Single-CPU only. SMP is scaffolded but boots run cpuCount=1 deliberately.

•DS25 / ES45 (Titan chipset) are experimental — model-only, not yet booting.

•Cosmetic mismatches. The clock-MHz banner and a handful of SRM defaults differ from real hardware.

 

Beta test focus

We would most value reports on:

•Cold-boot to >>> on DS10 / DS20 / ES40 (via run_fw.sh or the run_* helper scripts).

•Console over PuTTY/plink on TCP 10023 — show config, show device, show memory, environment variables.

•Storage — attaching a virtual disk / CD-ROM and show dev enumeration.

•The Platform Editor — opening and editing a <model>_platform.json.

Because EmulatR treats itself as the primary correctness oracle, anything that diverges from real-hardware behavior is worth reporting.

 

Getting started (as shipped for v1.4.4)

Two build variants are provided: EmulatR_v1.4.4_relwithdebinfo.zip (diagnostic logging and trace facilities compiled in — preferred for beta, since it lets you capture the logs/traces that make a bug report actionable) and EmulatR_v1.4.4_release.zip (optimized, diagnostics compiled out; for performance and clean runs).

Firmware is not included — DEC/Compaq/HP SRM images are licensed, so supply your own <model>_v7_3.exe in ./firmware/. Full documentation ships in documentation/EmulatRGuide.pdf.

 

Reporting issues

Please include the model, the build variant, the run command, and — on a RelWithDebInfo build — the run log and any .trc from logs/ and traces/.
