Debugging OpenVMS with XDELTA

XDELTA is the OpenVMS kernel debugger. It uses the same commands as DELTA, the process-level debugger, but it is entered directly from the hardware exception vectors, so it can debug system code in any processor mode and at any IPL. It must be loaded when the system boots, and it stays in memory until the system is rebooted without it (VSI OpenVMS DELTA/XDELTA Debugger manual, section 1.1).

Everything below is the Alpha form, as the manual gives it. XDELTA talks to the console terminal only, which under EMulatR is the telnet console (PuTTY). Keep the console connected for the whole session.

Booting with XDELTA

Give the boot flags as the second value of -flags (manual, section 1.7):

P00>>> boot dka200 -flags 0,6

Flags

Meaning (manual, Table 1.1)

0

Normal, nonstop boot (the default)

1

Stop in SYSBOOT

2

Include XDELTA, but do not take the initial breakpoint

3

Stop in SYSBOOT, include XDELTA, but do not take the initial breakpoint

6

Include XDELTA, and take the initial breakpoint

7

Include XDELTA, stop in SYSBOOT, and take the initial breakpoint at system initialization

Use your own boot device: dka200 on the ES40, dka0 on the DS10 and DS20. On Alpha the flags value is passed unchanged to the primary bootstrap. With 6 or 7, XDELTA stops at the initial breakpoint, where you can set breakpoints or examine memory before the system starts (manual, sections 1.7 and 1.8). Alpha takes two initial breakpoints; the first reports:

BRK 0 at address

Type ;P and Return to continue.

Entering XDELTA on a running system

XDELTA must have been loaded at boot (flags 2, 3, 6 or 7). Then (manual, section 1.8.2):

•Press Ctrl/P at the console. The processor halts and the console prompt appears.

•Request a software interrupt at IPL 14: P00>>> deposit sirr e

•Continue: P00>>> continue

XDELTA is entered as soon as IPL drops to 14, and reports Brk 0 at address. The saved PC and PS on the stack show where the system was interrupted. On a multiprocessor the break is taken on the CPU that received the interrupt, usually the primary.

Leaving XDELTA

•;P continues from the breakpoint; address;G continues at an address.

•;C forces a bugcheck (BUG$_DEBUGCRASH), which produces a crash dump if the system is set up for one. See OpenVMS Crash or Hang: Capturing Diagnostics.

•EXIT does not work in XDELTA. XDELTA stays loaded until you reboot without it.

Commands you will use first

All numbers are hexadecimal. XDELTA shows no prompt; it waits for input. Commands of the form ;x end with Return. Do not type extra spaces: a space is the addition operator (manual, chapter 4 and section 2.3).

Registers are R0 to R31 (decimal), PC, PS, FP0 to FP31 and FPCR; open them with / like memory. Useful symbols: G is the start of system space (FFFFFFFF80000000), . is the current location, Q is the last value shown, X4 is the current CPU's database.

Cautions

•Run XDELTA on a standalone system: breakpoints are handled at IPL 31, so the whole system stops while XDELTA waits for you (manual, section 1.3).

•Eh? is XDELTA's only error message. On Alpha it can also mean a step or proceed could not write the next instruction; use O, or set another breakpoint and ;P.

•On a multiprocessor only one CPU is in XDELTA at a time; a breakpoint set on one CPU applies to all.

•EMulatR and the JIT. EMulatR applies a changed instruction when the guest synchronises the instruction stream, as Alpha requires after code is patched. Breakpoints have not yet been verified on EMulatR with the JIT on; if a breakpoint is not hit, run with EMulatR_JIT=off.
