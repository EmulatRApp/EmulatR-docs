Current Development Status

This page is a plain-language snapshot of where EmulatR stands as of August 2026 -- what works end to end, the milestone the project is working toward next, and the known rough edges. It is deliberately a moving target; the authoritative day-to-day record lives in the engineering journals and the dated CHECKPOINT notes. For a per-subsystem breakdown see the Feature Matrix.

 

What works today

A clean cold boot runs the original, unmodified DEC SRM console firmware all the way to the interactive >>> prompt, fully usable over a serial terminal. The commands show config, show memory, show pal and show version all return correct output. Firmware is a real SRM 7.3-1 image carried in emulated flash; the LFU update srm path works, and machine-state snapshots have been captured for both the firmware-update (UPD>) and console (>>>) states. An entry-snapshot boot-acceleration lever (EMULATR_FAST_DECOMPRESS) was designed on top of snapshots but is NOT implemented; booting the pre-decompressed .rom image is the working way to skip self-decompression. ES40 (Typhoon) silicon-mode bring-up is in progress alongside the DS10 / DS20 line.

 

The current frontier: mounting the system disk

The frontier has moved. Both gaps that previously stood between the console prompt and an OS boot are CLOSED: on-board PCI devices are now walked and enumerated (the SCSI adapter and the Ethernet controller are modeled and appear in show config), and a bootable SCSI disk is enumerated - show device lists a dka drive carrying a genuine DEC identity, and boot dka0 loads and transfers to the operating system bootstrap.

 

OpenVMS Alpha V8.3 now boots from that disk to its startup banner reliably, and its device drivers initialize against the emulated adapter and drive: the adapter is identified correctly as a SCSI port, the drive's identity strings and capacity reach the guest byte-exact, and the power-on attention handshake completes.

 

That blocker is cleared, and the boot now goes considerably further than a prompt. A cold boot reaches the OpenVMS Username: prompt with no human at the console, and the startup behind it is healthy: LANACP, IPCACP, ERRFMT, OPCOM, JOB_CONTROL and TP_SERVER all settle at their real priorities, no process parks in WTTQE, QUEUE_MANAGER runs, TCPIP comes up with an active interface and an address, and NCP SET EXECUTOR ALL returns - that is the guest's own stack configuring itself, not reachability: no host network backend is attached, so nothing leaves the machine - and a full orderly SHUTDOWN completes. Everything on that path was measured working rather than assumed. What remains open is tracked per-item in the gap rows rather than as a single frontier - see EmulatR - Known Gaps.

 

Known cosmetic issues

Two harmless display quirks are still open. Neither affects operation.

 

Garbled SROM revision, and a stray "PuTTY" at the prompt. EmulatR does not populate the SROM revision field, so when the console prints it the firmware formats an uninitialized buffer and emits a short run of garbage characters. That garbage happens to contain an ENQ control byte (0x05), and PuTTY answers ENQ by transmitting its answerback string - which is literally the word PuTTY - back to the host, where the console echoes it. That is why show config can leave you looking at P00>>>PuTTY. It is a round trip through your terminal emulator, not the emulator inventing text, and it is specific to clients that implement answerback. WORKAROUND: clear PuTTY's "Answerback to ^E" setting. The real fix is to populate the field, or to strip control bytes on the console transmit path so every client benefits.

 

Line-doubling. show device can print each line twice, also seen at the firmware-update UPD> prompt. The leading hypothesis is that this is not a per-command bug but the console transport echoing input that the guest firmware already echoes; the test is to default terminal echo off and see whether the doubling clears. That test has not been run yet, so the cause is not confirmed.

 

What is planned next

• DONE - the system volume mounts and the OpenVMS boot reaches the DCL login prompt on the DS20.

• Complete the SCSI CD-ROM target so an OS can be installed from CD media, not only booted from a prepared disk.

• Give the IDE channel an interrupt path, a write path and DMA, so an IDE disk can serve as a system disk on DS10.

• Finish ES40 init, and drive the Titan machines (DS25, ES45) to the console prompt.

 

Completed since the previous revision of this page: SRM environment persistence (set now survives reset and cold boot via emulated flash), PCI bus enumeration with on-board Ethernet and SCSI device models, and a bootable SCSI disk with real DEC drive identities.

 

Snapshot date: August 2026. Because status changes frequently, treat this page as orientation and confirm specifics against the current build and the latest CHECKPOINT journal.
