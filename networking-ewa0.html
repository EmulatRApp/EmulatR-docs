4.9 Networking (EWA0)

4.9 Networking (EWA0)

EmulatR can bridge the emulated DE500-BA Ethernet controller to a real host network adapter, so the guest becomes an ordinary node on your LAN: it answers ARP, replies to ping, accepts TELNET and FTP sessions, and carries DECnet and OSI traffic exactly as a physical DS20 would.

This page covers the whole path -- what to install, how to prepare the host adapter, how to tell EmulatR to use it, and how to verify the result. For the silicon itself, see the DE500 Ethernet topic.

 

Networking is optional, and enabled by default

With nothing configured, EmulatR looks for a DEDICATED host adapter -- one that is up, connected, and carries NO bound network address -- and attaches to it automatically. That test is chosen precisely because it CANNOT select the host's own NIC: the host's adapter always carries an address, so auto-detection can never place the guest on the same wire as the Windows network stack.

If no such adapter exists, or if several do, EmulatR reports what it found and continues without a wire. Several matches are not guessed between -- name the one you want.

Without an attached adapter the guest still has a fully working NIC with no wire. It initialises, reports link up, transmits, and keeps clean counters -- frames simply go nowhere. Nothing needs to be installed or configured for EmulatR to run.

To choose an adapter explicitly, or to switch networking off altogether, set EMULATR_NET_ADAPTER to a device name or description substring, or to off.

This matters for two reasons. A machine without Npcap behaves exactly as it always did rather than refusing to start, and a run without networking stays DETERMINISTIC -- see Limitations below.

 

Dependencies

EmulatR itself has NO networking dependency. Without any of the below it starts normally and the guest has a working NIC with no wire attached. Everything here is needed only to put the guest on a real network.

The only hard dependency. EmulatR loads wpcap.dll at run time; it is never linked, so no SDK is needed to build or run. If it is absent EmulatR says so and continues without networking.

RECOMMENDED

Not required by EmulatR, but its installer is the usual way to obtain Npcap, and you will want it: EmulatR writes captures in libpcap format and Wireshark is how you read them. Installing Wireshark and letting it install Npcap satisfies both in one step.

A second NIC used for nothing else. Sharing the host's primary adapter works but is much harder to reason about when something goes wrong. See the sections below.

situational

The guest transmits from its own DECnet-derived address, not the host adapter's. Managed switches with port security or a per-port MAC limit will drop those frames. Unmanaged switches and consumer gateways do not care.

 

Installing Wireshark and Npcap

Install Wireshark from wireshark.org and accept the bundled Npcap when the installer offers it. Npcap is also available on its own from npcap.com if you truly do not want Wireshark -- but you will almost certainly want to inspect packets at some point, and there is no second copy of the driver to conflict with.

The supplied Wireshark profile

EmulatR ships a Wireshark configuration profile that turns a raw capture into something readable. It is in the installed tree at tools\wireshark\ as both a folder and a zip.

 

It provides three things:

File

What it gives you

dfilters

A grouped bookmark list beside the display filter bar -- ANOMALIES, ADDRESSING, PROTOCOL FAMILIES and SANITY.

dfilter_buttons

One-click toolbar buttons: All, Bcast, Mcast, Group, Unicast!, DECnet, OSI, IP, Undec, <60, >1514.

To install it: Edit -> Configuration Profiles -> Import -> from zip file, then select EmulatR-EWA0 from the profile list (it also appears in the bottom-right of the status bar). If the import misbehaves, copy the EmulatR-EWA0 folder into %APPDATA%\Wireshark\profiles\ instead and restart Wireshark.

IMPORTANT: the bookmark list and toolbar buttons only appear once a capture file is OPEN. On Wireshark's welcome screen the only filter box is the CAPTURE filter, which takes BPF syntax and will reject display-filter expressions such as eth.dst. Open the file first.

 

The anomaly probes are the point of the profile. On a healthy capture each of these should return ZERO:

Probe

A hit means

<60

A frame below the 60-byte pad floor -- a TX padding defect in the model.

>1514

An oversize frame -- a descriptor gather defect.

Unicast!

Unicast traffic where none is expected. Legitimate once the guest has peers; suspicious before that.

Undec

A note on capture files: EmulatR's own captures are written in libpcap format and open directly. A LIVE Wireshark capture on the host adapter shows the same traffic from the host's side, which is useful for confirming that frames really left the machine.

 

Use a DEDICATED host adapter

Bridge the guest to an adapter that does nothing else. Sharing the host's primary NIC works but is materially harder to reason about.

 

A dedicated adapter gives three things:

Property

Why it matters

Exactly one route on the subnet

No multi-homing, no interface metrics, and no question about which adapter Windows chose when something goes wrong.

No host stack on that wire

Windows neither processes inbound frames nor answers ARP there, so it cannot collide with the guest.

Clean captures

A capture taken on that adapter contains guest traffic and genuine LAN traffic only -- never the host's own stack chattering into the file.

 

On the adapter's properties, UNBIND every protocol -- Internet Protocol Version 4 and 6, File and Printer Sharing, LLDP -- and leave ONLY Npcap Packet Driver (NPCAP) enabled.

This is safe because Npcap is an NDIS lightweight filter that sits BELOW the protocol edge. It needs no protocol driver bound, and it is ethertype-agnostic: DECnet, OSI, LAT, MOP, ARP and IP are all simply raw frames to it.

 

Host adapter: required bindings

ONLY the Npcap packet driver may be enabled on the EmulatR NIC. Every other protocol, service and filter must be UNBOUND. This is not a preference -- a bound protocol puts the Windows stack on the same wire as the guest, where it can answer ARP, claim an address, and appear in captures that are supposed to contain guest traffic only.

Npcap is an NDIS lightweight filter and sits BELOW the protocol edge, so it works perfectly well with nothing else bound.

The converse matters as much: Npcap must be UNCHECKED on every OTHER adapter. Installing Wireshark binds Npcap to every adapter on the computer. Afterwards, open Properties on each adapter except the EmulatR NIC and uncheck Npcap Packet Driver (NPCAP). When you are done, Npcap should be enabled on exactly one adapter -- the EmulatR NIC -- which keeps a packet-capture filter off the computer's own connections, and makes the EmulatR NIC the only adapter that carries Npcap.

To check every adapter at once:

Get-NetAdapterBinding | Where-Object ComponentID -like '*NPCAP*' | Format-Table Name, Enabled

Enabled must be True for the EmulatR NIC and False for every other. The pattern matches either Npcap component ID -- NPCAP or INSECURE_NPCAP -- which differ depending on how Npcap was installed.

Host adapter: Power Management tab

SEPARATE FROM THE ADVANCED PROPERTIES ABOVE, and easy to miss because it lives on a different tab of the adapter's properties dialog. In Device Manager, open the adapter, go to the Power Management tab, and UNCHECK:

Checkbox

Required

Why

Allow the computer to turn off this device to save power

UNCHECKED

Windows may power the adapter down independently of any driver setting. A powered-down NIC loses link, and the guest is not told -- it simply stops receiving. This defeats every advanced-property setting above if left checked.

Allow this device to wake the computer

unchecked

Wake logic implies the device is expected to sleep. A dedicated bridge should never sleep.

Only allow a magic packet to wake the computer

unchecked

Moot once waking is disabled; uncheck for consistency.

From PowerShell, the equivalent is:

Disable-NetAdapterPowerManagement -Name '<adapter>'

Verify with Get-NetAdapterPowerManagement -Name '<adapter>'. Note that not every driver exposes these through PowerShell even when the Device Manager checkbox is present -- if the cmdlet returns nothing, set it in Device Manager and confirm visually.

 

Applying it

The supplied script applies every MUST SET row above, reports what was already correct, and skips anything the adapter does not expose:

tools\provision_enic.ps1 -Match <description-substring>

Options: -DryRun shows changes without making them; -Name selects by adapter name instead of description; -Force overrides the refusal to touch an adapter holding an IPv4 address.

The script writes the previous values to a JSON file beside itself before changing anything, and restarts the adapter once at the end.

RE-RUN IT AFTER ANY DRIVER UPDATE OR ROLLBACK. A driver install silently restores the shipping defaults, and the resulting failure is gradual and easy to misattribute.

 

Telling EmulatR which adapter to use

Using the installed kit? Set the adapter in the Launcher's Runtime environment variables panel -- and TICK its row, or the value is ignored. The complete procedure, with how to confirm it took effect, is in Naming the Host Adapter (EMULATR_NET_ADAPTER). The forms below are the values that page describes.

Unset means AUTO-DETECT, which is the default: EmulatR attaches to the one adapter that is up, connected and has no bound network address. To choose an adapter yourself, set EMULATR_NET_ADAPTER before launching; set it to off to disable networking.

On a machine with more than one adapter -- a laptop with Wi-Fi and a wired port, for example -- see Choosing the Host Adapter (Wi-Fi and Wired). Wi-Fi cannot carry the guest; use a wired adapter.

The value is either a libpcap device name or any case-insensitive substring of the adapter's description:

EMULATR_NET_ADAPTER="I219"

EMULATR_NET_ADAPTER="\Device\NPF_{DD1B82DC-0887-4F32-AD71-0D9CCE161C71}"

Prefer the description substring. A device GUID changes when hardware moves; a description usually does not. If no adapter matches, EmulatR lists every adapter it can see so you can choose.

On startup EmulatR reports the adapter it attached to, the Npcap version, and a reminder that the run is no longer deterministic.

Run these in order. Each is independent, so the first one that fails tells you where to look.

Capturing traffic

EmulatR can write every frame crossing the descriptor ring to a libpcap file, readable directly in Wireshark:

EMULATR_DIAG_TULIP_PCAP=1

The capture lands in the run directory as logs\<stem>_ewa0.pcap. It records frames as they cross the emulated wire, so it is the guest's view rather than the host's -- which makes it the right instrument for questions about what the guest actually sent or received.

This knob exists only in diagnostic builds. A hex dump of the same frames is available with EMULATR_DIAG_TULIP_DUMP=1.

 

Limitations

Limitation

Detail

A networked run is NOT deterministic

Inbound frames arrive on other machines' schedules, so two runs of the same firmware are not the same run. Never enable networking for a timing measurement or a paired comparison, and state that it was enabled when recording any result from such a run.

Host link loss is not reported to the guest

If the host adapter loses link, the guest is not told: it sees no link-down transition and no transmit failure, and recovery has to come from protocol timeouts instead. This is why the power-saving settings above matter so much.

Oversize frames are discarded silently

A frame larger than the emulated NIC's maximum is dropped by EmulatR rather than delivered part-formed. The guest's Frame too long counter does not move. Setting Jumbo Packet to 1514 prevents the situation arising.

Link speed is reported, not modelled

The guest may report a 100 Mbps full-duplex link, but no transmission timing is derived from it. The setting affects what the guest BELIEVES; it is not a throughput or timing reference.

 

Troubleshooting

Symptom

Likely cause

Backend reports UNAVAILABLE at startup

Npcap not installed, or installed Administrators-only while EmulatR runs unelevated. The message states which.

No adapter matches the configured name

EmulatR lists every adapter it can see -- choose a substring from that list.

Guest transmits but nothing arrives

Check the switch is not filtering the guest's MAC. The guest uses a DECnet-derived address, not the host adapter's, so port security or a MAC limit will drop it.

Ping and TELNET work, bulk transfer stalls

Almost always host adapter power saving. Run provision_enic.ps1 and retest.

Guest receives broadcast but not unicast

Expected only on builds predating the station-address learning fix; otherwise check the switch.

Transfers slow with rising retransmissions

Capture on the host adapter as well as in EmulatR. If frames appear on the wire but not in EmulatR's capture, the loss is on the host side.
