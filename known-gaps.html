EmulatR - Known Gaps

Release checkpoint = DS10 + DS20 + ES40 certified to the same boot milestone. All three reach P00>>>, and that three-platform console gate is now a standing pre-commit requirement for any shared core, chipset, or device change; ES40 does not yet complete init. IDs are stable handles: an ID is never reused, and a row is never deleted. When a gap closes, its row is replaced by a one-line TOMBSTONE in the Closed and retired IDs table below, carrying the close date and where the result went, so that a citation to the ID keeps resolving after the work is done.

 

Beyond the console, the current front is the guest operating system: OpenVMS Alpha V8.3 boots from the SCSI disk to its banner reliably on DS20 and its drivers initialize, the system volume mounts, and the boot reaches the DCL login prompt on the DS20. Rows G-28 through G-30 carry what remains on that front.

 

Severity legend. BLOCKER: on the ES40 boot/console path, gates the checkpoint. OPEN: unresolved contradiction to reconcile. GAP: fidelity or downstream, not blocking the prompt. REF: blocked on an absent primary source. DEFER: intentional deferral (silicon-mode / a later generation / post-prompt). PROV: a value is _PROVISIONAL.

Trust in the ISP model

G-08

DEFER

Exec mode

Silicon-mode delays busy-wait on RSCC; krn$_micro_delay returns immediately only in ISP mode, so silicon grinds. EmulatR models RSCC = cycleCount/5594; the fix is a safe warp that advances cpu.cycleCount COHERENTLY so RSCC crosses the limit and the spin exits. The surviving levers to build on are EMULATR_UDELAYWARP, which advances only as far as the next timer edge so no boundary is skipped, and EMULATR_SPINSKIP. The old warp family - EMULATR_IDLEWARP, EMULATR_RSCCWARP and the rest - was REMOVED on 1 August 2026 and is not available to re-enable; RSCCWARP is why the survivors are shaped this way, having jumped ticks and rewritten 0x3c970 out-of-band for confirmed boot corruption. Gated EMULATR_PLATFORM=silicon, discuss-before-code.

 

Silicon mode is now a live surface for the warp validation.

Silicon-mode completion

REFERENCE BLOCK CLEARED - the ALi M1543C datasheet is now in the reference library, and PCI identities and legacy port decode are verified against it. What remains is behavioral: south-bridge configuration space above the identity header is stored but inert (IDE enable/disable, IDSEL relocation, interrupt routing and PIRQ steering have no effect), which is the prerequisite for wiring the IDE interrupt path (G-30).

SCSI

REFERENCE BLOCK CLEARED and the adapter is BUILT - this row no longer describes a missing file. G-17

GAP

FP/FBOX

Arithmetic leaf coverage is still partial and Tier 0 FPCR / rounding-mode infrastructure is still owed. NOTE this row is NOT what blocked the VMS startup: that was the S/F FORMAT-CONVERSION helpers (LDS/STS/LDF/STF are architected BIT operations and were implemented as arithmetic re-encodes), fixed and accepted 2026-08-18 with static_assert gates so a conversion regression fails the build. READ THIS ROW TOGETHER WITH Floating-Point Considerations, which describes the same situation from the other end and can look like it disagrees: the COMPUTE BACKEND is complete - SoftFloatBackend implements the whole IEEE S/T and VAX F/G operation set over Berkeley SoftFloat, bit-identical across hosts - while what is partial is the WIRING of that backend into the individual FP grain leaves. Backend complete, integration in progress. This row stays open on the Tier 0 FPCR / rounding-mode work, not on the arithmetic itself.

OS boot (post-console)

G-18

DEFER

DMA

Scatter-gather translation is now IMPLEMENTED and verified against the chipset manual (page-table walk, address composition, window-miss behavior) with unit tests, and device DMA is routed through it. It remains UNEXERCISED by real firmware: the console and the guest so far use direct-mapped windows, so the gather path has no live witness yet. Expect the OS-installer DMA-mapped path to be its first real consumer.

G-21

DEFER

JIT

No JIT code generation. V6 is fidelity-first: the interpreter is the reference implementation and JIT is deferred behind it by design; jitLib in the tree holds trivial examples only. The deferral condition -- a guest operating system booting -- has now been met (G-22), and a first execution profile has been measured to decide whether the JIT program proceeds. No throughput figures are published here until that decision is made.

(by design)

G-22

DEFER

OS boot

End-to-end OpenVMS boot. LARGELY ACHIEVED on the DS20: a cold boot reaches the Username: prompt unattended, and the startup behind it is healthy - system processes at real priorities, no WTTQE parking, QUEUE_MANAGER running, TCPIP up with an active interface, NCP SET EXECUTOR ALL returning, and an orderly SHUTDOWN completing. What remains depends on G-17 (floating point) and, for the multi-CPU machines, G-19 (SMP). Tru64 remains untried.

Milestone

G-23

BLOCKER

Boot

RUN/STOP handling on the boot path; mechanism _PROVISIONAL - CPU RUN/STOP (console halt/continue, HWRPB BIP/RC hand-off) and/or device RUN/STOP (controller start/stop bit in the boot driver). Future blocker once boot is wired; trace to pin the mechanism before scoping.

boot hand-off (G-03)

G-24

OPEN

Silicon

ES40 does not yet initialize in silicon mode (EMULATR_PLATFORM=silicon) -- outstanding diagnostic, active surface (not a deferral). Under warp the RSCC micro-delay spin now exits (G-08), but ES40 init still does not complete on the silicon path; entangled with the ISP-path init blockers (G-02 / G-10) and the exec-mode reconciliation (G-06 / G-07). Needs an evidence-first trace of where silicon-mode init diverges before scoping a fix.

ES40 silicon-mode bring-up

G-25

DEFER

Config/CLI

Unified configuration precedence not yet implemented. TODAY: built-in defaults < Emulatr.ini < CLI (CLI wins) for shared tunables (firmware, memory). EMULATR_* env vars are ORTHOGONAL -- most are ENV-only diagnostic/trace toggles; the two that overlap a CLI flag (--no-autoload / EMULATR_NO_AUTOLOAD, --autosnapshot / EMULATR_AUTOSNAP) are OR/AND-merged, not ranked. INTENDED: a single order ini < CLI < ENV (ENV overrides both), by threading env reads through the same settings resolver as ini/CLI.

Unified config override (intended)

G-26

DEFER

Config/INI

RESOLVED - the rename has landed. The settings file is Emulatr.ini (release versioning is handled by the directory tree / hive, not the filename), the loader searches for that name only (IniLoader::defaultSearchPaths), and the shipped file is config/Emulatr.ini. The doc topics that still named the old file were corrected on 2026-08-20. Note no back-compat fallback was kept: the old name is not in the search order at all, so a stale copy is simply ignored.

Filename cleanup (intended)

G-28

DEFER

SCSI

No disconnect / reselection and no tagged command queuing. The adapter runs every command to completion without releasing the bus, which is self-consistent and adequate for a single initiator with one outstanding request, but it is not how the real chip behaves under a loaded multi-drive system. INTERLOCK, learned the hard way: the drive must not advertise the queuing capability until the adapter can actually honour it - claiming it while tag messages are silently discarded wedged the mount path for tens of thousands of operations. Advertise only when both halves land.

Concurrency; multi-drive load

G-29

GAP

SCSI / CD

The virtual SCSI CD-ROM lags its disk sibling on protocol behaviour shared by both: it has no UNIT ATTENTION condition at all (so a media change is invisible to a running guest, and swapping an image under a mounted volume goes unannounced), pending sense is not cleared by an intervening successful command, an unsupported command does not record why it failed, and MODE SELECT is absent - the same command whose absence previously broke the disk boot path. Enumeration and console-era use are unaffected.

Booting or installing from CD media

G-30

GAP

IDE

The IDE / ATAPI channel is a polled, read-only enumeration surface: no interrupt path (IRQ 14/15 are never driven), no write path (every write aborts), and no DMA. The no-DMA story is at least internally honest - the drive advertises no DMA capability, so a conforming driver stays in programmed I/O. Harmless while the system disk is SCSI; FATAL for any IDE-resident OS disk or install target, and the three pieces are interlocked and must land together. Blocked behind G-09.

IDE as a system disk (DS10)

G-31

GAP

Console

>>> init is not verified to perform a reset boot. On a real DS20 it warm-resets the console (banner and device probe re-run), PRESERVES the environment variables, and then honors auto_action - so with bootdef_dev and auto_action set, init returns to the guest with no keystrokes. What EmulatR does instead is unrecorded. Distinct from G-02, which is the ES40-specific fault.

Hands-off reboot; beta test plan

G-32

GAP

Console / OS

Guest-initiated stop: behaviour observed, confirmation pending. On the current binary a VMS SHUTDOWN taking the POWER_OFF option was observed to exit EmulatR cleanly (HaltedClean), while a PLAIN shutdown halts back to >>> with the process still alive - both seen 2026-08-20. The SRM >>> power off command itself remains untested. Treat as observed-not-yet-confirmed; the ledger carries the evidence.

Fully hands-off boot-work-shutdown cycle

What it was, and where the result went

G-14

before 2026-08-20

Retired under the earlier delete-on-close policy, and its text did not survive: no copy of this topic still holds the row, so what G-14 said cannot be stated here without inventing it. What is known is only its company - it is cited in the Notes below as one of the unmodeled-region gaps alongside G-05, G-10 and G-20, where a region that is not decoded answers with a plausible-looking value the firmware then branches on. This entry is the reason the policy changed.

 

G-27

2026-08-20

The SCSI system disk never went VALID under OpenVMS, so the volume was never mounted and the boot could not proceed to a login prompt. CLOSED: the DS20 now mounts the system volume and boots through to the Username: prompt unattended. The remaining guest-OS work moved to G-17 (floating point) and G-19 (SMP), with G-28 to G-30 covering SCSI concurrency, CD media and the IDE surface; the milestone itself is tracked by G-22.

 

G-33

2026-09-20

No host L2 backend was attached to the DE500 (21143), so nothing left the emulated machine: a guest could bring an interface up and configure an address with no reachability at all. CLOSED: EWA0 now bridges to a dedicated host adapter over libpcap/Npcap and is ON BY DEFAULT. The guest answers ARP, replies to ping, accepts inbound TELNET and FTP, and brings a DECnet circuit to State = On with every one of its own error counters at zero. The receive path is proven for all three address classes -- unicast, broadcast and true multicast. What is carried but still UNTESTED moved to the release notes rather than back here: LAT, LAST/InfoServer, and the SCS traffic an OpenVMS Cluster runs on. Result: Networking (EWA0) in the release notes and topic 4.9 of this guide.

 

 

Notes

Release-critical set (must clear for the DS10/DS20/ES40 console checkpoint): G-01, G-02, G-03, G-04, G-10, plus the G-07 reconciliation. Guest-OS-critical set: G-27 is CLOSED (OpenVMS reaches a login prompt and a full startup on DS20); what remains on that front is G-17 (floating-point leaf coverage) and G-19 (SMP / cross-CPU IPI), with G-28 to G-30 covering SCSI concurrency, CD media and the IDE surface.

 

Reference blocks cleared since the previous revision: G-09 (ALi M1543C datasheet) and G-13 (SCSI datasheets plus the DEC SRM driver source). Both rows were rewritten rather than deleted because a behavioural gap survives the reference arriving - the source was the blocker, not the whole gap. No ID has been reused.

 

Next probe (evidence-before-scope): a compile-gated NXM-address probe at the raise site to confirm or refute G-10 before any Pchip-decode edit lands.

 

Unifying failure mode across G-05/G-10/G-14/G-20: an unmodeled region returning a plausible-looking value (0x00 or 0xFFFF...) the firmware branches on, so the symptom surfaces far downstream from the defect. Every CSR the console reads must be decoded and faithful; INERT-TRUTHFUL store-through is allowed only where no consumer reads a side-effect.

 

Second failure mode, learned on the mount path and now standing doctrine (see G-28): a CAPABILITY CLAIM is not a label - it is an assertion the other side acts on. A wrong geometry value is inert until something reads it, but a wrong capability bit changes what the guest DOES. A device datasheet's feature list describes the silicon, not the model; advertise a capability only when the model can honour it end to end.
