System Disk Configuration

This topic takes you end to end: create an EmulatR virtual disk, point the platform manifest at an OpenVMS distribution ISO and at the new disk, boot the ISO, install OpenVMS onto the virtual disk, and boot the installed system disk. The worked example is a DS20 (Tsunami/EV6) with firmware stem ds20_v7_3. DS25, ES40 and ES45 follow the same shape; DS10 differs in one respect, noted under Step 3.

 

The storage model in one paragraph

EmulatR enumerates EXACTLY the storage devices declared in the platform manifest (<stem>_platform.json, for example ds20_v7_3_platform.json). A storage row MEANS the device exists on the bus: an undeclared SCSI id selection-times-out, and a row whose media is empty enumerates as an empty drive. Each row names its media as a bare FILENAME, which resolves against the [Storage] diskDir setting in Emulatr.ini -- in a launcher-managed system that is the run directory's disks folder. Drive identity and geometry come from the row's model field, resolved against the storage catalog. So a manifest names a drive TYPE and a filename, never a byte count and never a host path.

 

What a fresh installation ships with

The manifests in a newly installed copy are deliberately unwired. Every storage row is present, but only dka0.vdisk -- the system-disk convention -- names any media; every other row ships with its media field empty. Since an empty-media row does not enumerate a device, a fresh installation boots with just the one system disk, and no manifest points at a path that existed only on the machine that built the kit.

 

The empty rows are left in place on purpose: they are the documentation of which slots the platform offers. To use one, fill in its media field with a filename (and set the row's model to a drive profile no smaller than the image). To add the system disk, either create it as dka0.vdisk and it is picked up as shipped, or edit the id-0 row to name whatever you called it.

 

Step 1 -- Create the virtual system disk

Use Make Disk in the EmulatR Launcher. It opens the Create Virtual Disk dialog, which writes the container into the SELECTED system's disks folder -- placement is fixed, there is no free path selection, and that is deliberate: the manifest can then name the file by bare filename and the whole run directory stays portable.

 

field

what it does

Drive model

28 verified DEC drive geometries (RZ, RA, RF, RC and ESE series), plus a Custom geometry entry. Selecting a model shows its exact geometry and pre-fills the name.

Custom geometry

Cylinders, heads, sectors per track and block size (512 for a fixed disk, 2048 for optical). Container size is the product of the four. Sanity-bounded, not policed.

Disk name

A file stem: ASCII, no path separators, no Windows-reserved names. The extension .img is added for you.

Will create

Live preview of the exact path, the block count and block size, the resulting size, and the free space on that volume -- all shown BEFORE anything is written.

 

Create stays disabled until the geometry and the name are both valid and there is room. The dialog refuses to overwrite an existing file, and refuses outright when the volume has less free space than the image needs, naming both numbers.

 

The container is a RAW FLAT FILE: exactly total_lbn * block_bytes zero bytes, sparse where the host filesystem supports it, with no header, no partition table, no disklabel and no filesystem. It reads back as zeros -- a blank drive. The OpenVMS installation writes every structure onto it. That is exactly what an install target should be.

 

Choosing a drive profile

The model list is read from the emulator's own storage catalog, config/disk_types.json, found beside the emulator the system is set to launch. The key you pick here IS the model value you will type into the manifest in Step 3 -- one name, one namespace, no translation. Retired profiles are never offered, so a name that reaches the dialog is a name the manifest accepts.

For an OpenVMS Alpha system disk, pick RZ29L. Custom geometry remains available for a size the catalog does not cover, but a custom container still has to be DECLARED under some catalog profile, and that profile must be no larger than the container: an image smaller than its declared profile is REFUSED at attach. Larger is accepted and simply wastes the difference.

 

If the dialog cannot locate an emulator -- and therefore cannot read the catalog -- it falls back to a bundled geometry list and says so. That list is for offline authoring; it may lag the catalog and can name profiles the manifest will not accept. Point the system at its emulator binary and reopen the dialog rather than creating from the fallback.

 

Step 2 -- Place the OpenVMS distribution ISO

Copy the distribution ISO into the same disks folder. An ISO is SUPPLIED, never created: the optical device is read-only, so no creation path applies to it and Make Disk has no part in this step.

 

Step 3 -- Declare both in the platform manifest

Open the Platform Editor from the launcher (the Configure button in the bottom bar, or Open in PlatEd on the system's detail tab). It is a schema-validated manifest authoring tool with the drive catalog built in, and its JSON round-trip preserves field order and comment fields, so your annotations survive an edit.

 

1.Select the SCSI HBA (pka_53c810). On the id-0 row, set model to RZ29L and media to the file from Step 1.

2.Select the IDE controller (cypress_ide). On the ATAPI row, set media to the ISO from Step 2.

3.Save. Validation flags illegal rows -- SCSI id 7, duplicate ids, missing media -- before they ever reach a boot.

 

Manifest reference

The manifest is strict JSON. Storage rows live in a storage array inside the controller's entry under pci_devices. SCSI disks hang off the NCR 53C810 HBA (console pka0, disks dka*); the CD-ROM is an ATAPI row on the Cypress 82C693 IDE function (console dqa*).

The system disk at SCSI id 0, and the distribution CD:

 

{ "channel": 0, "unit": 0, "lun": 0, "type": "scsi_disk",

 "model": "RZ29L", "media": "system_disk.img",

 "media_kind": "image",

 "comment": "SCSI id 0 -> dka0: the OpenVMS system disk." }

 

{ "channel": 0, "unit": 1, "lun": 0, "type": "atapi_cdrom",

 "model": "EMULATR VIRTUAL CDROM", "media": "OpenVMS_v82.iso",

 "media_kind": "iso",

 "comment": "primary slave = dqa1, ATAPI CD. media empty = no disc." }

 

SRM unit naming for SCSI is dka<id*100+lun>: id 0 is dka0, id 1 is dka100, id 6 is dka600. IDE names follow the real-hardware 100*func+slot convention -- slot 5 func 1 gives 105, so the CD is dqa1.1.0.105.0. Only IDE channel 0 is declared today; dqb is a known gap. DS10 is IDE-only and has no SCSI rows -- there the system disk is an IDE row and boots as dqa0.

 

What not to touch

Leave iic_devices (platform badge and FRU identity), pci_irq_table_hose0 (board interrupt routing, transcribed verbatim from console sources) and the vendor / device / class_code / bars fields of existing devices alone. These are board data, not user configuration. Interrupt pins are silicon constants owned by the device models -- never add an interrupt_pin field.

 

Step 4 -- Boot the distribution CD and install

Start the system from the launcher and open its console. At the SRM prompt, confirm the CD and the blank target both enumerated, then boot the CD:

 

P00>>> show dev

P00>>> b dqa1

 

show dev lists exactly the enumerated devices and prints the first token of each drive model. From there the standard OpenVMS installation dialog runs: choose the install option, select DKA0: as the target device, give the volume a label, and let the installer initialize the disk and restore the distribution save sets. Nothing in the procedure is EmulatR-specific -- follow the OpenVMS installation guide for the version you are installing.

 

Beta status. Booting an ALREADY-INSTALLED system disk is the exercised path and is on the Ready-for-Testing list. A full install from distribution media onto a blank target is not yet on that list. If the installation dialog stalls, keep the console log and report it, and use the migration route below in the meantime.

 

Step 5 -- Boot the installed system disk

Once the install completes, boot the disk directly:

 

P00>>> b dka0

 

The recommended interactive entry path is a conversational boot, which reaches a live DCL prompt on the console:

 

P00>>> b dka0 -fl 0,1

SYSBOOT> SET/STARTUP=OPA0:

SYSBOOT> C

 

That yields the version banner, a date and time dialog if the hardware clock has not been set yet (see the Time-of-Year Clock topic -- with the default clock mode it is already set, and the dialog does not appear), and a root $ prompt. To run the full startup afterwards, use @SYS$SYSTEM:STARTUP FULL "VD", which runs to completion with DCL verification echoed and leaves a transcript in SYS$SYSTEM:STARTUP.LOG. To restore normal automatic startup permanently, return to SYSBOOT> and issue SET/STARTUP SYS$SYSTEM:STARTUP.COM together with SET STARTUP_P1 "".

 

Alternative -- migrate an existing system disk

A system disk built elsewhere (another emulator product or real Alpha hardware) can be adopted directly, and this is the best-exercised route today.

 

1.Copy the disk image file into the system's disks folder.

2.Point the SCSI id-0 row's media at it, with model set to a profile no larger than the image -- RZ29L for a 4 GB image.

3.Boot with b dka0.

4.On first boot, check that SHOW LOGICAL SYS$TIMEZONE_DIFFERENTIAL matches the site's real offset -- imported state travels with the disk.

 

Never attach the same image file to two running emulators at once. Disk images are single-writer; concurrent attachment corrupts the volume.

 

Adding data disks

Make the disk, declare it at a free SCSI id, boot, then initialize and mount it from DCL:

 

$ INITIALIZE DKA200: MYDATA

$ MOUNT/SYSTEM DKA200: MYDATA

 

Add the MOUNT to SYSTARTUP_VMS.COM so the volume returns across boots. This is ordinary OpenVMS administration; consult the VMS system manager documentation for the details.

 

Creating disks from a script

Make Disk is the supported path and needs nothing installed. For scripted or repeatable provisioning on a development machine, tools/mkdisk.py is the scriptable equivalent. It resolves its size from the runtime catalog rather than the launcher's table, so its --type takes the same key you put in the manifest:

 

> python tools/mkdisk.py --type RZ29L disks/system_disk.img

> python tools/mkdisk.py --type EMULATR-512M disks/mydata.img

 

--type is required and the size is DERIVED from it -- you never pass a size. It requires a Python interpreter, which is why it is not the tester path.

 

Caveats

•Warm reboot after a halt (Ctrl/P to >>> then b) faults the second boot deterministically today (kernel-stack-not-valid; tracked as JRN-KSNV-001). Exit EmulatR and relaunch for a fresh boot instead.

•Periodic auto-snapshot makes iteration cheap: --autosnapshot 1000000000 mints a save every 1B cycles, and a later launch without --no-autoload restores a mid-session guest to the prompt in seconds.

•The IDE secondary channel (dqb) is not yet declared.

•Tagged queuing and reselection on the SCSI bus are later-phase work; the target set is command-queue-free by design.

•Catalog geometry is checked against a +/-2 percent band, never an equality assert -- these are banded (ZBR) drives whose published sectors-per-track is a flattened average.

•Silicon memory ceilings are enforced per platform (DS10 2 GB, DS20 4 GB, ES40 32 GB); an oversized memory request is clamped.
