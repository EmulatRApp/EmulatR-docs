AlphaServer ES40

The ES40 is a four-processor Typhoon system with the ALi M1543C south bridge in place of the Cypress part the DS10 and DS20 use. Its SRM console powers up cleanly to P00>>> with every device present, and it boots OpenVMS V8.3 from its SCSI system disk to the Username: prompt.

These are the positions a real ES40 uses. The four parts of the ALi M1543C are four separate single-function PCI devices, each on its own device number: the ISA bridge at 7, the IDE controller at 15, power management at 17 and USB at 19. The positions are fixed by the board and are not relocatable in the platform manifest. OpenVMS depends on them: its ES40 support expects the IDE controller as function 0 of device 15, and stopped with a bugcheck during startup while EMulatR presented it anywhere else.

 

Console firmware

Required firmware. The ES40 works only with HP's 67CLIPPER SRM console, V7.3-1. That is the firmware EMulatR is tested with: the console completes its power-up and stops at P00>>> with every device present, and OpenVMS V8.3 boots from the SCSI system disk to the Username: prompt with the JIT off and on. No other ES40 firmware works with EMulatR at this time.

EMulatR does not ship firmware (see Firmware Requirements). You obtain the file, prepare it once, and copy it into the system's firmware folder under the name es40_v7_3.exe. The steps below cover each part.

Where to get it

HP's V7.3 ES40 console files were published on Digital's firmware FTP site as a single zip, es40.zip, which is preserved in a public archive of that site:

https://ftp.zx.net.nz/pub/archive/ftp.digital.com/pub/DEC/Alpha/firmware/v7.3/es40/es40.zip

 

The zip is 4,209,297 bytes and dated 4 March 2007. It holds eight files: the 67CLIPPER console (cl67srmrom.exe and cl67srmrom.sys), the CLIPPER console (cls67rmrom.exe, cl67srmrom.sys), the AlphaBIOS console (clarcrom.exe), and HP's clu.exe, mkboot.exe and mkbootfirm. Only cl67srmrom.exe (or cl67srmrom.sys) is needed.

 

Check the download, then unzip it. In PowerShell, in the folder that holds the zip:

Get-FileHash .\es40.zip

Expand-Archive .\es40.zip -DestinationPath .\es40

Get-FileHash .\es40\cl67srmrom.exe

 

The two hashes must be, in order:

C42397A55F7DEF1E0A818E86D41A4CA6044DE5B0FA0C11989E104F995933A537

392546CD375A734883A48026D36F6F48E3B0FCE636F6DD9EE190D49A042FC885

 

The second is the file EMulatR is tested with, wherever it comes from; the same cl67srmrom.exe circulates on other sites too. A different hash means a different file: another version, another platform, or a damaged download. Do not use it.

 

Why the file must be prepared

HP packages the console as an input to its firmware update utility, not as a bare console image. The file holds, in order: a 512-byte update wrapper (1,024 bytes in the .sys), a 64-byte flash header naming the version and platform, the console image itself (692,224 bytes), and a checksum.

 

EMulatR loads a firmware file into the emulated machine's memory exactly as it is on disk, so the wrapper and header must be removed first. Preparing the file does only that: it copies out the console image unchanged. Nothing is decompressed. The console image is compressed, exactly as it sits in a real ES40's flash, and it decompresses itself each time the emulated machine starts, as the real console does.

 

Preparing it with PowerShell

Needs nothing beyond Windows. In the folder that holds cl67srmrom.exe (the es40 folder the zip was expanded into):

$b = [IO.File]::ReadAllBytes("$PWD\cl67srmrom.exe")

$o = New-Object byte[] 692224

[Array]::Copy($b, 576, $o, 0, 692224)

[IO.File]::WriteAllBytes("$PWD\es40_v7_3.exe", $o)

Get-FileHash .\es40_v7_3.exe

For cl67srmrom.sys, read that file instead and use 1088 in place of 576. The prepared file must be exactly 692,224 bytes, and its hash must be:

968876CB19D2330B0FFDA806CE7A7A10CD983E6049AE31C8A86A1BDDF8787D6D

 

Preparing it with the EMulatR tool (source tree)

The source tree has a script that does the same thing and checks the file first: it confirms the 67CLIPPER platform, version V7.3-1 and HP's checksum, refuses anything else (including HP's update image and the V7.2-1 and V6.2-1 consoles), and reports the hash of what it wrote. It accepts the .exe or the .sys:

python tools/extract_es40_cl67.py cl67srmrom.exe es40_v7_3.exe

 

Naming it and putting it in place

Name the prepared file es40_v7_3.exe and copy it into the system's firmware folder. In the launcher, press Open firmware folder on the Named System Details tab, copy the file there, then select it in the Firmware control.

 

The name matters. EMulatR names everything that belongs to a firmware image after the file name: the platform manifest es40_v7_3_platform.json, the flash (console settings) es40_v7_3.rom, and the speed-up and badge profiles. Under any other name, es40_cl67.exe or cl67srmrom.exe for example,

EMulatR finds no ES40 manifest, falls back to its built-in DS10 platform, and the run stops with a PLATFORM MISMATCH error.

 

Note the name clash: HP's ES40 update file is also called es40_v7_3.exe. If a system misbehaves, check that the es40_v7_3.exe in its firmware folder is 692,224 bytes and carries the hash above. HP's update file is 2,822,144 bytes.

 

Or: a pre-decompressed image

Instead of the prepared es40_v7_3.exe, EMulatR can boot the console already decompressed, as a .rom. Make it with the tool shipped in the tools folder; it accepts HP's cl67srmrom.exe as downloaded or the prepared es40_v7_3.exe, and both give the same file:

tools\host_firmware_decompressor.exe cl67srmrom.exe --rom console\es40_v7_3.rom

The result is byte-for-byte identical to the reference image EMulatR's loader was validated with. It is optional: see Pre-decompressing the Firmware for how to boot it and what it does and does not gain today.

In the source tree

For developers building EMulatR: the prepared image is kept as common/firmware/es40_v7_3_cl67srm.exe, and the build copies it to firmware/es40_v7_3.exe beside EMulatR.exe. HP's update image is kept as common/firmware/es40_v7_3.exe_do_not_use and is never copied.

 

Background

Earlier builds used HP's firmware-update image, which is a different program: it boots the Loadable Firmware Update utility (LFU) instead of the console, runs it on every cold boot, and on the ES40 never returns to a console prompt after the utility exits. That image is kept for firmware-update testing but is no longer staged.

 

HP ships two SRM builds for the ES40: CLIPPER for the EV6 processor and 67CLIPPER for the EV67 and EV68. EMulatR uses 67CLIPPER, and presents the processor that build expects: an Alpha 21264B (EV68CB), a part real ES40 systems shipped with. Earlier builds presented an EV6, and the console printed *** Warning - PALcode/CPU Mismatch - Reload SRM Firmware *** at every power-up; it no longer does. The processor identity is set per platform, so the DS10 and DS20 are unchanged.

 

Flash and console settings

The ES40 keeps its SRM environment variables in its 2 MB flash, not in a separate NVRAM file. EMulatR stores the flash in firmware/es40_v7_3.rom in the run directory and writes it back on a clean shutdown. The flash also holds the firmware images an LFU update writes:

To start from factory-fresh settings, shut the machine down, then rename es40_v7_3.rom (do not delete it) before the next launch. EMulatR creates a new, blank flash when the file is missing.

Status

•SRM console to P00>>> with every device present.

•OpenVMS V8.3 boots from the SCSI system disk (b dka200) through startup to the Username: prompt, with the JIT off and with it on (EMulatR_JIT=fused).

•The IDE controller (ALi M5229) presents its interrupt, its base address registers and its bus-master registers as the real part does. The console lists the CD as dqa1 and boots from it.

 

Known limitations

•Installing OpenVMS from the CD (b dqa1) does not complete yet. The CD boots and OpenVMS starts to load, then waits indefinitely when it begins to use the IDE controller. Install on a DS20 and copy the disk, or boot the ES40 from an installed SCSI disk.

•show config shows an unreadable AlphaBIOS (ARC) version, and placeholder versions for the RMC and the TIG.

•After an LFU update, the update utility does not return to the console on its own: the TIG module reset it relies on is not modelled. See ES40 TIG Module Reset.

•Only the 67CLIPPER SRM console (cl67srmrom.exe) works. HP's ES40 firmware-update images (es40_vN_N.exe) and the CLIPPER (EV6) console are not supported yet.

 

SMP considerations

The ES40 supports four CPUs; EMulatR runs one. Running more than one CPU (SMP) is planned for release 2.3, with every CPU on one host thread so that a run stays deterministic and repeatable. A threaded mode, one host thread per CPU, follows in release 3.1. Everything in the DS20 guide's SMP section applies. What the ES40 adds:

•Four CPUs, not two. Every per-CPU structure in the Typhoon chipset (interrupt masks and summaries, inter-processor interrupts) must hold four entries, and the one-thread schedule has to be fair across four.

•CPU identity. The console checks the processor type against its PALcode build. EMulatR now presents an EV68CB, the identity the 67CLIPPER console expects, and applies it to every CPU, so the secondary CPUs will carry the same identity when SMP arrives.

•The TIG. EMulatR's design releases the secondary CPUs through the TIG, and on the ES40 the TIG is also where the unmodelled module reset lives. Both have to work before the ES40 runs more than one CPU.
