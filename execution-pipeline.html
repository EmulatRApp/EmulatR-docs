Execution Pipeline

EmulatR executes guest Alpha instructions through two cooperating paths: a six-stage main pipeline that models the full instruction lifecycle, and a four-stage block path that accelerates hot straight-line code. The two paths are mutually exclusive per instruction — every retired instruction completes on exactly one of them — and both produce identical architectural results.

 

The main pipeline (six stages)

The main pipeline carries every instruction through fetch, decode, context build, execute, drain, and retire. Decode results are cached, so repeated instructions do not pay the decode cost twice, but each retire still runs the full per-instruction boundary work: interrupt evaluation, tick bookkeeping, and dispatch re-entry. All privileged operations, PALmode execution, and exception paths run here.

 

The block path (four stages)

On a hot hit, the block path elides the front-end: fetch and decode are served from a cached descriptor run, and execution proceeds directly through context build, execute, drain, and retire. These are not different stages — they are the same back-end code as the main pipeline, invoked verbatim, with the front-end amortized across the block. Fidelity is therefore structural, not asserted: the block path cannot compute a different result because it executes the same execution engine.

A block ends where straight-line execution ends: at a branch taken, a page boundary, a privileged or PALmode instruction, or the configured block-length limit. Code that does not qualify simply runs on the main pipeline; there is no functional difference, only a performance one.

 

Fidelity contract

Architectural state — registers, memory, and processor state — is exact per retired instruction on both paths. What the block path coarsens is interrupt-delivery granularity: interrupt evaluation runs at block boundaries and at the configured sweep interval rather than after every instruction, so delivery latency is bounded by a small number of guest cycles rather than zero. AST delivery is never deferred. This contract is certified by byte-level shadow checking: the block path with the shipping sweep configuration has been verified against the reference execution over more than 988 million operations through a complete OpenVMS boot with zero mismatches.

 

Workload behavior

The block path benefits code that revisits the same instruction sequences: tight loops, spin waits, and the operating-system idle loop are the best cases. Measured guest workloads spend the large majority of their execution in such repeated runs, which is why a running guest feels responsive: the hot path serves repeated work from the block cache while cold and privileged code takes the faithful main pipeline.

 

Configuration

The execution pipeline is controlled by environment variables, documented in the environment-variable registry. The block path is on by default; EMULATR_BLOCKEXEC=0 turns it off for comparison runs. EMULATR_BLOCK_MAX bounds the instructions per block (2 to 256, default 32). EMULATR_BLOCKCACHE_BLOCKS sets the block-cache capacity (minimum 256, default 8192). EMULATR_IRQ_MODULUS sets the interrupt sweep interval in guest cycles (1 to 524288, default 1). A value outside a variable's documented range reverts to the bound defined by the code.
