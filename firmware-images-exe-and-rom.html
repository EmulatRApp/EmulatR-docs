Firmware Images: .exe and .rom

Two files in the firmware\ directory can share a name and differ only by extension - ds20_v7_3.exe and ds20_v7_3.rom - and they are not two copies of one thing. One is the firmware you boot; the other is the flash memory that boot writes. Knowing which is which explains what the emulator does at startup and what it says when a file is pointed at the wrong slot.

 

The three kinds of file

File

What it is

Role at startup

ds20_v7_3.exe

The vendor firmware UPDATE DISTRIBUTION image - a self-decompressing blob shipped by Digital / Compaq.

This is what EMulatR boots. The decompressor stub sits at the very start of the file; it is loaded and run, unpacks the PALcode and SRM console, and hands control to the console. Because it is the update image, it also walks the firmware-update prompts on the way through - see Firmware Update Utility (LFU).

ds20_v7_3.rom

EMulatR's flash / NVRAM backing file: 2 MiB, the contents of the emulated flash device.

Not booted. It is bound automatically alongside the firmware image and is where the machine's persistent state lives - SRM environment variables, and whatever a firmware update writes. It is a PRODUCT of running the .exe, not an alternative to it.

cl67_decompressed.rom

A pre-decompressed console image (AXPBox layout): a 16-byte header followed by a 2 MiB console image.

Bootable, and the only kind of .rom the loader will accept. The header carries the entry PC and PAL_BASE, the image is already unpacked, so there is no decompression stage at all. Made from a compressed console with tools\host_firmware_decompressor.exe (below).

 

Making a pre-decompressed image

tools\host_firmware_decompressor.exe runs the same decompression the firmware runs at every cold boot -- DEC's own algorithm, built natively -- and writes the result in the format above: tools\host_firmware_decompressor.exe cl67srmrom.exe --rom firmware\es40_cl67srm.rom

 

It finds the compressed console in the file, decompresses it, takes the PAL_BASE value from the firmware's own start-up code, and writes the 16-byte header (entry PC = load address + 1, for PALmode) followed by the 2 MiB image with the console at its load address. It prints what it did:

wrote firmware\es40_cl67srm.rom (entry PC 0x8001, PAL_BASE 0x600000 from stub@0x240, 2097168 bytes)

 

Without --rom it writes only the raw decompressed console (ref_decompressed.bin), for inspection. From HP's cl67srmrom.exe the .rom is identical, byte for byte, to cl67_decompressed.rom. How to boot it, and when it is worth doing: Pre-decompressing the Firmware.

 

How the loader chooses

The extension selects the loader, and --firmware-format overrides it:

•--firmware-format auto (default) .exe -> the self-decompressing SRM loader .rom -> the pre-decompressed console loader  anything else -> raw binary

•--firmware-format srm force the SRM loader

•--firmware-format raw force a raw binary load

 

The platform manifest is keyed to the SYSTEM stem, not to the firmware file name. The system stem is --system-stem if given, else the ini key [System] systemStem, else the firmware file's own stem. So both extensions select the same device set: with systemStem = es40_v7_3, es40_cl67srm.exe and es40_cl67srm.rom alike resolve to es40_v7_3_platform.json; with neither set, ds20_v7_3.exe and ds20_v7_3.rom alike resolve to ds20_v7_3_platform.json. Model and firmware therefore cannot drift apart.

 

Which flash file gets bound

The flash backing is resolved in this order, first match wins: EMulatR_FLASH_ROM > ini [ROM] flashImage > <system-stem>.rom > ds10_v7_3.rom

So booting firmware/ds20_v7_3.exe binds firmware/ds20_v7_3.rom beside it without being told to, and reports which file it picked:

FlashRom: NVRAM backing -> 'firmware/ds20_v7_3.rom'

 

The <system-stem>.rom sits beside the firmware file, and a pre-decompressed console binds it exactly as the .exe does: with systemStem = es40_v7_3, booting firmware/es40_cl67srm.rom binds firmware/es40_v7_3.rom. EMulatR refuses to use a console .rom as its own flash; if the resolution would pick one, it prints FlashRom: REFUSED.

Give each concurrently running instance its own flash file - two machines sharing one backing file will corrupt it.

 

What to expect if you point --firmware at a .rom

Setting the firmware to the flash backing file is the natural mistake, because the name matches and the file is obviously firmware-shaped. It does not boot, and it fails immediately and specifically rather than misbehaving later.

 

The flash backing is exactly 2 MiB of device contents. The pre-decompressed loader wants a 16-byte header in front of the same-sized image, so the size check rejects it before anything is loaded: EMulatR: SrmLoader: decompressed.rom wrong size (got 2097152, expected 2097168): firmware/ds20_v7_3.rom

 

The emulator then exits with status 2, the firmware-load failure code. The sixteen bytes are the whole difference: 2097168 minus 2097152.

 

Forcing the SRM loader onto the same file fails differently, and the second message is worth recognizing because it also appears when a genuinely damaged .exe is offered: EMulatR: SrmLoader: decompressor signature not found in first 4096 bytes of firmware/ds20_v7_3.rom

 

That is not an arbitrary refusal. In a firmware update image the decompressor stub is the first thing in the file, at offset zero. In a flash backing the low addresses are erased device space - all 0xFF - and the console content sits far higher up, well past the 4096-byte header window the loader scans. The signature exists in the file; it is simply nowhere near the front, because a flash image is not laid out like a distribution image.

 

A correctly formed pre-decompressed image, by contrast, loads with no decompression stage and no announcement: the console image goes to physical address 0 and execution starts at the entry PC from the header - typically 0x8000 in PAL mode, with PAL_BASE 0x600000.

Booting the machine's own updated flash content directly - the way a real DS20 runs its console from flash after the update image has been run once - is tracked work, not current behaviour. Until it lands, every cold boot re-runs the update image, which is why the firmware-update prompts appear on every boot and why the console answers them for you.
