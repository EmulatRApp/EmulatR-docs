6.12 Guest Time

EMulatR keeps the guest's time in processor cycles, not in host time. Every clock the guest can read is driven by the emulated processor's cycle count, so the guest's sense of time depends on how many instructions it has executed, not on how long the host took to execute them.

 

The guest's clocks

•Cycle counter. The processor's cycle counter (read with RPCC) advances with every cycle the guest executes.

•Interval timer. The interval timer interrupts the guest 1024 times per guest second. At a CPU speed of 50 MHz that is one interrupt every 48,828 cycles (and a fraction, kept exact over every 1024 ticks).

•Time-of-year clock. The battery-backed clock that OpenVMS reads at boot advances with guest cycles too, from the starting time set by its mode (below).

 

One guest second is as many cycles as the CPU speed: 50 million at the default 50 MHz (the supported speeds are 50, 60, 75, 85 and 100 MHz). See 11. Tuning EMulatR for setting the speed and for what it changes.

 

Dilation

Dilation is the number of wall-clock seconds the host takes to run one guest second. It depends on the host and on what the guest is doing: a boot, an idle prompt and a busy workload all run at different rates. At a dilation of 1.0 the guest's clock keeps pace with the wall clock; above 1.0 it falls behind, below 1.0 it gains. OpenVMS's own clock follows EMulatR's guest time exactly, so its drift against the wall clock is the dilation and nothing else. Measured figures for each platform are in 11. Tuning EMulatR.

 

Waits

When the guest waits by watching its clocks, for example a firmware delay loop that polls the cycle counter until a deadline, EMulatR can advance the clock to the end of the wait instead of executing every pass. The guest sees the same times and the same interrupts as if it had executed the wait; only the host time it takes is shorter. The WARP-ACCOUNTING line at the end of the run log totals the guest cycles advanced this way.

 

Time-of-year clock modes

The setting EMulatR_TOY_MODE chooses where the time-of-year clock starts:

•host (the default). The clock starts from the host's local time when EMulatR starts, then advances with guest time. Because the guest runs dilated, the guest's date and time gradually fall behind (or, on a fast idle platform, run ahead of) the host during a long session.

•fixed. The clock starts from a fixed date (EMulatR_TOY_FIXED_EPOCH) and advances with guest cycles only, so every run sees exactly the same times. Use it for repeatable test runs.

•unset. The clock behaves like hardware with a dead battery: it is invalid until the guest sets it, so OpenVMS may ask for the date at boot.

 

To correct the guest's time in a long session, set it from the guest, for example with the OpenVMS SET TIME command.

 

Measuring guest time

 

Measuring guest time. Press Ctrl+/ in the console: EMulatR prints a host status line with the host time, the exact guest cycle count, the guest time and the time dilation. Press it twice around anything you want to measure; the d_dil field on the second line is the dilation over that interval (host seconds per guest second). The fields are listed in Console Control Keys.

 

Idle pacing

 

When the guest is idle, EMulatR recognizes the idle loop and collapses it: the cycles the loop would have used are credited to the guest clock in one step, for almost no host time. Left alone, guest time can run ahead of wall time while the guest is idle. In the measured DS20 idle case the idle dilation fell to 0.35, meaning the guest clock ran about three times faster than the wall clock. Guest time running ahead of wall time in idle is not acceptable, so EMulatR paces idle guest time to wall time with an idle pacing barrier.

 

The barrier works at each idle collapse. A stretch is a run of collapses that are less than 20 ms apart. If the guest time that has passed since the anchor of the stretch exceeds the wall time that has passed by 2 ms or more, the host sleeps for the difference. Idle guest time therefore cannot run ahead of wall time. On the DS20 the idle dilation moved from 0.35 to 1.01. A boot is not affected: it made no sleeps.

 

The idle pacing barrier ships in the 3.0 Experimental release (X3.0-2) and is on by default. It works wherever IdleScan takes effect, which is the DS20 and the ES40; there the measured idle ratio of guest time to wall time is 1.00. Setting EMulatR_IDLESCAN=0 turns IdleScan and the barrier off.

 

Known open item, DS10. IdleScan does not take effect on the DS10, because no matching idle site is recognized there, so the barrier does not apply. The DS10 runs fast at idle: its guest time is not held to wall time. A general barrier for the DS10 is under review and is not part of this release.

 

For how the idle loop is recognized and collapsed, and the options that control it, see 6.14 IdleScan.
