Console Trace Hotkey

The console trace hotkey lets the operator start and stop a full instruction trace from the console, at the moment something interesting starts. It suits problems that only show up late in a run, such as a boot that goes quiet after a particular console message, where tracing from power-up would take far too long and produce far too much data.

Each traced instruction is written with its program counter, encoding, mnemonic, PAL mode and the full integer register file, so the trace shows exactly what the processor did while the window was open.

 

Requirements

The hotkey is a diagnostic facility. It exists only in diagnostic builds (RelWithDebInfo). The Release build that the kit installs does not contain it.

 

It is off unless the run is started with EMulatR_DIAG_TRACE_HOTKEY=1. Without that setting the two keys pass to the guest unchanged, as in any other run.

 

The keys

Key

Character

Action

Ctrl/\

0x1C

Opens the trace. Tracing starts at the next instruction the processor completes.

Ctrl/]

0x1D

Closes the trace at the next instruction. Pressing Ctrl/\ again later opens a new window in the same file.

 

EMulatR takes both keys before they reach the emulated serial port, so the SRM console and the operating system never see them. They can be pressed at the >>> prompt, during a boot, or while the guest is silent. Neither key is used by the SRM console, and neither starts an escape sequence, so arrow keys and command recall keep working. (Ctrl/[ is not used because it is the ESC character that begins every arrow and function key sequence.)

 

In PuTTY, type the keys as Ctrl and backslash, and Ctrl and right square bracket. A raw connection passes them through unchanged.

 

Running with the hotkey

Set the variable in the shell that starts EMulatR. Set EMulatR_RETIRE_TRACE_DIR as well, so the trace lands in the run directory's traces folder beside the run log:

EMulatR_DIAG_TRACE_HOTKEY=1 EMulatR_RETIRE_TRACE_DIR=./traces tools/EMulatR_env.sh ds10 hotkey

 

A typical session:

1.Boot as usual, for example b dqb0.

2.Wait until the run reaches the stage to be studied, for example the console going quiet after a message.

3.Press Ctrl/\ and let the run continue for as long as the trace is wanted.

4.Press Ctrl/], or stop the run cleanly by creating the EMulatR_STOP file in the run directory. A clean stop closes an open trace properly and writes the end-of-run record.

Stop the run cleanly rather than ending the process; a killed process loses the end of the trace and the flash contents.

 

What the run log shows

Each key press is confirmed in the run log, and the trace sink reports the exact cycle and program counter where the window opened and closed:

TRACE-HOTKEY: Ctrl/\ -> full retire trace OPENS at the next retire

BRKSINK: FORCE-OPEN at cyc=1526406171 pc=000000000007fe70 -- full trace until shutdown

TRACE-HOTKEY: Ctrl/] -> full retire trace CLOSES at the next retire

BRKSINK: FORCE-CLOSE at cyc=1527486428 pc=00000000000847cc -- full trace stopped

 

When the IDE wire log is also on (EMulatR_DIAG_ATAPIWIRE), each key press is recorded there as a HOT event and the wire log is written to disk at that moment, so the device events leading up to the trace are on disk even if the guest has gone quiet.

 

The trace file

The trace is written to <date>-<time>_break.trc in the folder named by EMulatR_RETIRE_TRACE_DIR. If that variable is not set, it goes to D:\EMulatR\traces. Every window in one run goes into the same file:

•BP_OPEN marks where a window opened. It is followed by IPR_SNAP, PT_SNAP and CBX_SNAP records holding the processor's internal registers, PAL temporaries and cache-box state at that point.

•One BRK line per completed instruction: cycle, program counter, encoding, mnemonic, PAL mode, exception address, and registers R00 to R30, plus the memory address and value for loads and stores.

•BP_CLOSE marks where a window closed, with the same register snapshots.

•RUN_END is the last line of a cleanly stopped run. A file without it was cut short.

 

The file grows by roughly 0.75 GB for every million instructions traced, and the run slows down sharply while the trace is open. Keep windows short and aim them at the stage under study; check the free space on the trace drive before a long window.
