6.9 Storage Engine

This chapter is the technical companion to the Storage section of Operating EMulatR. That section covers creating and attaching disk images; this chapter explains what happens to a guest disk request after it leaves the emulated SCSI or IDE controller: which code serves it, which host threads touch it, what is guaranteed about it when something fails, and every setting that controls it.

 

Two storage engines

EMulatR has two interchangeable engines behind the emulated storage controllers. The platform manifest chooses between them with one key, storage_engine.

Engine

Manifest value

What serves a writable disk

Direct

direct, or the key absent (the default)

FileBlockMedia: a host file read and written in place through the ordinary Windows file cache.

Pool

pool

The storage pool (storageLib): EMulatR's own resident page cache in front of each image, with per-disk read workers and one ordered writer.

 

Both engines sit behind the same seam, the block-media interface, so the emulated controllers and the guest cannot tell which one is in use. Both complete every guest request before the guest instruction that issued it finishes, so a storage request never advances guest time on either engine. Measured side by side, the same boot on the two engines produces the same console output with guest time-of-day agreeing to within a few hundredths of a second through startup. Wall time and host resource use are what differ.

 

What the pool adds

•A read cache EMulatR controls: repeat reads of a page are served from locked memory (measured at a median of 0.6 microseconds, against about 57 microseconds for an unbuffered host read) instead of a host call.

•Truthful durability: images are opened with host caching disabled for writes (write-through), so a write reported complete is on the host device, not only in the Windows cache.

•Ordered write-back as an option: with write_cache set to ordered a disk acknowledges writes from memory while one writer drains them to the host in exact guest order.

•Defined behaviour when the host fails: bounded waits on every host call, retry, a paused writer that keeps queued data in memory, and a dump of modified pages so nothing acknowledged is silently lost.

 

Status in this release

•The pool serves writable disks (SCSI and ATA). CD and ISO images always stay on the direct engine.

•Write mode off (write-through) is the default and the recommended setting. Write mode ordered is experimental: the machine-wide pause that must accompany a failing ordered writer is not yet wired into the emulator.

•Planned, not yet present: a separate system-disk pool that reports host failures to the guest as a device failure; automatic replay of a dump at the next start; SYNCHRONIZE CACHE, FUA and a truthful write-cache bit in the SCSI disk model.
