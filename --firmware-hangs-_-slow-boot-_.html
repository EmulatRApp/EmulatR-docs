Firmware Hangs, Slow Boot, and Missing Devices

Firmware hangs (usually timed loops, not crashes)

Some long pauses are time-based firmware loops rather than emulator hangs:

•-The option-firmware scan -- after "Checking dva0.0.0.0.0 for the option firmware files. . ." the firmware enters a krn$_sleep-based wait (the 0x7bef0 software-tick loop). It is a timed sleep, not a device probe; a profiled gap of roughly 36 minutes was observed (a 2026-07 measurement, recorded here as a historical observation - it predates several boot-path fixes and has not been re-measured on a current build) has been observed here (open item).

•dqa0 "no media present" is followed by a stall (suspected timer loop).

•FIXED in X1.6-15 - the multi-minute stall right after the SRM banner. On earlier builds the guest issued READ LONG / WRITE LONG, the adapter answered UNSUPPORTED, and the retry ladder behind it cost roughly six minutes on every boot before startup continued. If you still see a post-banner pause of minutes, you are on a build older than X1.6-15; there is nothing to configure. Verified on two hands-off cold boots with no unsupported-command reports and no stall.

•GCT/FRU initialization can be significantly delayed.

•ES40 silicon mode: a stall at "Initializing...." after an LFU exit / update srm is the (experimental) TIG module reset, not a crash -- see the ES40 TIG Module Reset topic.

 

Slow boot (shorten it)

Boot time is dominated by power-up diagnostics and several bounded timeout loops. To speed iteration, turn the heavy diagnostics off at the prompt:

 

>>> set memory_test none

>>> set full_powerup_diags off

 

Bounded device-wait loops - these are the firmware's own iteration counts times its per-iteration delay, so they are upper bounds derived from the firmware rather than measurements of a run (approximate wall-clock): dq_wait_on_busy ~5000 x 100us; dq_wait_for_drq ~5000 x 100-200us; dq_long_wait_on_busy ~310000 x 100us (about 31 s). The warp levers that used to collapse these waits - EMULATR_IDLEWARP and its family - were removed on 1 August 2026: they advanced the guest clock without replaying the timer edges, and the launcher now strips them from every child environment. EMULATR_UDELAYWARP is the surviving lever and is safe by construction: it advances only as far as the next timer edge, so no boundary is skipped. On a repeated run the self-decompression need not happen at all: snapshot autoload is the default, so a launch with no --no-autoload resumes the newest snapshot instead of cold booting (see Boot Acceleration - Entry Snapshot). Pass --no-autoload when you specifically want a genuine cold boot - without it a run that looks slow may simply be resuming.

 

Guest hangs after the operating system takes over

These are past the firmware. The console is still yours - the SRM is not involved once OpenVMS is running.

•TCPIP startup stops at %TCPIP-I-STARTDROUT and does not come back. This is a known open item, and there is no workaround today. You may also see %TCPIP-E-INVINTER earlier, naming an interface called SE0 - that one is left-over configuration inside the disk image describing a network card this machine does not have, and it is harmless. The rest of the system is up: the hang is in TCPIP's dynamic-routing step, not in the boot. If you do not need networking in the guest, the practical course is to leave TCPIP out of startup for now.

 

Messages you can ignore

•An UNSUPPORTED opcode line from the virtual disk device. The guest asked the disk for a command the model does not implement; the guest handles the refusal and carries on. It is diagnostic output that was left switched on in the shipping build by mistake - it is not an error, and it does not mean data was lost or a command failed silently.

 

Missing devices

If a device is absent from show device, check the IDE / ATAPI enumeration path. The dqa CD enumeration gap is a known open item: the firmware does not always observe the device during the option-firmware scan. Tracing 0x1F0..0x1F7 plus the PCI config of bus 0 / dev 5 / func 1 distinguishes a port-never-initialized case from a probe-protocol mismatch.
