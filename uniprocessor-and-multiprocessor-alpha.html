Uniprocessor and Multiprocessor Alpha Systems

Each Alpha system that EMulatR models was built for a fixed number of processors: the AlphaServer DS10 holds one, the DS20 up to two and the ES40 up to four. This page describes how that difference reaches the guest -- through the console firmware, the Hardware Restart Parameter Block (HWRPB) and OpenVMS -- and what it means for performance under EMulatR. For how EMulatR itself is structured to run more than one processor, see SMP (MultiProcessor) Design.

EMulatR runs one processor on every platform in this release. On the DS20 and ES40 the other sockets are empty, exactly as on a real machine fitted with a single processor.

 

How the firmware describes processors

 

The SRM console firmware is built separately for each platform family, and the build fixes the number of processor slots. That number goes into the HWRPB, the structure the firmware hands to the operating system at boot: one slot per possible processor, each holding that processor's state flags. The slot count describes the machine's capacity, not how many processors are fitted.

 

At power-up every processor that is actually present starts and reports in, and the firmware marks only those slots as present and available. An empty socket leaves its slot's flags at zero. A firmware built for more than one processor also includes the code that starts, stops and coordinates secondary processors; with one processor fitted that code finds nothing to start and costs almost nothing.

A running primary processor shows 1EE (hexadecimal): restart capable, available, present, context valid and the three PALcode flags. An empty slot shows 0.

 

How OpenVMS responds

 

OpenVMS reads the processor slots at boot. On every platform under EMulatR its active, configured, present, powered and tested processor sets all hold processor 0 only. What differs is the number of processors OpenVMS considers the machine able to hold: 1 on the DS10, 2 on the DS20 and 4 on the ES40, taken from the slot count.

 

With more than one possible processor, OpenVMS runs its multiprocessor idle path: on every pass of the idle loop it scans its set of processors, one bit at a time. With a single processor fitted the scan finds nothing to do, but it is real guest work, and a real single-processor DS20 or ES40 performs it too. On the DS10 the same code skips the scan.

 

Observed on the OpenVMS V8.3 system disk used for testing (SYSGEN MULTIPROCESSING = 3 on all three platforms): the DS10 and DS20 load SYSTEM_SYNCHRONIZATION_UNI; the ES40 loads SYSTEM_SYNCHRONIZATION_MIN.

 

What it means for performance

 

The idle scan is the main reason the DS20 and ES40 idle more slowly than the DS10 under EMulatR. Each scan is a tight loop of very short code blocks, which costs EMulatR more host time per guest instruction than ordinary code. Measured at 50 MHz with a Release build, the DS10 idles at a dilation of about 0.93 and the DS20 and ES40 at about 1.9: while idle, their guest clocks run at about half the speed of the wall clock. See Tuning EMulatR for the full figures.

 

The ES40's longer boot has a different cause: its console firmware tests all of memory before starting the operating system, which takes several minutes for 4 GB.

 

Inspecting the processor configuration

 

From a privileged OpenVMS account, the DCL command SHOW CPU/FULL summarises the processor configuration. For the underlying values, use the System Dump Analyzer on the running system:

 

$ ANALYZE/SYSTEM

SDA> SHOW CPU

SDA> EXAMINE SMP$GQ_ACTIVE_SET

SDA> EXAMINE SMP$GQ_CONFIGURE_SET

SDA> EXAMINE SMP$GQ_MAX_SUPPORTED_CPUS

SDA> EXAMINE @EXE$GPQ_HWRPB+90;18

SDA> EXAMINE @EXE$GPQ_HWRPB+@(@EXE$GPQ_HWRPB+0A0)+80

SDA> EXIT

 

The EXAMINE @EXE$GPQ_HWRPB+90;18 line shows three HWRPB fields: the number of processor slots (offset 90), the size of each slot (offset 98) and the offset of the first slot (offset A0). The next line shows the state flags of slot 0; add the slot size once per slot to see the others.
