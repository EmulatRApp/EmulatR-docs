6.13 Grain Composition

A grain is EMulatR's unit of instruction semantics. Every Alpha instruction word the guest executes is decoded to one grain: a leaf function that implements the instruction, plus the static properties the pipeline needs to run it. This page describes what a grain is made of, where its definition comes from, and how it travels from decode to execution. For the code generator that builds the tables, see grainFactoryLib and DispatchTables.

 

What a grain is composed of

The grain appears in the code in three forms. They hold the same information at three levels.

 

The table entry (GrainEntry). One entry exists for each decoded operation, that is, for each (primary opcode, sub-decode) pair in the master table. It is generated at build time and never changes at run time. It has four parts:

 

Field

Meaning

fn

The executor leaf: a pointer to the function that implements the instruction (for example the Ebox leaf for ADDL or the Mbox leaf for LDQ). A leaf is a pure function from the grain and the execution context to a result record. It does not change architectural state itself: the register write, the memory effect and the PC change are applied by later pipeline stages.

semFlags

The semantic flag set. The pipeline stages consult these flags for every cross-cutting decision (which registers the instruction reads and writes, whether it is a load or a store, whether it changes the PC, whether it is a PAL entry) instead of switching on the opcode.

box

The functional box that owns the leaf: Ibox, Ebox, Fbox, Mbox, Cbox or PalBox. A routing hint.

mnemonic

A text literal used by trace and listing output.

 

The decoded slot (InstructionGrain). When an instruction passes through the pipeline, the decode stage builds a small plain-data record, 32 bytes, that rides the pipeline slot until the instruction retires:

 

Field

Meaning

pc

The address the instruction was fetched from. It is set at fetch and never changes. It is not the CPU's architectural PC.

execFn

The leaf function, copied from the table entry. It is never null: an unimplemented or unmapped encoding resolves to the OPCDEC leaf, which raises an illegal-instruction fault.

semFlags

The semantic flag set, copied from the table entry.

encoded

The raw 32-bit instruction word.

box, primaryOp

The box and the primary opcode (bits 31:26 of the word), kept for trace output.

two reserved bytes

Unused. Reserved for future per-grain state.

 

The register numbers, displacement and literal are not copied onto the grain. A leaf reads them from encoded, which is their single source.

 

The cached reference. The decoded-instruction cache and the block cache (described below) store the table entry by pointer together with the encoded word. They never store a copy of the grain.

 

Where the grain definition comes from

The table entries are not written by hand. The master table GrainMasterV4.tsv has one row per Alpha operation, with these columns: mnemonic, primary opcode, sub-decode value, dispatch kind, format, box, semantic flags, notes, an optional leaf base that lets several rows share one leaf, and an optional p2 group. The generator genGrains.py checks the table against SemanticFlags.tsv and emits the dispatch tables, which are then compiled in. The primary table has 64 slots, one per primary opcode. Each slot names a dispatch kind that tells the decoder which bits of the word select the sub-table entry. A slot or a sub-decode with no row resolves to the OPCDEC entry.

 

The p2 column marks the grains that have a specialized P-2 handler. Group A is an operation that writes one integer register and advances the PC by 4, and cannot fault, touch memory, change mode or branch. Group B is a PC-relative integer branch. The generator emits a table of these from the column. An empty column means only the faithful path exists for that grain.

 

How a grain flows from decode to execution

1. Decode. The decoder takes the primary opcode from bits 31:26, indexes the primary table, and then selects the entry by the dispatch kind of that slot (the 7-bit, 11-bit, 2-bit or 16-bit sub-decode field, or a sparse lookup for PAL calls and miscellaneous operations). The result is a reference to the table entry. The lookup has no side effects.

 

2. The decoded-instruction cache. Fetching and decoding give the same answer every time for the same address under the same translation state, so the result is remembered. The cache has 65,536 entries, is direct-mapped on the word address, and each entry is 32 bytes (2 MB in all). An entry holds:

 

Field

Meaning

key

The full PC, including the PALmode bit, so PAL and native code never alias.

gen

The fetch-path generation at fill. Every event that can change the answer (translation-buffer fills and invalidates, writes to I_CTL, PAL_BASE and VA_CTL, instruction-cache flush) increments the generation, so an old entry stops matching.

asn, mode

The address-space number and the current mode, which affect translation.

spec

The P-2 handler index. 0 means the faithful path; 1 to 127 select a Group A handler and 128 to 191 a Group B handler.

ccCls

A reserved byte for the cycle-cost class of the instruction. It is not used yet.

encoded

The raw instruction word.

ge

The reference to the table entry.

 

An entry is a hit only if the key, generation, ASN and mode all match.

 

3. Execution. The grain is run by one of three paths, which give the guest the same result:

•Single step. The pipeline driver fetches and decodes one instruction, or takes it from the cache, builds a pipeline slot and calls the leaf. If the cache entry has a P-2 handler index and P-2 is enabled, the specialized handler runs instead, without building a slot.

•Interpreted block. A block is a straight-line run of already-decoded instructions. It is built by walking the decoded-instruction cache and stops at the first instruction not yet decoded, at a page edge, at an unconditional transfer, before CALL_PAL and the hardware-format instructions, or when the block holds the limit set by EMulatR_BLOCK_MAX (default 32, at most 256). Each descriptor of a block holds the table entry, the encoded word and the primary opcode (plus three reserved bytes). The block executor calls each leaf in turn and re-reads every operand from the CPU state, so it keeps no register contents between instructions.

•JIT. A block that is executed often can be translated to a fused or native form from the same descriptors. Where the translation cannot handle an instruction, execution continues in the interpreter from that instruction.

 

Cycle cost is a property of the grain

The cycle cost model described in the Cycle Harness topic makes the charge for an instruction a property of its grain. The weight of the grain is the 21264 hardware cycle count for the instruction, held in fixed-point units of 1/256 cycle, together with the scale factor. For a conditional branch the weight also includes the expected mispredict cost of that opcode. The weights are generated from the master table at build time, in the way the P-2 group table is. There is no cost file and no run-time setting, so the cost is a property of the compiled image. Whichever path runs the grain (single step, interpreted block or JIT), it charges the same cycles.

 

The charge model and its arithmetic are in 6.11 Cycle Harness.

 

Implementation is in progress. The current build charges one cycle for every executed instruction (Mode A) at a single charging point, and the grain does not carry a weight yet.

The weight is carried by the grain as a ccCls byte; the charging site dereferences it once per retire. This was ruled RUL-20261004-28 and -30 (the ruling log entry).
