Choosing the Host Adapter (Wi-Fi and Wired)

EmulatR bridges the emulated DE500-BA (EWA0) onto one of the host's own network adapters. Which adapter you choose decides whether networking works at all. This page covers the common case of a machine with more than one adapter -- typically a laptop with both Wi-Fi and a wired port -- and how to set it up.

 

The one rule: use a WIRED adapter. Wi-Fi cannot carry the guest.

 

Why Wi-Fi cannot carry the guest

This is a property of Wi-Fi, not of EmulatR, and no setting changes it.

A Wi-Fi access point accepts frames only from the MAC address that associated with it -- your computer's own wireless adapter. The guest transmits under its OWN MAC address, which never associated with the access point, so the access point discards its frames.

Rewriting the guest's MAC to match the host does not rescue it. Under DECnet Phase IV the MAC address IS the node address: DECnet sets it to AA-00-04-00- followed by the area and node number, so a guest at DECnet address 1.3 transmits as aa:00:04:00:03:04. Change the MAC and DECnet no longer works.

 

Identify your adapters

Open PowerShell and list the adapters:

Get-NetAdapter | Format-Table Name, InterfaceDescription, Status, MediaType

 

The MediaType column tells wired from wireless:

Note the Name of the wired adapter -- often Ethernet -- for the steps below.

 

Option 1 -- dedicate the wired adapter (recommended)

The host's own networking moves to Wi-Fi, and the wired adapter carries the guest alone. This is the arrangement EmulatR is designed around, and it needs no EmulatR configuration at all: auto-detection finds the adapter by itself.

 

1. Remove the host's protocols from the wired adapter

In an ELEVATED PowerShell (Run as administrator), substituting your adapter's name:

Disable-NetAdapterBinding -Name "Ethernet" -ComponentID ms_tcpip, ms_tcpip6, ms_msclient, ms_server

 

This takes the host's IPv4, IPv6, file sharing and client off that adapter, so it no longer holds an IP address. Your computer keeps its network connection through Wi-Fi.

 

2. Remove Npcap from every other adapter

Installing Wireshark binds Npcap to EVERY adapter, including the Wi-Fi. Open Network Connections (ncpa.cpl), open Properties on every adapter EXCEPT the wired one you are dedicating, and uncheck Npcap Packet Driver (NPCAP).

Afterwards Npcap should be enabled on exactly one adapter. To check them all at once:

Get-NetAdapterBinding | Where-Object ComponentID -like '*NPCAP*' | Format-Table Name, Enabled

 

Enabled must be True for the wired EmulatR adapter and False for every other, the Wi-Fi included.

 

3. Provision the adapter

From the EmulatR installation folder, in the same elevated PowerShell:

.\tools\provision_enic.ps1 -Match "Ethernet"

 

The script sets the adapter properties that matter for bridging, reports what was already correct, and saves the previous values so the change can be reversed. Its binding check should finish by reporting ONLY Npcap enabled. If it lists anything else still bound, unbind that too.

The script deliberately REFUSES an adapter that still holds an IPv4 address -- which is why step 1 comes first. Re-run it after any network driver update: a driver update resets these settings.

 

4. Start EmulatR with EMULATR_NET_ADAPTER unset

Leave EMULATR_NET_ADAPTER empty. With nothing configured, EmulatR attaches to the one adapter that is up, connected and has NO bound network address. The wired adapter now qualifies; the Wi-Fi adapter does not, because it carries an address.

That rule is also why auto-detection is safe: it can never select the adapter your computer uses for its own networking, because that adapter always has an address.

 

Option 2 -- share the wired adapter with the host

The wired adapter keeps its IP address for your computer AND carries the guest. It works, with two costs:

 

You must name the adapter. Auto-detection will not choose an adapter that holds an address -- by design, so it can never take over your computer's own connection. In the Launcher, open the environment variables panel and set EMULATR_NET_ADAPTER to a distinctive part of the adapter's description, for example I219. Tick the row, or the value is ignored -- see Naming the Host Adapter (EMULATR_NET_ADAPTER). A description substring is better than a device name because it survives a GUID change.

 

Your computer usually cannot reach its own guest. A network adapter does not loop a frame back to its own host. The guest can talk to every other machine on the network, but you typically cannot ping or TELNET the guest from the computer it runs on.

 

The provisioning script refuses a shared adapter unless given -Force. For a test system, Option 1 is cleaner, and it is the arrangement to recommend to anyone else.

 

Laptops: power management

Laptops power down their Ethernet port aggressively, and two defaults work directly against a bridge:

Setting

Effect if left on

Allow the computer to turn off this device to save power

the port can switch off while the guest is idle, and the guest loses its network

Energy Efficient Ethernet

the adapter parks itself between bursts of traffic and the link briefly drops; bulk transfers then fail in a way that looks like an EmulatR defect

The provisioning script turns both off. Do not skip it on a laptop.

 

Confirm it worked

Start the emulator and look for the EWA0 line in the run log. Success reads:

EWA0 network backend ATTACHED to '\Device\NPF_{...}' via Npcap ...

 

Then, from the guest, ping your gateway and another machine on the network.

In every case the guest keeps a working network adapter with no wire attached, and the run continues -- a networking problem never stops EmulatR from starting.

 

Networking makes a run NON-DETERMINISTIC: frames arrive on other machines' schedules. Set EMULATR_NET_ADAPTER to off for any run you intend to time or compare.
