Platform Execution

Every supported model is launched the same way, through one script. The model is not really a flag you choose -- it follows the firmware image the run loads.

 

The launcher

tools/emulatr_launch.sh ds20 bgate

 

The full form is tools/emulatr_launch.sh <ds10|ds15|ds20|ds25|es40|es45> [purpose] [-- extra Emulatr args]. The platform argument is the single input, and it fixes all three identity channels together -- firmware, memory ceiling and ini model -- so a mis-badged or over-allocated launch cannot be typed by hand. For one run the script:

 

- resolves firmware/<stem>.exe and passes it as --firmware;

- requests 4 GiB of guest memory, clamped down to that model's silicon ceiling;

- sets the [System] model line in config/Emulatr.ini and restores the original on exit;

- always raises the PuTTY console -- it unsets EMULATR_NO_PUTTY and sets EMULATR_CONSOLE_MIRROR -- because diagnostic runs are driven by an operator at the console;

- writes a stem-keyed log to logs/<stem>_<purpose>_<timestamp>.log;

- passes everything after -- to Emulatr.exe verbatim, and forwards diagnostic environment variables (EMULATR_VALUE_GATE and the like) from the calling shell;

- on exit, echoes the platform-latched line and flags any PLATFORM MISMATCH.

 

The run directory is $RUN_DIR, defaulting to out/build/v6-relwithdebinfo/run. Set it in the environment to run a different configuration; the script changes into it before launching, so relative paths resolve the same way whichever build you point at.

 

Platform-named wrappers

Six wrappers exec straight into the launcher with the platform already supplied. They hold no argument logic of their own, so there is only ever one place where the per-platform arguments are decided.

 

tools/run_ds20.sh bgate -- --no-autoload --autosnapshot off

DS10, DS20 and ES40 additionally form a standing three-platform gate: all three must still reach the prompt before any shared core, chipset or device change is committed.

 

DS15 is the newest entry and the least finished. Its wrapper exists, but no ds15_v7_3.exe is staged in the run directory, so the launcher stops with a FATAL before the emulator starts; the v7.3 image is in the firmware archive and staging it is what the platform waits on. DS15 is also the one model EmulatR itself does not recognize -- see Platform Identity & Memory Geometry.

 

Cold boots

The launcher has no cold keyword. A genuinely cold boot is requested by passing the emulator flags through: tools/run_ds20.sh cold -- --no-autoload, where the first word is only the log tag. Stale auto_*.axpsnap files are not purged for you, so a run that must not restore from a snapshot should pass --no-autoload explicitly rather than rely on the snapshot directory being empty.

 

What the launcher does not decide

It still rewrites the ini model line, but that is belt and braces rather than the authority: the model is derived from the firmware stem whenever --firmware is given, so ds10_v7_3.exe means DS10 regardless of what the ini says. The rewrite covers the case where the binary in the run directory predates that rule.

 

Memory is clamped twice, and for most models the two agree. The launcher clamps its request to the model's ceiling before launching, and EmulatR clamps again at argument resolution. On a DS10 the 4 GiB default becomes 2 GiB at the first clamp and passes the second untouched. DS15 is the exception: EmulatR does not know the model, so only the launcher's clamp applies, and a bare Emulatr.exe invocation for a DS15 is unprotected. Both clamps announce themselves on stderr; neither is a failure.

 

run_fw.sh, and why it is superseded

run_fw.sh is the earlier launcher, still staged in the run directory and still working for the five models it knows. It is no longer the recommended entry point. It requests a flat 4 GiB with no per-model ceiling of its own, leaving over-allocation to be caught by EmulatR rather than prevented; it does not know DS15; it writes fw_<name>_<timestamp>.out to the run-directory root instead of the stem-keyed name under logs/; and it copies the firmware image in from the source tree on every run. Prefer emulatr_launch.sh or a platform wrapper for new work.

 

Which build to run

The run directory is out/build/<tree>-<config>/run, where <config> is one of release, relwithdebinfo or debug. The launcher lives in the repository's tools/ directory rather than being staged beside the executable, and changes into $RUN_DIR itself, so it can be invoked from anywhere in the tree.

 

Use relwithdebinfo or debug for any diagnostic capture. The EMULATR_DIAG_* retire-time facility is compiled out of release entirely, so a release build will silently produce no diagnostic output rather than warn you.
