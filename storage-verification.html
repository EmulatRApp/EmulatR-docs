Storage Verification

The storage engine is verified from unit tests on an in-memory store, through crash and power-loss simulation on real images, up to guest boots on both engines side by side. This topic describes what each tier checks and the results that stand behind the claims in this chapter.

 

Tier 1: unit tests

test_storage_pool (32 cases) runs the pool against FakeStore, an in-memory backing store that can fail, delay or hang any chosen host call. It covers hits and misses, read-modify-write, copy-on-write ordering, eviction and quotas, back-pressure, both write modes, retry and the retry window, pause and resume, hung reads and writes and rule R-1, orderly abort, dump and discard, dump sealing and the refusal to start over a pending dump. It is part of the standard suite.

 

Tier 2: stamped soak and kill

storage_soak works on scratch images in a marked directory. Every image carries a test signature in sector 0 and is refused without it, and the harness never touches images a guest mounts. Every sector written carries a stamp (disk, sector, sequence number, checksum), so any sector read back can be checked against the history that should have produced it.

Mode

What it does

soak

Random reads, writes and rewrites from 512 bytes to 128 KB, aligned and unaligned, across several images in both write modes, with a pool small enough to force eviction and back-pressure. Every read is checked; at the end every sector of every image is checked.

kill

The workload runs in a child process that logs each intended write before submitting it and reports every durability acknowledgement to the parent. The parent kills the child at a random moment, then checks ORDER (the images hold an unbroken prefix of the history) and DURABILITY (every write acknowledged durable is present).

kill --point

As kill, but the child dies at a named point in the pool: run-pre, run-post, cow, pressure, flush, hung or shutdown (or all).

 

Overnight run (7 hours on a JBOD hard disk, script tools/storage_overnight.ps1): 25 phases, 25 passed. The soak phases verified 54.5 million sectors with none bad. 1,200 kills produced no failures: all 127,350 writes acknowledged as durable were present, and every image was an unbroken prefix at its cut.

 

Tier 4: power-loss simulation (software)

A kill simulates an emulator crash. It cannot tear a write the way losing power can. The power mode covers that in software: the pool runs against real unbuffered, write-through images wrapped by a logging store that records every completed device write with its data. Afterwards, starting from pristine copies, the harness rebuilds the images at hundreds of random cut points. Each rebuild includes every write that completed before the cut plus the in-flight write torn to a random subset of its 4 KB (or 512-byte) units, in any order. Each cut is checked for order, for torn units and for durability, and the fully replayed images must equal the live ones byte for byte.

 

This tier assumes the host honours write-through. Proving that a particular drive does requires a real power-off, which is out of scope. Host requirement: store pooled images on a volume whose device honours write-through (FILE_FLAG_WRITE_THROUGH); a drive that acknowledges writes from a volatile cache defeats every durability promise above.

Guest A/B comparison

The same DS20 guest boots from cold to the OpenVMS Username: prompt on both engines, run side by side with identical disk images and TOY stores. Both reach the prompt with the same console output. Guest time-of-day agrees to within a few hundredths of a second through startup: startup begins at the same guest time in both, and the startup job ends 0.03 guest seconds apart. Executed cycle counts are close but not identical; that residual drift is under investigation. Boot I/O is about one second of the boot, so the engine does not change boot time measurably. The pool's benefit is expected in guest workloads that repeatedly re-read pages the guest's own caches (XFC, VIOC) do not hold.
