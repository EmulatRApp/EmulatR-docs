Console Control Keys

The console is a serial line (COM1) that EMulatR carries over TCP to your terminal client. Control keys typed there travel down that line like any other character. Five of them matter when operating EMulatR: two belong to the operating system, one is EMulatR's status key, and two are EMulatR's own diagnostic keys.

Key

Byte

Handled by

What it does

Ctrl/P

0x10

The guest (OpenVMS and the SRM console)

With OpenVMS running: halts the CPU and returns to the SRM console, which reports the halt and shows P00>>>. From there crash forces a crash dump, and continue resumes the system. See OpenVMS Crash or Hang: Capturing Diagnostics.

Ctrl/T

0x14

The guest (OpenVMS and the SRM console)

At a DCL session with SET CONTROL=T in effect: prints a one-line status of the current process (node, time, process name, CPU time, page faults, I/O, memory). Useful to see whether a long command is still working. At the SRM >>> prompt it prints the console's process table instead (see Ctrl/T: process status, below).

Ctrl/ (also Ctrl/_)

0x1F

EMulatR (every build), then the guest

Prints an EMulatR host status line in your terminal (UTC time, host elapsed time, the exact guest cycle count, guest time and time dilation), then sends Ctrl/T to the guest so OpenVMS or the SRM console prints its own status too. See Ctrl/: host status and cycle count, below.

Ctrl/\

0x1C

EMulatR (diagnostic builds with EMulatR_DIAG_TRACE_HOTKEY=1); otherwise the guest

Starts the full instruction trace at the next instruction. See Console Trace Hotkey.

Ctrl/]

0x1D

EMulatR (diagnostic builds with EMulatR_DIAG_TRACE_HOTKEY=1); otherwise the guest

Stops the trace started with Ctrl/\. See Console Trace Hotkey.

Ctrl/P: halting OpenVMS

Ctrl/P is the operator halt. EMulatR passes it to the guest unchanged; OpenVMS and the SRM console do the rest, as on the real machine. After the halt the machine sits at P00>>>:

Type at P00>>>

Result

crash

OpenVMS writes a crash dump and reboots (if the system is set to). Set up the dump first -- see OpenVMS Crash or Hang.

continue

OpenVMS carries on from where it was halted.

b (boot)

Not recommended today: a warm boot after a halt faults the second boot (JRN-KSNV-001). Exit EMulatR and start it again for a fresh boot. See System Disk Configuration.

Note: A run with guest delay-loop warp on (EMulatR_UDELAYWARP) can be slow to answer Ctrl/P. If the halt does not appear, wait a few seconds before pressing it again.

 

Ctrl/T: process status

Ctrl/T is an OpenVMS terminal feature, off until enabled with SET CONTROL=T (put it in LOGIN.COM to have it always). The time it prints is the guest's clock, which runs slower than wall-clock time under EMulatR by design, so do not use two Ctrl/T lines to time something in real seconds.

At the SRM console prompt (>>> or P00>>>), Ctrl/T is handled by the console itself and needs no setting: it prints the console's process table -- each console task (shell, polling tasks, timer, idle) with its ID, priority, accumulated CPU time, affinity and state. It is the same list as the SRM show process command, and is a quick way to see that the console is alive and what it is waiting on:

 ID PCB Pri CPU Time Affinity CPU Program State

-------- -------- --- -------- -------- --- ---------- ------------------------

00000268 3ff53180 3 1 00000001 0 shell ready

00000008 3ff26160 5 2 00000001 0 dup_poll waiting on tqe bca7c

00000004 0002e020 7 0 ffffffff 0 timer waiting on timer

00000001 001b8560 0 19775 00000001 0 idle ready

At either prompt, press Ctrl/ instead of Ctrl/T to get the same output plus EMulatR's host time and cycle count above it.

 

Ctrl/: host status and cycle count

Ctrl/ is EMulatR's status key. EMulatR takes the key before it reaches the emulated serial port, writes one host status line to your terminal, and then hands the guest a Ctrl/T in its place. The host line is printed first, so it appears just above the guest's own Ctrl/T output. It works at the DCL prompt and at the SRM >>> prompt. OpenVMS prints its Ctrl/T line only when SET CONTROL=T is in effect; the EMulatR line is printed either way. The host line goes to your terminal only -- the guest never receives it -- and it is also written to the run log.

The line is a set of key=value fields, so it can be read by eye or picked out of a log by a script. An example, from an idle DS20 at the DCL prompt with the CPU clock set to 50 MHz:

[EMulatR host] utc=2026-10-05T02:27:49.051Z tz=-07:00 t_run=892.934 cyc=39987484804 ret=11173833917 warp=22506048894 hz=50000000 guest_s=799.750 dil=1.12 mhz_eff=44.78 mhz_exec=19.58 mhz_warp=25.20 ips=12513616 d_run=36.494 d_cyc=1821288533 d_guest=36.426 d_dil=1.00

CPU rating block. After the host line, Ctrl/ prints a formatted CPU rating block. It is calculated at the moment you press the key, never read from the stored badge value. This part of the status key is in development and is not yet in a released build. An example, from an idle DS20 at the DCL prompt with the CPU clock set to 50 MHz:

 

[EMulatR] CPU rating: 44.8 MHz effective = 19.6 MHz executing + 25.2 MHz skipped waits

 (clock 50 MHz, Mode C2); last 36.5 s: 49.9 MHz effective, 49.9 MHz executing, guest 36.4 s for 36.5 s wall (x1.00)

 since power-on: guest 13:20 for 14:53 wall (x1.12)

 

The terms mean the following.

 

•Effective MHz: guest cycles per wall-clock second. It shows how fast the guest clock advances.

•Executing MHz: cycles from executed instructions per wall-clock second. This is the CPU-work rating.

•Skipped waits: the cycles that warps add: guest timer waits that EMulatR skips in closed form instead of executing.

•Clock: the configured CPU speed.

•Mode: Mode A counts one cycle per instruction. Mode C2 uses the cycle weights from the hardware reference manual. The mode is a build choice.

•last: the interval since the previous Ctrl/ press. Press Ctrl/ twice a few seconds apart to read the current rate.

•(xN): wall-clock time divided by guest time. 1.00 means the guest runs in real time; a figure above 1 means the guest runs slower than real time.

 

How to read it. dil is the long-run average and includes the boot, which is mostly warped. d_dil answers "how slow is the guest clock right now?": press Ctrl/ twice around whatever you want to measure -- an idle prompt, a command, a copy -- and read d_dil on the second line. See 6.12 Guest Time for what the figures mean and how the CPU clock setting changes them.

To use a different key, set EMulatR_CONSOLE_STATUS_KEY to its byte value (for example 0x1E); 0 turns the status key off and passes the byte to the guest. Ctrl/\ and Ctrl/] are taken by the trace hotkeys, and Ctrl/[ is the escape prefix of every arrow and function key, so do not choose those.

 

Ctrl/\ and Ctrl/]: the trace hotkeys

These two are EMulatR's own keys, active only in a diagnostic build (RelWithDebInfo or Debug) started with EMulatR_DIAG_TRACE_HOTKEY=1. EMulatR takes them before they reach the emulated serial port, so the guest never sees them. In a release build, or without the setting, they are ordinary characters passed to the guest; neither the SRM console nor OpenVMS uses them. Full details: Console Trace Hotkey.

 

Terminal client notes

Some Telnet clients use Ctrl/] as their own escape key and never send it: the Windows telnet command, for example, opens its own command prompt instead. Use PuTTY (Telnet or Raw) for the console, which sends Ctrl/] as a character. If your keyboard layout does not deliver Ctrl/ as a control character, press Ctrl/_ (Ctrl+Shift+minus), which sends the same byte.

 

See Terminal Clients.

Any key reaches the guest only while a client is connected to the system's console port; the console serves one client at a time.
