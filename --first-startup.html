First Startup

The simplest first run is EMulatRLaunch.exe from the installation: it creates a system, gives it a profile directory to run in, and starts the emulator with the right working directory. See Configuring a System with the Launcher.

 

To do the same from a command line, run FROM your system's profile directory rather than from the installation - the install directory is read-only and a kit upgrade replaces it wholesale, so logs and NVRAM must not be written there:

 

cd '<your profile directory>'

& "C:\Program Files\eNVy Systems, Inc\ASA-EMulatR\EMulatR.exe" --firmware firmware\ds20_v7_3.exe

 

The leading & is required, not decoration. A quoted path is a STRING in PowerShell; without the call operator the shell simply prints the path back and nothing starts.

 

The firmware image is yours to supply - EMulatR ships no SRM image, so the installation has no firmware folder and the profile's own one is where the image goes. See Firmware Requirements. Working from a build tree instead? The developer chapter uses out/build/<tree>-<config>/run/ - see Running from a Run Directory.

 

On launch the TCP console server comes up (default port 10023) and, unless EMulatR_NO_PUTTY is set, a PuTTY session is auto-launched against it. The firmware then runs through its power-up sequence to the SRM >>> prompt. For the step-by-step walkthrough, see Quick Start; to stop cleanly, see Clean Shutdown.

 

Three things about that first boot are worth expecting.

 

The console may appear to type by itself. When the firmware image is an update-distribution image - the DS20 v7.3 image is one - power-up walks a console-update question and the LFU menu before it reaches the real SRM, and EMulatR answers both the way an operator would. Each answer prints one line saying what was sent, so nothing the machine appears to type is unaccounted for. See Firmware Update Utility (LFU).

 

The guest does not ask you for the date. The emulated time-of-year clock is seeded from the host clock by default, so a fresh installation boots with a correct time. Setting EMulatR_TOY_MODE=unset selects the faithful dead-battery lifecycle instead, and with it the boot-time date prompt returns. See Time-of-Year Clock (TOY).

 

The console may report an ISA table error. In a newly created run directory - a new installation or a new named environment - the flash NVRAM file (<stem>.rom, for example ds20_v7_3.rom) starts at its defaults. After the memory and PCI probe lines the SRM prints:

 

probing PCI-to-ISA bridge, bus 1

ERROR: ISA table corrupt!

Initializing table to defaults

 

and later type >>>init to use these changes. This is expected and harmless. The SRM finds no ISA configuration table in the empty NVRAM, builds the default one, and asks for an init so that it takes effect. It appears once for each new run directory. The same boot also prints two other lines, both harmless:

 

*** keyboard not plugged in... - EMulatR has no PS/2 keyboard, so the SRM uses the serial console (PuTTY). This is the intended setup.

 

Flash ROM writes are disabled - printed because a status register that EMulatR models reads back 0. It does not stop the SRM from saving its settings, which persist as described below.

 

At the >>> prompt, type init, then set the boot variables you want, and boot:

 

>>> init

>>> set bootdef_dev dka0

>>> set auto_action boot

>>> boot

 

The init command applies the rebuilt table in the current session only. Restarting EMulatR (a cold start) has the same effect.

 

On the ES40, do not type init. It is not wired for the ES40 and faults with a non-existent-memory error (Known Gaps G-10). Set the variables and boot directly; restarting EMulatR is the way to apply the table on the ES40. See Known Gaps.

 

You can also give the device directly, as in boot dka0. For the variables themselves, see SRM Environment Variables.

 

The SRM keeps its NVRAM, which holds the ISA configuration table and the environment variables, in the NVRAM sector of the flash. EMulatR saves the whole flash to the run directory's firmware\<stem>.rom (the stem is the system stem; for example es40_v7_3.rom for es40_cl67srm.exe) when no flash write has happened for a while (8,000,000 cycles) and at a clean shutdown. The save is atomic. Settings therefore persist across restarts provided EMulatR stops cleanly; a forced kill before the save loses the latest changes.

 

On a new run directory the SRM rebuilds the default ISA table and saves it at once, so the message does not return on the next start. To confirm, start EMulatR a second time and check that the FlashRom "restored" line appears in the run log and that the ISA message is gone.
