Auto-boot

off; the boot command is typed at >>>

Console update

Every cold boot runs the console update (LFU). The driver answers its prompts; set EMulatR_LFU_INTERACTIVE=1 so the emulator's own responder stays out of the way.

Startup

The system disk's startup was corrected on 29 September 2026; it no longer waits for a volume labelled TEST2 on DKA200.

Tests

B-1 to B-8: boot

The eight boot tests (see 11. Test/Regression). One driver session from launch:

python v2.1/tools/srm_console_driver.py --port 10011 --boot "b dka0" --expect "job terminated at" --then-expect "Username:"

Start the driver before the emulator so it holds the console from the first moment. The driver answers the console-update prompts, types the boot command at >>>, waits for the end of startup, sends a Return 20 seconds later and waits for the Username: prompt. Its last line, VERDICT: PASS, is the result.

C-1 and C-2: late console connection

Launch with no console connected (the emulator answers the console update), wait for >>> after the update, then connect the driver and boot as above. C-1 runs with the harness off, C-2 with it on. Record whether the late connection receives anything, and whether the console reacted to its input (the run log's console lines show the boot command if it arrived).

I-1: halt and restart

After Username:, press Ctrl/P, then enter init and b dka0. Expected today: init returns to >>> in about two seconds without re-initialising, and OpenVMS halts with kernel stack not valid shortly after its banner. This is a known fault; the test passes when the machine re-initialises as a real DS10 does (banner and self-test) and OpenVMS boots.

Pass

•OpenVMS startup completes: the STARTUP job reports job terminated at.

•After a Return at the console, OpenVMS prints the Username: prompt.

•No bugcheck, and no halt at the console.

The DS10 instruction count at the end of startup is not compared between runs: the boot command and the console-update answers arrive over a live console, so their timing varies.
