Platform Identity & Memory Geometry

Two rules settle what machine EmulatR is about to be, and both run at argument resolution -- before the machine is constructed. The firmware image names the model, and the requested memory size is capped at what that model's silicon could physically hold.

 

The firmware stem names the model

When --firmware is given, the model is derived from the firmware stem's leading token -- the text before the first underscore, upcased. ds10_v7_3.exe gives DS10. A recognized token overrides the [System] model line in the ini, and the override is announced on stderr when the two disagree.

 

The recognized tokens are DS10, DS20, DS25, ES40 and ES45. With no --firmware, or a leading token that names no known model, the ini model stands -- no guess is made. A vendor firmware revision inside the stem is not part of the identity, so ds20_v7_3_b.rom still resolves to DS20.

 

Before this rule the platform had two identity channels. The manifest was already keyed to the firmware stem, but the model rode the ini -- so an ini reading model=DS20 launched with --firmware ds10_v7_3.exe booted a DS10 device bus under a DS20 model. South-bridge selection, the capability latch and the memory-geometry expectations all followed the wrong machine, while the guest firmware badged itself from the DS10 IIC bus it actually probed. The platform latch reports that split as PLATFORM MISMATCH; it stays in place as the second line of defense for firmware whose stem is unrecognized.

 

Memory is clamped to the silicon maximum

A requested memory size larger than the modeled machine could physically hold is reset to that maximum, and the change is announced on stderr. The policy is clamp-and-continue rather than fail: the ini carries a single memorySize shared by every model, and a DS10 run should not die because the ini was last tuned for an ES40.

DS15 is in the table because the launcher enforces its ceiling, but the binary does not yet. EmulatR recognizes DS10, DS20, DS25, ES40 and ES45 in both its stem-token list and its clamp table, and DS15 is in neither, so a DS15 run takes its model from the ini and is not clamped inside the emulator at all -- the 4 GiB ceiling holds only because tools/emulatr_launch.sh applies it before launch. Adding DS15 to those two tables closes the gap.

 

These are BOX ceilings -- what the chassis holds in DIMMs -- not chipset addressing limits, and the two differ. Titan (21274), the core logic behind DS15, DS25 and ES45, addresses 32 GiB, so a DS25 clamped at 16 GiB is bounded by its 16 DIMM slots rather than by anything Titan cannot reach. The ES40 shows the same split from the other side: 32 GiB is the Model 2 figure, with 32 DIMMs at eight per memory motherboard, while Model 1 carries 16 DIMMs and tops out at 16 GiB. Where one model name covers both builds, the clamp table takes the larger figure, so it bounds the most capable machine of that name and leaves a smaller build of it unprotected.

 

Requests at or below the maximum pass through untouched -- the rule constrains the ceiling, not the floor. A size beneath the machine's minimum, or a geometry the firmware otherwise dislikes, remains the firmware's to reject, exactly as on real hardware.

 

Why an oversized request is not simply a bigger machine

An unsupported geometry does not run slowly and does not report an error. A DS10 -- real maximum 2 GiB -- handed 4 GiB churns its memory configuration indefinitely: past ten billion cycles with no console output after the early banner, alive but never converging, and landing in varied SRM init code rather than one identifiable loop.

 

At 2 GiB the same binary, the same firmware and the same boot reach the memory banner (2048 Meg of system memory), the PCI probe, LFU, the DS10 console banner and >>> within minutes. An unsupported geometry is not a bigger machine; it is an impossible one the firmware was never written to configure.

 

Resolution order

Each setting is resolved in this order, highest priority first:

 

Setting

Resolved from

firmware path

--firmware, else the ini [ROM] firmwareImage

model

the firmware stem, if its leading token is recognized; else the ini [System] model

memory requested

--mem, else the ini [System] memorySize, else 64 MiB

memory granted

the lesser of the request and the model's silicon maximum

 

All four are settled before the machine is constructed, so every downstream consumer -- the chipset and the Cchip address-array registers among them -- sees the clamped value rather than the request.

 

What these rules do not do

Neither rule overrides the platform manifest. EMULATR_PLATFORM_CONFIG still points the manifest wherever an experiment needs it. The model still follows the stem, and the latch still reports a hybrid combination rather than accepting one silently -- an experiment may want a hybrid, but it must not get one by accident.

 

The clamp is a ceiling, not geometry validation. DIMM interleave legality, array counts and alignment are not checked -- only the total size. Faithful geometry modelling, of the kind the ES40 banner reports, is future work.

 

Neither rule changes emulated behavior. Both act at argument resolution, before the machine exists, so there is no snapshot, oracle or determinism impact.
